# WW3MOD lint baseline — the known-bad floor for `./utility.sh --check-yaml` (`make test`).
#
# HOW IT IS READ. Every error the lint emits is reduced to a signature `<scope> | <first line of the
# message>`, where <scope> is the map's package folder name, or `mod` for the mod-wide passes. A signature
# listed here does not fail the run. A signature NOT listed here does.
#
# HOW TO CHANGE IT. Lowering is automatic, raising is not, and that asymmetry is the whole point:
#   * You fixed something -> the run names the entries that no longer occur and FAILS until they are gone.
#     Re-run with LINT_BASELINE_PRUNE=true to remove them and commit this file with your fix. The prune
#     path can only REMOVE lines; it can never add one.
#   * You hit a NEW error -> fix it. Adding a line here is a deliberate act that shows up as an added line
#     in review, and it belongs in the right section, with a reason if it is going in [accepted].
#
# SECTIONS.
#   [repo]                 DEBT. Errors this repository owns and has not fixed. Every run prints this count
#                          as a standing amnesty, with the age of the oldest entry and the largest single
#                          class in it, because the way a baseline fails is not by letting a regression
#                          through — it is by becoming furniture nobody reads. THIS is the number that is
#                          supposed to fall.
#   [accepted]             Errors that are CORRECT and must keep occurring: a map that has to breach a rule
#                          in order to be the test it is. Enforced the same way — if one stops occurring it
#                          still has to be removed — but never counted as debt, because counting a decision
#                          as debt is how a debt figure stops meaning anything. Every entry needs a comment
#                          above it saying why.
#   [requires-ra-content]  Only occur where the Red Alert content is absent. `mods/ww3mod/mod.yaml:15` mounts
#                          `~^SupportDir|Content/ra/v2/`, downloaded at first run; the CI runner never
#                          installs it, so every RA sprite reads as missing there and none of these appear on
#                          a developer machine that has run the game. Matched but never required, so both
#                          environments pass, and never pruned — an environment that cannot produce an entry
#                          has nothing to say about whether it is fixed. NOT defects and NOT lint debt:
#                          installing content in CI deletes this entire section at a stroke.
#

#   CI run 31981227086 (Windows, `Check Mods`):  Errors: 437
#   local `make test` on this branch:            Errors:  89

# THE SHORTFALL IS THE MECHANISM UNDER TEST, NOT AN OVERSIGHT. Both scenarios cut MANPAD's projectile
# RangeLimit from 24c0 to 4c0 while leaving the weapon's Range at 23c0, so every missile expires ~16
# cells short of an aircraft 20.2 cells away and no damage is ever dealt. The lint is right that this
# is a strange weapon; it is strange on purpose.
#
# WHY IT HAS TO BE THIS WAY. The overkill mark and the damage are the same number by construction --
# EstimatePercentDamage sums the weapon's damage warheads and the weapon then deals them -- so a mark
# large enough to suppress is a shot large enough to kill, and the target dies before a second AA
# could ever have joined. Measuring whether a battery volleys or serialises is impossible while the
# two stay coupled. Cutting the flight distance decouples them without touching the warheads, so the
# claim being measured is the REAL shipped arithmetic: min(3000 * 100 / 600, 100) = 100, exactly
# OverkillThreshold. It is also the honest live case, since MANPAD carries Inaccuracy 256 against
# moving aircraft and nothing releases the mark when a shot resolves into nothing.
#
# DO NOT "FIX" THIS BY RESTORING RangeLimit. It would not make the scenarios wrong-looking, it would
# make them silently measure nothing -- helicopters would die to the first missile and the spread
# measurement would have one shooter in it. That is precisely how afa18718 disarmed
# test-aa-overkill-cadence for eight days: it closed the ValidTargets over-count that the scenario's
# old payload split depended on, nobody re-ran it, and a pure diagnostic went on reporting confident
# answers about a mechanism that was switched off. The RangeLimit approach was chosen to replace that
# split BECAUSE it depends on no divergence between the estimate and the damage model, so a future
# fix to either cannot disarm it the same way. Full reasoning is in each scenario's weapons.yaml.
