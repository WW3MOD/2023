What changed, and why the panel got shorter

  • gone The word DEFCON. Nowhere in the lobby. The blue band says NO RUSH and the marker says THE LINE LIFTS — the mechanic keeps its name in-game only.
  • gone Four dropdowns replaced by two markers. Start At, Escalation Pace, Doomsday Clock and the escalation interval were four numbers a host had to combine mentally. The timeline shows the match they add up to.
  • new SIDES states the two-team constraint where it is chosen, rather than refusing at launch.
  • new PURCHASING reads "Disabled in Escalation" — dimmed rather than hidden, so the answer to "can I buy nukes here" is on screen.

Order, and why this one

  • The engine renders sections in a fixed order defined in C#, so this ordering is a real change to SectionOrder, not a yaml tweak. MATCH → ARSENAL → ECONOMY → BATTLEFIELD → DEVELOPER.
  • It runs from what game is this down to what am I debugging: the mode and its shape first, then what weapons exist, then the numbers, then the map, then developer switches. A host changing one thing scans top-down and stops early.
  • Two sections stay suppressed exactly as today — Unit Availability (24 placeholder options) and Combat Tuning (7). Nothing here un-hides them.

Honest about the placeholders

  • Two shipped options are still not wired — Powers Enabled and Friendly Fire — and are drawn as the engine draws them: #969696 text with a (not wired) suffix.
  • They are also still clickable, and clicking one de-readies every player. Harmless today only because their sections are suppressed — and this design un-suppresses one. That one-line fix is queued and must land in the same change.

The same panel, one dropdown different

  • Switching GAME MODE to Skirmish changes the bands, not the layout. The gold marker now means "first tier purchasable" instead of "first warheads issued".
  • DEAD HAND at 60 minutes adds a third marker and a red tail band. That is the whole of the time-limit feature, visible rather than inferred from a dropdown reading "60 minutes".
  • ARSENAL swaps to the purchase controls: availability, the cap, and the unlock interval. The ESCALATION cell dims to "None in Skirmish" for the same reason PURCHASING dims in tab 1 — a question answered rather than a control hidden.

Why the cap stops at 100 kt

  • Game-enders are never purchasable in Skirmish, so they are not in the HIGHEST YIELD list at all. A nuclear ending in Skirmish comes from Dead Hand, which is a host's deliberate lobby choice.

Sandbox: All Support Powers

This is what the lobby draws today

  • Reconstructed from the code, then checked against a live capture. 17 visible options across 6 sections, 584 px of content in a 731 px viewport at 1080p — so it very nearly fits, and scrolls at every smaller resolution.
  • ESCALATION renders as four dead dropdowns under a header that says NOT YET WIRED. That is deliberate: the section is exempt from the suppress-when-all-placeholder rule, because hiding it would answer "what mode am I playing?" with silence.
  • Six option ids are hidden outright — shortgame, crates, creeps, buildradius, allybuild, techlevel — and two more, Airstrikes and its cooldown, are switched off in yaml.

The trap worth knowing

  • There is a lobby-options.yaml in the engine tree defining a 3-column grid at 30/60 px rows. It is never loaded. Anyone grepping for the row templates lands there first and measures a panel the mod does not draw. The live one is lobby-players.yaml:860-1067.

The timeline is buildable, and the limit is narrower than it looked

  • Confirmed: there is no integer option type. A repo-wide grep returns exactly one LobbyOption subclass. The only value domain the engine has is Dictionary<string,string>, and an option cannot supply its own widget — LobbyOptionsLogic dispatches on C# type and locates children by type, so swapping a dropdown for a custom widget in yaml alone throws.
  • But the wire protocol does not care what UI produced a value. Setting an option is the text order option <id> <value>, and the server validates only that the value is a key in that option's dictionary. Preset loading and the test-mode stager already drive options with no dropdown anywhere in the path.
  • So: a custom timeline writing enumerated string values needs zero server or protocol change. Markers snap to the same values the dropdowns offered — "10", "20", "30" — and the match stays configurable without the widget. The timeline is a presentation upgrade, not a prerequisite, which is what makes it safe to commit to.

What has to be written

  • A TimelineWidget in the engine tree — the mod ships no assembly of its own, and three WW3MOD-specific widgets already live there, so this is the established pattern. SliderWidget cannot be reused: its Draw re-reads the authority value every frame, so a synced port snaps back mid-drag, and its ticks are draw-only with an in-source TODO saying snapping was never reimplemented.
  • A ChromeLogic to bind it, and chrome yaml — which means forking the stock lobby-players.yaml into the mod, since the panel currently uses the engine's copy unmodified.
  • The real design problem is drag versus network, not drawing. Every accepted order resets all clients to not ready and posts a chat line, so the order fires on mouse-up only — never per drag-move.

Two things that will bite a naive reproduction

  • Dropdown value text is centre-aligned, not left — it inherits TextAlign.Center and neither row template overrides it.
  • Checkbox internals are engine-fixed: the box is a square of the row height and the label sits at x + height × 1.5. Not adjustable from yaml. Both are reproduced above.
