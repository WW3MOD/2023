Why WW3MOD now pins its .NET SDK

Merged as c1f7e697 on 2026-08-17 · the change is one new file, global.json, six lines · written so you can find the hole in it

The short version: the automated check that says “this project compiles cleanly” was being run by a different compiler on GitHub than on your machine, and nobody had noticed because that check couldn't report failure anyway. Both halves are now fixed. Pinning the SDK is the second half, and it has a real cost that is worth understanding before you accept it.

1. What actually broke, in order

Three separate things went wrong, stacked on top of each other. They're easier to follow in the order they were found rather than the order they happened.

The check could not fail

The Windows CI job called Check Code had been showing a green tick while its log contained 106 Error(s) and the words Build failed. — twice.

The mechanism is a detail worth knowing, because the obvious guess is wrong. The script does not “return 0”. It never sets an exit code at all: it prints Build failed., carries on, and runs two OpenRA.Utility.exe checks afterwards. Those are the last commands the script executes, they succeed, and in PowerShell the last command's status is the script's status. The failure was silently overwritten by a later success.

How we know, rather than assume

On CI run 31992009079, on the same commit, Windows Check Code passed while Linux Check Code failed on the identical 106 errors. Same code, same errors, two different verdicts. That is not an inference from reading the script — it is the two lanes disagreeing in public.

Fixed in f149dce3. Two write-ups this week had already cited that green tick as evidence the project compiled cleanly.

The 106 errors themselves

Cleared in a7142780. 84 of them were a single mechanical rule about <para> tags in documentation comments; 19 were a mix; only 3 were real defects. One of those three was a genuine bug rather than a typo: a constant had been declared between a documentation comment and the method it described, so the documentation had silently re-attached itself to the constant.

And then: which compiler is actually running?

This is the part the pin addresses, and it only became visible once the gate was honest. The CI config asks for SDK 6.0.x and genuinely installs 6.0.428 — you can watch it do so in the log. But setup-dotnet adds that SDK alongside the ones the GitHub machine image already ships, and the .NET launcher then picks the highest version installed.

The two sentences that look identical and are not

“CI installs 6.0.428” and “CI builds with 6.0.428” were different claims, and only the first was true.

The proof is again from the log rather than from reasoning: that same run reports errors CA1862 and IDE0251 — neither of which exists in the 6.0.428 analyzer pack. They could only have come from a newer compiler.

2. Why global.json is the only lever that reaches it

The project's code-quality rules come from four sources. Two were already pinned; two were not, and there is no other way to pin them.

Rule familyComes fromPinned before tonight?
SA**** (StyleCop)A NuGet package listed in Directory.Build.propsYes — by version
RCS**** (Roslynator)A NuGet package listed in Directory.Build.propsYes — by version
CA****Bundled inside the SDKNo — whatever the machine has
IDE****Bundled inside the SDK. Has no standalone package at all.No — and cannot be

Because IDE**** ships only inside the SDK, the SDK version is the only thing that controls it. That is what global.json sets:

{
  "sdk": {
    "version": "6.0.428",
    "rollForward": "latestFeature"
  }
}

rollForward: latestFeature is the deliberately loose part: it accepts any 6.0.4xx SDK, so a developer on 6.0.436 is fine. It refuses to silently climb to .NET 8 or 10, which is the behaviour that caused the problem.

3. What this costs — the honest list

Cost 1: it switches off analyzer coverage that was live yesterday

This is the strongest argument against the change and it deserves to be stated plainly rather than buried. Of the 106 errors cleared tonight, 6 were found only because the runner was using a newer compiler than we were — 5 × CA1862 and 1 × IDE0251. After this pin, those rules run nowhere. And because .NET 6 is end-of-life, that rule set is now frozen until somebody deliberately edits the file.

The justification offered was “a rule you cannot reproduce locally cannot be acted on” — which is contestable, and I want to flag that it is contestable rather than sell it, because a previous worker did act on CA1862 by temporarily hand-pinning a newer analyzer package to see what it said.

Cost 2: it can hard-fail a machine that only has a newer SDK

Anyone whose only installed SDK is newer than 6.0 — or a 6.0 below the 4xx band — used to build fine by rolling forward. They will now stop with:

A compatible .NET SDK was not found.

This is the one that could affect you directly, since you test from a second computer. Check it with:

dotnet --list-sdks

If nothing in the 6.0.4xx range appears, that machine needs .NET SDK 6.0.428 installed, or the pin removed. Either is a one-minute fix, and the failure is loud and names global.json explicitly rather than being mysterious.

Cost 3: a landmine left in on purpose

If someone later bumps global.json to a newer SDK without also bumping ci.yml's dotnet-version: '6.0.x', all five CI lanes fail instantly with “SDK not found”. Wiring ci.yml to read global.json directly would make them one source of truth. That was deliberately not done, because the worker could not test a CI edit — this is alternative C below and it remains available as a two-line change.

Cost 4: ~90% confidence, not certainty

Nobody can run the GitHub machine locally. The failure mode that would show up on first push is if setup-dotnet installs 6.0.428 somewhere the launcher doesn't look — which would turn every lane red at once. The reason that's thought unlikely: the image's newer SDKs and the installed 6.0.428 must already share one directory root, because that co-location is precisely what produced the “highest wins” behaviour we measured. That is inference, not observation.

It is cheap to detect — the very next CI run — and reverts by deleting one file.

4. The alternatives, and why each was not taken

A. Pin, as merged chosen

Local and CI compile with the same analyzer set. A GitHub image update can no longer turn main red on its own. Costs 1–4 above.

B. Don't pin at all

Keeps whatever newer coverage the runner brings — which genuinely did catch 6 real findings today. The price is that main's CI can go red with no commit behind it, and whoever hits that will be debugging GitHub rather than the project. It also means a developer can never reproduce a CI failure locally, which is the specific frustration that makes people start ignoring red builds.

Why rejected: the whole point of tonight's work was to make the gate trustworthy. A gate that fails for reasons outside the repository is a gate people learn to ignore — which is how it got into the state it was in.

C. Pin, and also wire ci.yml to read global.json

Strictly better in principle: one source of truth, and cost 3 disappears entirely. Rejected only because the worker could not test a CI edit from this machine, and an untested CI change can break all five lanes. This is the alternative most worth revisiting — it is about two lines, and the next time CI is being touched for another reason it should be folded in.

D. Pin, and add the newer analyzers back as an explicit package

This looks like the obvious best of both: freeze the compiler for determinism, but pull the newer CA**** rules in deliberately as a versioned dependency so coverage is not lost. It was rejected for a concrete measured reason, not for tidiness.

Adding NetAnalyzers 8.0.0 immediately reintroduces a rule called CA2021 against UnloadCargo.cs, and that rule is wrong there. It claims a type conversion can never match anything and is therefore dead code. A probe against the real types shows it produces 2 results over a 2-element input; the rule simply does not model the conversion the code uses.

The “obvious fix” would have introduced a real bug. That conversion is load-bearing: it is what makes a lookup return “nothing” instead of a misleading default value, and the game branches on that to report a transport as blocked. Deleting it would mean a fully blocked transport silently stops reporting that it is blocked.

So the only ways to adopt the newer analyzers today are to suppress a rule (which the brief forbade) or to break working code. The coverage question is therefore deferred, not solved — it becomes tractable whenever the project moves off .NET 6.

5. One limitation, so it isn't discovered later

The pin reaches the YAML lint gate only halfway. make test depends on a build, so the pin does govern the compiler that builds the lint tool. But the lint runs as dotnet bin/OpenRA.Utility.dll — the launcher starting an already-built application — and that path does not read global.json at all.

In short: the pin makes the compiler deterministic, not the runtime. In practice this is fine, because the lint's behaviour depends on the code it was compiled from, not on which runtime executes it. But if lint output ever differs between machines, this is the first place to look, and the pin will not have prevented it.

6. What to actually do with this

  1. Run dotnet --list-sdks on your other test machine. If no 6.0.4xx appears, install SDK 6.0.428 there before your next pull.
  2. Watch the first CI run after this push. If every lane goes red at once with “SDK not found”, the pin is the cause — delete global.json and everything returns to how it was.
  3. Consider alternative C next time CI is being edited anyway.
  4. If you disagree with cost 1 — losing the newer analyzer coverage — that is the most reasonable thing here to disagree with, and reverting is one file.
