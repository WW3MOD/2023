Rally is keyed per manejectRallyPoints is keyed by passenger ActorID (Cargo.cs:190) and consumed per-man in UnloadCargo.cs:131–132. A class has no ActorID to key on, so "send Riflemen there" has no representation in the current data model. See the box below.
The panel is 228×240garrison-panel.yaml:3–6, rows at a 14 px pitch. So: 36 men = 504 px, more than double the panel. 16 classes = 224 px, which fits with 16 px to spare. A realistic 9-class load is 126 px. This is arithmetic, not taste — and it is the strongest argument for the user's idea.
Placement was cut from every option, on purpose. One thing here is expensive and it is not the grouping — it is the drop point. Because ejectRallyPoints is keyed per passenger, a per-class drop point has only two routes: (a) a rally per man applied across the group — n orders with group membership resolved client-side, the exact shape that caused an earlier desync in this project; or (b) a new class-keyed dictionary on the trait, which is new simulation state, therefore a new order and a sync review. Neither is worth it for a feature no player has ever been able to reach, because the panel carrying it has never been on screen. So A, B and C below drop men to the default eject cell and say nothing about placement. Only Option D touches it, and only in the one shape that is already free — clearly marked.
The finding that cuts against class grouping. E1R1, E3R1 and E2R1 are veteran variants that Inherits: ^E1 / E3 / ^E2 and never override Selectable.Class (infantry.yaml:1181–1189, 1301–1309). So a 2-star Rifleman and a green Rifleman collapse into the same row and the same count. Class grouping silently removes the player's ability to choose which Rifleman gets out — and it hides wounded men and men out of ammo too. That loss is real; whether it matters is the actual decision here. Options A, B and D below all offer the same escape hatch: expand a class row to see the individuals, and only when you want to.

Option A — Class-grouped list the user's own idea; recommended

One row per class with a live count. Click the row to drop one man. Click again to drop another. The count decrements in place; at zero the row greys out but keeps its slot for ~2 s so the list never jumps under a repeat-clicking finger, then collapses. ALL drops the whole class in one go.

Where they walk: the default eject cell, same as the deploy hotkey today. No placement, by the decision above. Cost: nothing. One GroupBy in the panel logic and one existing order per click. — Fits by arithmetic: the 9-class Chinook load is 126 px of rows in a 240 px panel; the 15-class worst case is 210 px and still fits. The same 36 men as individual rows would be 504 px.

Option B — Context menu at the cursor "context menu ish, but not radial"

Right-click the transport (or CTRL+click) and the same class-grouped list appears at the cursor instead of in a fixed panel. It is sticky — it stays open as you click, so click · click · click drops three men. ESC or right-click closes it.

Option C — Radial breaks at the Chinook

Included so you can see the failure rather than take my word for it. Same class grouping, wedges instead of rows, count badge per wedge. Watch what the wedge angle does as the class count climbs.

A wedge stops being comfortably clickable below roughly 40° of arc — that is 9 classes at this radius, and the labels stop fitting well before that. Class grouping does not rescue the radial, because the thing it has to survive is not 36 passengers, it is 16 possible classes. A Chinook carrying one of everything is legal.

Option D — Deploy stamp the only one that keeps placement, and only the free half

A compact class strip docked above the command bar. Click a class to arm it — the cursor becomes that class with its remaining count. Then every left-click on the map drops one man of that class and sends him to that cell. Click four spots, four riflemen walk to four spots. Right-click disarms.

Why the single click is free. One click picks one passenger and keys the rally to his own ActorID — which is exactly what ejectRallyPoints already stores. There is no class key anywhere, so no new state and no new order: it is SetEjectRally then UnloadCargoPassenger, both existing, both already replicating since 409b0fd2. This is the one place per-man placement survives class grouping intact, because the grouping is only in the strip, never in the order.
The expensive variant, shown so you can reject it knowingly. SHIFT+click to send a whole class to one cell is route (a) from the box at the top: n orders with group membership resolved client-side. That is the shape that has burned this project before. It is demonstrated below and should not ship in a first cut. The cheap substitute is a SHIFT+click on the strip tile itself, which dumps the class to default cells and touches no rally state at all.

This is the only option where "which man" and "where he walks" are the same gesture. It scales identically at 3 passengers and 36 because the strip is class-grouped and horizontal: 16 classes is a 672 px strip, which fits above a command bar. But note what it costs you: D only earns its keep if placement is in scope at all. If placement stays cut — the recommended default — then D collapses into Option A rotated 90°, and A is the simpler thing to build.

Where it fails Hides veterans, wounded men and empty magazines behind a single count. A fixed panel means your eyes leave the drop zone at the moment you most want them on it. Occludes exactly the ground you are about to drop onto. Edge-flipping makes muscle memory impossible. Right-click is already the move/attack verb and this would overload it. Dies at the only transport that motivated the feature. Beautiful for the Bradley, worthless for the Chinook — and the Chinook is the reason we are here. Modal — a stray click spends a soldier irreversibly. Poor discoverability. And it only justifies itself if placement is in scope; if it is not, this is Option A with extra steps.
Recommendation: Option A, now — and it is the user's own design. Collapse by Selectable.Class, one row per class with a count, click to drop one, click again to drop another. The instinct was right, and the arithmetic is what proves it: 36 men as rows is 504 px into a 240 px panel and cannot be done under any styling, while 16 classes is 224 px and fits. Class grouping is not a nicety here, it is the only thing that makes the panel possible. It costs one GroupBy and reuses an order that already exists, already carries an ActorID, and already fails safe on a stale pick.
And explicitly: do not ship placement in the first cut. The per-man drop point is the only expensive thing in an otherwise very cheap change, and it is a feature no player has ever reached. Cut it, ship the grouping, and see whether anyone asks for it. Option D is what you build if they do — it is the one design where placement stays keyed to a single man's ActorID and therefore stays free. Until then D is A rotated, and A is simpler.
Two things this mockup does not prove. The class icons here are letter badges standing in for the real *_class sprites, so icon legibility at 20 px is untested — that is the thing most likely to sink D, since the strip leans on icon recognition harder than a list with text labels does. And the panel geometry below follows the garrison-panel.yaml idiom (WINDOW_WIDTH - 240, WINDOW_HEIGHT - 260) rather than WINDOW_RIGHT, which the engine does not define — an undefined symbol evaluates to 0 and parks the panel off-screen. That is the bug that cost three redesigns of a panel nobody had ever seen.
