## The desync — read this before touching it

**Both players' sync reports are committed** at `WORKSPACE/audit/logs-260816-snapshot/Logs/` (host `-1`, friend `-7`). Divergence is **net frame 1264 / world tick 3792**, actor `4617 e3.russia`.

**Ruled out with evidence — do not re-chase:**
- **Content divergence** — identical `cfd39710` digest on both machines.
- **RNG** — identical `SharedRandom` value *and* draw count at 1264.
- **Bots** — all 205 bot-module entries `IsTraitDisabled: True`.
- **Ambush-halt** — needs a condition only a disabled bot module grants. **Therefore this is a DIFFERENT bug from the known restore desync.**
- **.NET runtime mismatch** (host CLR 8, friend CLR 10) — ruled out; `string.GetHashCode()` is randomised per process, so order-dependent simulation would desync constantly on one runtime.

**Current best theory, honestly weak:** unsynced `Mobile.CurrentSpeed` / `MovePart.progress`. The floats were removed at `afac22a8` — but that turned out to be a **no-op** (zero disagreement across ~11.8M inputs), so **the evidence got weaker, not stronger.** Do not describe it as fixed.

**The one run that would settle it:** replay one desyncing match on a single machine under both .NET runtimes with `Test.ForceSyncReports=true`, and diff the `syncdiag-*` files. Identical output kills the runtime hypothesis outright.

**Correction owed:** `WORKSPACE/audit/260816-desync-rootcause.md` §5 claims a one-third rounding bug in the acceleration maths. **It does not exist** — `18f/54f × 3f` = 1.0000000298, under half a ULP in [1,2), rounds back to exactly 1.0f.
