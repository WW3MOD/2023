The deeper finding: the unit is the problem, not the threshold

The engine also states this test, at DangerFieldLayer.cs:416-417: “if min and max straddle the median by more than ~2 orders, the median is a weak reference and the unit wants revisiting — not the individual thresholds.”

  • Measured spread: min 164, median 3,412, max 1,271,250 — the max is 2.57 orders (372×) above the median.
  • Only 92 of 424 actor types contribute to the reference at all.

So the ruleset is not a population with a meaningful middle. Retuning thirteen numbers on top of a weak reference reproduces the exact failure that has already cost three rounds: a calibration input that is wrong underneath the thing being calibrated.

Why the original derivation failed — worth internalising

The reasoning at SupplyFollowerBotModule.cs:103-105 derived “50 units” from kernel taper geometry: a contact whose envelope merely reaches a cell contributes ~1/(r+1) of its core, and a decayed contact contributes 15% of that. That arithmetic is correct and the conclusion is still wrong, because taper geometry describes the shape of one contact's envelope and says nothing about how many envelopes overlap a cell in a real match. The live medians are what overlapping produces. This is a general trap: a threshold derived from single-source geometry is not a prediction about a field fed by many sources.

2 · Fixed already — no decision needed

doneThese were unambiguous, so they are committed rather than proposed.
  • Autotests were pacing at 1×. run-batch.sh forwarded every other flag to run-test.sh but not --speed, so a 77-test run had no way to be anything but wall-clock. Batches now default to 8×. The simulation is byte-identical — Test.SpeedMultiplier only divides world.Timestep and never enters a synced path — and --timeout is unscaled, so a faster batch gets more watchdog headroom. (8a193c41)
  • The harness could silently corrupt itself when run twice. Every verdict goes to one shared result.json, so a second concurrent run satisfies the first run's watchdog poll — the first stops watching and its game is orphaned with nothing left to kill it. That is what you saw on screen. run-test.sh now takes an atomic single-instance lock and refuses, naming the holder; a dead holder's lock is reclaimed rather than wedging the harness.
  • The benchmark spec pointed at a stale worktree. SPEC.md §5.1 said all loop work happens in a long-lived ai-bench worktree. That worktree had drifted 638 commits behind main, while run-tournament.sh measures whichever checkout invokes it — so following the spec would have produced valid-looking numbers for three-week-old code. Corrected; worktree removed; branch deleted.
  • Git tidied. Two fully-merged experiment branches deleted; 18 design records (14 decisions, a spec, a plan) that had been sitting untracked since July are now committed. (3b535f46)

3 · Decisions for you

decision A

What replaces the danger unit?

This is the load-bearing one; B and the threshold table both fall out of it.

A1 — Re-derive the thirteen thresholds from measured percentiles, keeping the median-based unit. Cheapest, and it will visibly improve behaviour. But it re-tunes on top of a reference the engine's own criterion calls weak, and it needs re-doing if decision F moves.
A2 — Change the reference from the median to a percentile of the live field (e.g. thresholds expressed as “the 60th percentile of cells that currently carry any danger”). Self-calibrating and immune to a lopsided ruleset. Costs a design pass and changes what a threshold means.
A3 — Drop the abstraction and set thresholds directly in field units from measured distributions. Most honest, least portable across rulesets — every future weapon change silently moves every threshold.

My read: A2 is right and A1 is the trap, because A1 is what we already did once and it is why we are here. The thirteen-threshold audit above hardens that — when every threshold is below the median, the common factor is the scale, not the individual choices. But this decides how the bot reads the battlefield, so it is yours.

decision B

What should make a supply truck run away?

Arithmetic can clear the 2,795 floor. It cannot answer the actual question: what fraction of the battlefield should a supply truck refuse to enter? A truck that flees the median cell never delivers. A truck that only flees the peak dies. That is a doctrine call about how expendable logistics are, and it wants your answer before any number is written.

decision C

The benchmark has no control any more

Commit b8d2e601 (2026-08-02) promoted @stable to full @experimental parity and renamed it Stable AI 0730 → 0802. Every number in WORKSPACE/benchmarks/ was measured against Stable AI 0730, a bot that no longer exists. Experimental-vs-Stable is now close to a mirror match, so “re-take the baseline” is the wrong frame — the yardstick changed, not just the thing being measured.

C1 — Pin an explicit frozen control. Snapshot a named historical bot as the permanent benchmark opponent so the yardstick stops moving when a promotion happens.
C2 — Run it as a mirror anyway, and read it as a side-fairness / noise calibration rather than an improvement measure. Cheap, honest, measures much less.
C3 — Defer the benchmark entirely until decision A lands, since A moves the danger field for both profiles and would invalidate the run.

Cost either way, measured not guessed: ~120 s/match at 8×, so a 10-match rung is ~20 min and three maps ~60 min. My read is C3 then C1 — running an hour of matches now measures a field we are about to change.

decision D

The RA-scaled durability weight — and the ordering trap

Filed as [med] in WORKSPACE/bugs/discovered.md: the merged branch fixed the throughput term of a weapon's intensity but not the durability weight term, which may still be Red-Alert-scaled. If true, every per-type intensity shifts — and therefore the reference itself shifts, and with it all thirteen thresholds.

This is the sequencing constraint that matters: if thresholds are re-derived (decision A) before this is settled, they get derived twice from two different unverified inputs. That is precisely the loop that cost this work three review rounds already. It was correct to keep this shut until the reference was measured; the reference is now measured, so it is open — and it should be answered before A is executed, not after.

decision E

exp-terr-bias — rebase or abandon

Left untouched pending your call. Note that its numbers were taken against the old control, so decision C applies to it too.

4 · Suggested order

  1. D — settle the durability weight, because it moves the reference everything else is derived from.
  2. A — pick the unit model, then re-derive all thirteen thresholds once, against a reference that is no longer suspect.
  3. B — set the truck doctrine, and only then write the evac number.
  4. Re-run the danger instrumentation and confirm the thresholds now sit between median and peak, which is the engine's own stated shape for a healthy threshold.
  5. C — take the benchmark after the field has stopped moving, against whatever control you pin.

The one thing I would not do is start at step 3. Setting the truck threshold first is what makes it look fixed while leaving the reference wrong underneath — which is the shape of all three previous claims.
