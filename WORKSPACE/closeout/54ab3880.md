**That hypothesis is now outranked.** The second machine's saved-game work — `522a6014` and `9b77d1fd`, landed after this session went quiet — named the restore desync's diverging field: `Detectable.visionDetectableConditionToken`, three traits, each off by exactly one, with SharedRandom verified identical on both sides. `Detectable` is applied via `mods/ww3mod/rules/defaults.yaml`, so it is on essentially every actor in a 2-human game. **The restore desync and this multiplayer desync are very plausibly the same defect.**

The mechanism, per `9b77d1fd`: a condition token is an opaque allocation handle whose value counts how many conditions the actor has ever been granted, and `DetectableVisionChanged` revokes and re-grants on every visibility change. Marking it `[Sync]` therefore syncs the *identity of the handle* rather than the gameplay state it stands for — so any difference in grant/revoke count between two clients desyncs the game while the actual gameplay state is identical.

**Next concrete step — the fix is already modelled in the same file.** Verified still unfixed at `engine/OpenRA.Mods.Common/Traits/Modifiers/Detectable.cs:149-150`:

```csharp
[Sync]
int visionDetectableConditionToken = Actor.InvalidConditionToken;
```

Ten lines below, `:160-162` does it the right way round — the *state* is synced and the handle is not:

```csharp
[Sync]
public bool IsRadarDetectable { get; private set; }
int radarDetectableConditionToken = Actor.InvalidConditionToken;
```

Vision has the inverse shape. So: add a synced `IsVisionDetectable` bool, drop `[Sync]` from `visionDetectableConditionToken`, and match the sibling. This directly answers `9b77d1fd`'s stated objection — that dropping `[Sync]` would hide a real missed visibility transition rather than fix it — because the transition stays observable through the synced bool. Sync the state, not the handle.

Note `:191-193` (`IsCounterBatteryRadarDetectable`) already follows the correct pattern too, so vision is the lone outlier of the three.

## 4. Transcript-only knowledge

All already persisted to the manager log; repeated here so this file stands alone.

**The frame number in a desync report is not a clue about when divergence happened.** Sync hashes go out from `NetFrameNumber = 1` (`OrderManager.cs:110,271`), but `ReceiveSync` can only compare a frame once *both* clients' packets for it have arrived (`OrderManager.cs:160-169`). The reported frame is gated by round-trip latency — frame 6 is roughly the earliest a desync can *surface*. This session initially narrowed its search window on the frame number, which was wrong; all four desyncs are consistent with divergence at world load.

**Host decides whether sync reports are armed.** `EnableSyncReports` is read from the *host's* lobby globals by every client (`Server.cs:339` → `OrderManager.cs:114`), not from each client's own settings. If someone hosts from a build without `b1178706`, neither machine records anything and both get "No sync report available" — the exact symptom under investigation, looking like nothing changed. Also: `Settings.Save()` only strips nodes matching the *compiled* default, so an explicit `EnableSyncReports: False` in either machine's `settings.yaml` overrides the new default permanently and silently.

**The live sync checks, and the trap in using them.** `Debug.SyncCheckUnsyncedCode` / `SyncCheckBotModuleCode` throw the instant unsynced code mutates sync state, naming the culprit directly rather than post-hoc. No code needed — Settings → Advanced (`AdvancedSettingsLogic.cs:55-56`), or `launch-game.cmd Debug.SyncCheckUnsyncedCode=true Debug.SyncCheckBotModuleCode=true` (`Settings.cs:403-407` applies any `Section.Field=value` arg). **They are not session-only**: `Settings.Save()` persists any field differing from its compiled default and runs on ordinary paths including every server join, so the flag sticks until explicitly set back to `false`. Deliberately left off by default — throwing on something benign would make the game unplayable.

**Replays of the first two desynced games survive** and hold both clients' order streams: `Replays/ww3mod/release-20230225/ww3mod-2026-08-11T170129Z.orarep` (108 KB) and `...T170300Z.orarep` (76 KB). The server-side recorder was invalidated on OOS (`Server.cs:791-798`) but the client-side files were not. Worth preserving before they age out. Note `generateSyncReport` is explicitly false for a `ReplayConnection`, so replaying them cannot produce a sync report — their value is the order streams.

**Design decision worth not re-litigating.** The build fingerprint shipped in `b1178706` WARNS on mismatch and never rejects a join. The implementer was briefed to hard-reject, built it, then deliberately reversed it; an independent reviewer agreed and strengthened the case. Reasons: the user builds from a dirty tree while the friend builds clean from the same commit, which is a legitimate difference; and a reject would have made the game unjoinable over a gitignored geoip file. A guard that blocks play is worse than the bug it diagnoses.

**Known gaps in that instrumentation.** The asset digest covers *filenames*, not bytes — two Red Alert installs agreeing on names but differing in frame counts inside a `.shp` read as identical at the handshake, and that was precisely the suspected mechanism at the time. `SequenceIntegrity` measures it but structurally cannot ride in the handshake, because sprites are not resolved until after the lobby; hence the world-load `Degraded sequences:` log line, which is the earliest point the mechanism is visible at all. Also, narrowing the dirty-tree pathspec to `-- engine` means an uncommitted change to a repo-tracked binary asset under `mods/` is invisible to the fingerprint — an accepted trade, since the build-loop cost was daily and certain while this gap is narrow.

**The per-frame cost of sync reporting was never measured** — it needs a running game, which project rules forbid a worker to launch. It is instrumented as `PerfSample("sync_report")`; read it in `perf.log` after any real game. If it costs more than roughly a millisecond per net frame in a large fight, the honest lever is `NumSyncReports` (raised 7 → 32 in this work), not the feature.

**Two incidental defects found and not chased.** `SpawnStartingUnits.cs:145,148` use `CPos.Zero` as a "no cell found" sentinel, but (0,0) is a legal cell — deterministic, so harmless for sync, but wrong on any map whose search annulus reaches the origin. And the file headers at `BeliefStore.cs:29`, `ControlField.cs:31`, `DangerFieldLayer.cs:35` claim "SharedRandom only staggers the first tick", which the code contradicts — those staggers touch no RNG at all.
