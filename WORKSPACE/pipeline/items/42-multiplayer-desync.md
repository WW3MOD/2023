_**Mechanism** (per `9b77d1fd`): a condition token is an opaque allocation handle whose value counts how many conditions the actor has ever been granted, and `DetectableVisionChanged` revokes and re-grants on every visibility change. `[Sync]` on it therefore syncs the *identity of the handle*, not the gameplay state it stands for — any difference in grant/revoke count desyncs the game while the actual gameplay state is identical._
_**STATUS SUPERSEDES THE PRESCRIPTION THIS ITEM WAS FILED WITH.** The source report, `9b77d1fd`, and the implementer brief all specced the same fix: add a synced `IsVisionDetectable` **bool** mirroring `[Sync] public bool IsRadarDetectable` at `:160-162`. **That was rejected on evidence during implementation — do not "restore" it.** The two radar siblings each grant a single fixed condition and are honestly boolean; vision grants `VisionDetectableConditionPrefix + CurrentVisibility` (`visibility-1`..`visibility-10`, consumed in `infantry.yaml`) and `DetectableVisionChanged` unconditionally revokes-then-re-grants, so it never lands in a not-granted state. A bool would be `false` before the first tick and `true` forever after, and would hash **clean** with client A at `visibility-3` against client B at `visibility-7` — reproducing exactly the blindness `9b77d1fd` objected to. The siblings are the pattern to copy **in principle** (sync the state, not the handle), not literally. Full reasoning: `.maestro/managers/ww3mod/decisions/01-detectable-vision-syncs-the-visibility-level-not.md`._
