Weapon sections — one template, four shapes

Every number is computed from shipped YAML at main @ b3a7564d and carries a file:line. Conversions: 1 cell = 1024 WDist; 1 tick = 60 ms (mod.yaml:382, DefaultSpeed: default → 16.67 ticks/s — not the 25 tps that several in-tree comments still assert). Refill figures are the batch maths from AmmoPoolInfo; depot reference is 1 Logistics Centre = 2250 supply (structures.yaml:466).

The weapon section is a CONTAINER, not a ninth element. Everything inside it is an existing element — the header reuses Subhead, the stats are StatRows, the refill is a CostRow, caveats are Notes. A ninth flat element would have had to re-implement all four. What actually changes is that the emit list gains one level of nesting. Cheapest encoding: keep the flat IEnumerable<TooltipElement> and give each element an optional Group string; the renderer wraps consecutive rows sharing a group in one indented container. No tree type, no new element kind.

Rows drawn in blue, inside a dashed box are candidates — rendered so you can choose by looking. They are not part of what I would ship. My ranking and pick are in the table at the bottom.

The one-shot reads as one shot. Ammo: 1 with ReloadCount: 1, so "1 rd · 50 supply" is the whole story and the one shot tag is derived from Ammo == 1, not authored. The rocket is 91% of the rifleman's refill bill — the fact today's tooltip prints twice, in two bases, and still never totals.

Penetration alone is misleading, and it caught me. His disposable rocket is Penetration: 500; the AT specialist's guided ATGM is Penetration: 100 — which looks like the specialist is five times worse against an Abrams' Thickness: 700. It is not. Penetration is compared against Thickness × ArmorDirectionPercent, and the ATGM is TopAttack: true (weapons-missiles.yaml:6), which selects Distribution[3] (DamageWarhead.cs:150-152) — 10% on the Abrams, so effective thickness is 70 and the ATGM clears it for full damage.

So the tooltip must show attack direction, or the penetration row is a trap. Two numbers, 500 and 100, rank the wrong way round without it. That is why Top attack is now in the shipped set rather than a candidate — it is not extra detail, it is what makes the row above it readable.

Why that one row matters measured, not asserted

Side by side, Penetration 100 (specialist) against Penetration 500 (the rifleman's throwaway rocket) reads as though the dedicated anti-tank soldier is five times worse at his job. I drew exactly that conclusion and filed it as a suspected balance bug. It was wrong.

Penetration is compared against Thickness × ArmorDirectionPercent (DamageWarhead.cs:240), and a TopAttack warhead takes Distribution[3] — the roof.

The design is coherent. The specialist's three-round load does 30 000 against an abrams' 28 000 HP — exactly one MBT per magazine, which reads deliberate. Penetration: 100 is sized against roof armour, not frontal. Retracted in bugs/discovered.md rather than deleted, because the reasoning is the point.

Supply figures use the 2026-08-30 re-pricing (rocket 30, ATGM 65 each). The rocket's 50 elsewhere on this page is the pre-repricing value that worker 4fb3b49b is currently changing.

Would ship Damage (what it does) · Penetration (whether it does it to armour) · Top attack when set (see below) · Range (where you can stand) · Blast (whether it catches more than one) · Refill (what sustaining it costs). Ranked by what a player actually decides with.
Top attack — promoted from nothing to shipped Penetration is compared against Thickness × ArmorDirectionPercent, not against Thickness. A TopAttack: true warhead selects Distribution[3] (DamageWarhead.cs:150-152) — 10% on an abrams, 15% on a t90 — so the ATGM's Penetration: 100 beats an effective 70 while the RPG's 500 loses to a frontal 700. Showing penetration without it ranks the two weapons backwards, which is exactly the false conclusion I drew and retracted. Cheap to derive: one bool already on WeaponInfo.
Would add if you want one more Min range — but only on the weapons that have one. It is decisive for artillery (HIMARS cannot fire inside 16 cells) and noise everywhere else.
Would drop Projectile speed (candidate D) — real, but nobody chooses a unit with it. Rate of fire (candidate A) I am lukewarm on: BurstWait, ReloadDelay and Burst compose in a way I did not fully verify, so a single "seconds per shot" risks being confidently wrong.
Deliberately NOT shown Effectiveness vs armour class. It reads as the most useful stat and it is the most dangerous: Kevlar is on all 28 infantry and in zero Versus tables, so a table lookup returns "no modifier" and would render as though armour had been consulted. Penetration vs Armor.Thickness is the mechanic that actually fires.
Penetration when unset Engine default is 1 (DamageWarhead.cs:24), which against Thickness: 700 delivers 0.14% of the written damage — a bug shape this project has already hit. 41 of 44 reachable weapons set it. The 3 that do not are targeter stubs with no real damage, so the row is omitted, never printed as 1.
