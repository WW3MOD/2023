# Coding Conventions — read before editing YAML or engine C#

## WDist notation

OpenRA uses `WDist` (World Distance) units throughout. Notation `NcXXX`:

- `1c0` = 1 cell = 1024 WDist units
- `1c512` = 1.5 cells (1024 + 512)
- `3c768` = 3.75 cells
- Plain `512` = 512 WDist units (half a cell)

## WAngle facing — counterclockwise (opposite of typical conventions!)

`WAngle` facings rotate **counterclockwise**, 0–1024 range. Easy to get wrong.

| WAngle | Direction | Screen (top-down) |
|--------|-----------|-------------------|
| 0      | North     | Up                |
| 256    | **West**  | **Left**          |
| 512    | South     | Down              |
| 768    | **East**  | **Right**         |

Map placement: units on the LEFT facing right → `Facing: 768` (East); on the RIGHT facing left → `Facing: 256` (West). Conversion: `WAngle.FromFacing(old)` where old RA facing × 4 = WAngle.

**Converting a bearing back to a cell step:** `WVec.FromSpeedAndAngle(speed, angle)` (`WVec.cs:94`) is the exact inverse of `WVec.Yaw` (`WVec.cs:66`). To turn a bearing `WAngle` (e.g. one built from a cell-space `WVec(dx,dy).Yaw`) back into a cell-space step, use `FromSpeedAndAngle` and take `Sign(X)/Sign(Y)` — it respects the "north = −Y" + counterclockwise convention automatically, avoiding hand-rolled `Cos()/Sin()` sign errors.

**A `RateOfTurn`-style field in YAML is a raw `WAngle`, not a facing — and this has now been mis-read three separate times.** `new WAngle(20)` is 20 raw units; consumers read `.Facing`, which is `Angle / 4` (`WAngle.cs:67`). So `HorizontalRateOfTurn: 20` (`Missile.cs:99`) means **5 facings/tick ≈ 7.03°/tick**, not 20 of anything a reader would guess. **Grep the consumer for `.Facing`, `>> 2` or `(sbyte)` before trusting any raw angle you see in YAML** — `WAngle`'s own `[0, 1023]` normalisation guarantees nothing about the range or units the *consumer* accepts. (Worked case in [`missiles.md`](missiles.md) §4: a field the engine re-decodes through `(sbyte)(Angle >> 2)` has a usable range of `[0, 511]`, and `Missile` decodes that one field three different ways.)

**`Mobile.Speed` in YAML is not the speed at the point of use.** `MovementSpeedForCell` appends the locomotor's per-terrain percentage to the modifier list before applying it (`Mobile.cs:826-831`), so a `lightwheeled` unit crossing `Clear` moves at **70%** of its declared figure (`world.yaml:98-101`) — a humvee's `Speed: 150` (`vehicles-america.yaml:70`) is 105 wdist/tick on open ground and only hits 150 on `Road`/`Bridge` at 100. Any timing or intercept arithmetic taken from the YAML number alone is ~30% optimistic over most of the map.

## YAML

### Templates (prefixed with ^)

```yaml
^Aircraft:          # Base template for fixed-wing planes
^Helicopter:        # Base template for helicopters
^Drone:             # Base template for drones
^Airborne:          # Common airborne traits
^NeutralAirborne:   # Airborne without faction-specific traits
^AirRadar:          # Radar trait for aircraft (range 24c0)
```

### Conditions system

Traits grant and consume named conditions:

```yaml
GrantConditionOnDamageState:
    Condition: heavy-damage-attained    # Granted at heavy damage
SpeedMultiplier@HeavyDamage:
    Modifier: 90
    RequiresCondition: heavy-damage-attained
```

Common conditions: `airborne`, `cruising`, `moving`, `empdisable`, `dronedisable`, `heavy-damage-attained`, `critical-damage`, `rank-veteran`, `suppression-*`, `unit.docked`

**A consumed-but-ungranted condition is a `make test` ERROR (not a warning).** `ConditionalTraitInfo.RequiresCondition` is `[ConsumedConditionReference]` (`ConditionalTrait.cs:21`), so a trait gated on `foo || bar` marks BOTH names *consumed on that actor*. `CheckConditions` (`Lint/CheckConditions.cs:73-75`) calls `emitError` — which fails `make test` — for any condition an actor consumes but nothing grants. (The reverse, granted-but-unconsumed, is only a `emitWarning`, `:70-71`.) To make a name grantable-but-not-yet-fired (e.g. a seam for later Lua/warhead activation) without a live grant, declare an `ExternalCondition` whose `Condition` field is `[GrantedConditionReference]` (`Conditions/ExternalCondition.cs`) — it satisfies the lint at zero runtime cost and a later `GrantCondition("name")` resolves to it.

**The Fluent lint is bidirectional, and the unused-key half is a WARNING that rots.** `CheckFluentReferences` checks referenced-but-undefined (an error) *and* defined-but-unreferenced (`CheckUnusedKey`, `Lint/CheckFluentReferences.cs:447-455`, `emitWarning`), reached for every key of every non-external file — and a file under `mods/ww3mod/` is not external. Unused keys therefore only fail the run under `TREAT_WARNINGS_AS_ERRORS=true` (`UtilityCommands/CheckYaml.cs:51`), and they arrive in a pile nobody reads to the end. That is how the entire server/lobby notification block in `mods/ww3mod/languages/en.ftl` — 38 keys from `timeout-in` (`:84`) through `chat-temp-disabled` (`:129`) — came to be **dead**: not one of those bare names appears as a string literal anywhere in `engine/OpenRA.Game/` or `engine/OpenRA.Mods.Common/`, because the `[FluentReference]` consts name the `notification-`-prefixed forms that live in `engine/mods/common/fluent/common.ftl` (30 of the 38 have such a twin; the other 8 were renamed *and* reworded upstream). Editing the ww3mod copies changes nothing any player sees. **Treat a large standing warning count as the defect it is** — this one had a real bug hiding in it.

**Grants scoped to the actor:** `GrantConditionOnBotOwner` grants only on the actor it sits on, checking `self.Owner.IsBot && Bots.Contains(self.Owner.BotType)` (`Conditions/GrantConditionOnBotOwner.cs:46`). A **unit** trait's `RequiresCondition` sees only conditions granted on that *unit*, so gating a unit trait to bot-only needs a per-unit `GrantConditionOnBotOwner` on the unit template — a Player-actor grant (e.g. the `enable-ai-experimental` grants in `ai.yaml`) does nothing for a unit trait.

### Faction-specific files

Each unit type has a base template file and two faction files:

- `aircraft.yaml` → `aircraft-america.yaml` + `aircraft-russia.yaml`
- `infantry.yaml` → `infantry-america.yaml` + `infantry-russia.yaml`
- `vehicles-america.yaml` + `vehicles-russia.yaml`

A unit type is defined in three tiers: an abstract template `^E6` and a bare concrete `E6:` (`Inherits: ^E6`) live in the base file (`infantry.yaml`); the buildable faction variants `E6.america:` / `E6.russia:` (each `Inherits: ^E6`, adding `Buildable`/`RenderSprites`) live in the faction file (`infantry-america.yaml:95`, etc.). Keys are declared uppercase but actor lookup is case-insensitive. **To annotate every variant at once, override the `^Template`** — a trait added to `^E6` reaches the bare concrete and both faction variants in one line; single-hull tweaks (`bradley`, `bmp2`) go on the concrete key.

This is also the reliable way to add a trait from **map/test `rules.yaml`**: override a `^Template` (e.g. `^Combatant`) or a bare hull key (`t90`, `bradley`), as `demo-wgm-suite/rules.yaml` does. Overriding a **faction-suffixed** concrete key (`ar.america`) from map rules has been observed to throw `LoadFromManifest<Rules>, duplicate values found for the following keys: ar.america: [ActorInfo,ActorInfo]` at load — prefer the template.

### Weapon `ValidTargets`: `Air` ⊃ `Helicopter` (the two are NOT disjoint)

**An airborne helicopter carries BOTH `Air` and `Helicopter`.** `^Helicopter` inherits `^Airborne` → `^NeutralAirborne`, whose `Targetable@Airborne` grants `Air, AirDetonateAttack` while the `airborne` condition holds (`rules/ingame/aircraft.yaml:35-38`), and `^Helicopter` adds its own *unconditional* `Targetable@Helicopter: Helicopter` (`:164-165`). Nothing in `rules/` removes `Targetable@Airborne`. A **landed** helicopter is `Ground, Vehicle` + `Helicopter` and is no longer `Air`; a fixed-wing aircraft is only ever `Air`. So:

- `Helicopter` is the **heli-only** selector — it is how a weapon engages helicopters *without* being able to touch fixed-wing.
- `Air` **sweeps both** helicopters and planes (while airborne).

That asymmetry is the design: ground autocannons and MGs list `Helicopter` and so can shoot helis without becoming air-defence — `^7.62mm` is `Infantry, Unarmored, Helicopter` (`weapons/weapons-ballistics.yaml:144`), `^12.7mm` adds `Light` (`:215`), and even Tunguska's dedicated `30mm.Tunguska.AA` autocannon is `ValidTargets: Helicopter` (`:455`), so it cannot engage a jet. Guided SAMs list `Air`: `MANPAD`/`Stinger`/`Stinger.quad`/`9M311` (`weapons/weapons-missiles.yaml:339,372`; `9M311 Inherits: Stinger`), which is how Tunguska gains true air-defence — via its `9M311` missile (`vehicles-russia.yaml:860`), not its gun. An "is this an air-defence weapon?" test must therefore key on the literal `Air` target type; keying on `Helicopter` sweeps in every MG-armed vehicle.

**Consequence for `CreateEffect` warheads:** an air-impact effect wants `ValidTargets: Air` alone. Writing `Air, Helicopter` also matches a *landed* helicopter, which the template's ordinary `Ground` warhead already covers — so the impact draws two explosions stacked on one hit. Note also that an in-flight ballistic missile (`^ShootableMissile`, `rules/defaults.yaml:877-891`) is `ICBM` and **not** `Air`, and that one unlisted target type on the victim suppresses the whole effect rather than degrading it (`CreateEffectWarhead.DoImpact` early-returns on `ImpactActorType.Invalid`, `:124-125`).

**The suppression is caused by BYSTANDERS, not only by the intended victim — an actor with a `HitShape` and no enabled `Targetable` swallows the explosion and the sound of any shell landing on it.** `ActorTypeAtImpact` (`CreateEffectWarhead.cs:67-96`) walks `FindActorsOnCircle(pos, WDist.Zero)` and, for every actor whose hitshape contains the impact point, sets `anyInvalidActor = true` unless the warhead `IsValidAgainst` it (`:89-92`) — and `IsValidAgainst` fails immediately when `GetEnabledTargetTypes()` is empty (`:107`). One such actor is enough: the method returns `Invalid` and `DoImpact` returns before the sprite and before `Game.Sound.Play` (`:155`). Because `^1x1Shape` spans a whole cell, an untargetable full-cell actor silences *every* shell in its cell. **Damage is unaffected** — `CreateEffectWarhead` and `WarheadAS.IsValidImpact` (`WarheadAS.cs:75-85`) are the only two sites carrying this early-out; `DamageWarhead.DoImpact` has no position-level gate. So "the shell did nothing" and "the shell did damage but looked and sounded like nothing" are different defects. Since `db01b0ae` both sites skip cosmetic ground cover (`victim.IsGroundCover()`, `CreateEffectWarhead.cs:82`, `WarheadAS.cs:48`), which is what un-silenced shells landing on `^CivField`; any *other* untargetable-but-hitshaped actor still swallows them.

### A duplicate trait key inside ONE actor: LAST value wins, at the FIRST key's position

**Scope first, because the rule inverts.** What follows holds while **one source** declares the actor. The moment a *second* source names it — a map's `rules.yaml`, or another mod rules file — the merge inspects the accumulated child list and a duplicate key becomes an `ArgumentException` **at rules load** (`MergePartial` → `IntoDictionaryWithConflictLog`, `MiniYaml.cs:522-529` → `Exts.cs:484-491`; that helper throws, despite the name). A shipped duplicate is therefore not "inert" — it is a latent load error armed against anyone who overrides the actor, and since overriding a `^Template` from map rules is the recommended idiom (below), a duplicate inside a template is the sharpest form. `^CivField` carries one today. Details and a no-build reproduction: `WORKSPACE/DISCOVERIES.md` 2026-08-17. With a single source:

Two same-named trait nodes inside a single actor do **not** produce two traits and do **not** throw. `ResolveInherits` hands each child to `MergeIntoResolved` (`engine/OpenRA.Game/MiniYaml.cs:427-447`), which on a repeat key finds the earlier node's index and writes `existingNodes[existingNodeIndex] = existingNode.WithValue(MergePartial(...))` (`:444`). So the survivor **keeps the FIRST occurrence's position in the node list but takes the LAST occurrence's field values** — and the merge is per-field, so a later block that sets only *some* fields overrides only those and inherits the rest from the earlier one. (`MergeSelfPartial`, `:497`, is a *different* function that de-dupes only **top-level** keys per source and never sees this case.)

**The blast radius is bigger than a wrong number: the dead block is invisible to every reader AND to `make test`.** The YAML lint does not flag duplicate child keys, so an actor can carry a plausible-looking stat the engine has never used, indefinitely. Any balance pass that reads top-down and stops at the first `Health:` tunes a value with no effect. (Real instance: `tunguska` declared `HP: 14000` and then `HP: 8000` thirteen lines later, and the actor fielded **8000**.)

- **`./utility.sh --resolved-rules <actor>` settles "which value wins" in one command** (`UtilityCommands/OutputResolvedRulesCommand.cs`) — it needs only a successful build, launches no match, and so is not gated by the no-autonomous-test-runs rule. Actor names are **case-sensitive** here even though actor lookup elsewhere is not — and the key it matches is the **YAML key verbatim**, not the lowercased ruleset key: `humvee` resolves, `mi28` returns *"Could not find actor"*, `MI28` resolves. Copy the key as written in the rules file. **Use it rather than hand-rolling a resolver for bulk "which actors carry trait X" sweeps.** A two-stage script (merge each actor across rule files, then apply `Inherits:`) must carry `-Trait:` nodes *through* the merge stage; the natural implementation applies each removal as it merges, where the definition table is still empty, so the node matches nothing and is then not carried forward. The removal vanishes and every descendant reports the trait as present — silently, and in the **over**-reporting direction. That is how `^CivBuilding`'s five `-Capturable*`/`-CaptureManager` lines (`civilian.yaml:6-10`) disappeared from a sweep. If a script is unavoidable, cross-check it against the utility on at least one actor with an explicit removal.
- **Technique worth reusing for any "clean up this YAML without changing behaviour" task:** capture `--resolved-rules <actor>` before and after and `diff`. Identical output is a byte-exact proof of behaviour-neutrality across the *whole* actor — inheritance, `-Removals`, faction variants and all — far stronger than eyeballing the edited lines, and it catches the blank-line/adjacent-entry merge accident below as a side effect.
- **Corollary when de-duplicating: preserving the resolved value is NOT the same as keeping the block you would expect.** Because the survivor sits at the *first* position but carries the *last* values, the behaviour-neutral edit is "keep the earlier block's slot, write the later block's values into it, delete the later block". Deleting the *first* block also preserves behaviour but silently relocates the trait in the file. **Deleting the second block while keeping the first block's values is the one option that changes behaviour — and it is the one that looks most obviously correct.**

### `Versus`: an OMITTED armor class is FULL damage, the opposite of a zero

`DamageWarhead.DamageVersus` (`Warheads/DamageWarhead.cs:96-110`) starts at `damage = 100`. An **empty** `Versus` early-returns that full damage (`:101-102`). A **non-empty** one filters the victim's armors to the classes it *lists* — `Versus.ContainsKey(a.Info.Type)` (`:105`) — so an **unlisted** class matches nothing, `ApplyPercentageModifiers` runs over an empty sequence, and the victim takes the unmodified **100%**. **A table that zeroes six classes and omits a seventh is a full-damage weapon against the seventh, not a weak one.**

WW3MOD's armor population is exactly nine: `Concrete, Heavy, Indestructable, Kevlar, Light, Medium, None, Unarmored, Wood`. Two traps follow from that list:

- **`Kevlar` is `^Soldier`'s armor** (`infantry.yaml:173-174`) and reaches essentially the whole combat-infantry roster by inheritance, while non-`^Soldier` actors keep `^Infantry`'s `Type: None` (`:34-35`). So a `Versus` table that zeroes `None` but omits `Kevlar` is harmless to a civilian and **lethal at full damage to every soldier** — selective in exactly the way that survives eyeballing.
- **Writing a class name that does not exist is silently a no-op.** A shipped table zeroing `Brick` accomplishes nothing, because `Brick` is not an armor class in this mod.

**So any "this weapon cannot hurt anything" judgement must be made against the ruleset's armor population, never against the table alone** — and three further shapes make such a judgement unprovable outright, because each ends at the same empty filter and therefore **fails open to full damage**: a null `ArmorInfo.Type`, a **conditional** `Armor` (it is a `ConditionalTraitInfo`, so it can be absent at runtime, and the filter also drops `IsTraitDisabled`), and a non-empty `HitShapeInfo.ArmorTypes` that excludes the class. `DangerFieldLayer.RulesetArmorTypes`/`WarheadIsHarmless` implement this test and fail open on all three; they are NUnit-pinned in `DangerFieldKernelTest`.

### Weapons live under `Weapons:`, and a warhead override REPLACES rather than merges

Two authoring traps that both end in a confident wrong answer rather than an error.

**A map's weapon overrides belong in the file named by `Weapons:` in `map.yaml`, never `Rules:`.** They are separate manifest keys (`Map.cs:180` maps `Weapons` to `WeaponDefinitions`, distinct from `RuleDefinitions`). Put a weapon block in the rules file and the loader reads the weapon name as an **actor** and its `Warhead@…` children as **traits**, producing `Cannot locate type: WarheadInfo` — an error naming neither the file nor the weapon. The game then never reaches the Lua, no verdict is written, and the runner reports a **timeout rather than a rules error**. *Check `debug.log` for "Failed to load rules" before treating a hang as a hang.*

**When overriding an existing warhead, restate its TYPE and every field the consumer reads.** `WeaponInfo.LoadWarheads` (`GameRules/WeaponInfo.cs:200-206`) builds each warhead with `Game.CreateObject<IWarhead>(node.Value.Value + "Warhead")` — **the node's *value* names the type**, so `Warhead@Spread:` written bare resolves `"Warhead"` and fails; write `Warhead@Spread: SpreadDamage`. And because the object is constructed fresh and `FieldLoader` fills only the fields present, **every omitted field falls back to the ENGINE default, not to the mod's value.** This is the opposite of the trait path, which merges per-field (see the duplicate-trait-key section above). The worked example: an override that restated only `Damage` and omitted `Penetration: 15` silently got the engine's `Penetration = 1` (`Warheads/DamageWarhead.cs:24`), which against a `Thickness: 10` target took the reduction branch and cut the intended effect by an order of magnitude — **and the scenario still completed and reported `pass`**, returning a confident number about a world that was never built.

### Blank lines are significant

Templates and top-level entries must be separated by a blank line. The MiniYaml parser silently merges adjacent ones, producing confusing override behavior — not a parse error. If a template "isn't taking effect," check the blank lines first.

### Removing an inherited trait: `-Key` matches the FULL node key

`-TraitName:` removes an inherited node only by **exact key match, including any `@label`** — `ResolveInherits` does `resolved.RemoveAll(r => r.Key == removed)` and throws `There are no elements with key '<key>' to remove` if nothing matched (`MiniYaml.cs:482-483`). So `-SquadManagerBotModule:` does **not** remove `SquadManagerBotModule@experimental.america.fixedwing`; you must write `-SquadManagerBotModule@experimental.america.fixedwing:`. There is no "remove all instances of this trait type" wildcard form — each labeled instance must be listed.

**A REDUNDANT removal is a hard error too, and inside a map's `rules.yaml` that error is SWALLOWED.** Stripping a trait on a base actor and then stripping it again on a derived actor that already `Inherits:` the stripped parent leaves the second `-Key:` with nothing to match, so it throws like any other mismatch. In mod rules that surfaces as a load-error dialog; in **map** rules it does not — `Map.PostInit` wraps the whole rules load in a `catch`, logs `Failed to load rules for <title> with error` to `debug.log`, sets `InvalidCustomRules`, and **falls back to `Ruleset.LoadDefaultsForTileSet`** (`Map.cs:540-547`; the scenario-rules loader has an identical catch at `:698-704`). Every actor type the map defined then ceases to exist. The map does not report a rules problem — it dies later and elsewhere, typically in the density pass at `actorsRules[actorType]` (`Map.cs:988`) with `KeyNotFoundException: The given key '<your custom actor>' was not present in the dictionary`, which reads exactly like a typo in the map's actor list and is nothing of the sort. **On a `KeyNotFoundException` naming a map-defined actor type, grep `debug.log` for `Failed to load rules` before debugging the actor list.**

### WW3MOD's map grid is `Rectangular`, not `RectangularIsometric`

`mod.yaml:319` sets `MapGrid: Type: Rectangular`. So cell neighbours are the plain `(x±1, y±1)` grid, a Manhattan/Chebyshev disc maps directly to spatial adjacency, and `CellLayer.Contains(CPos)` has no `X<Y` isometric rejection. This is what lets the density-neighbour idiom (`CohesionMoveModifier.CoverScore`, and the Phase-1 map layers) step cells with raw `CVec` offsets.

### Disabling a string field: bare colon, not `""`

To clear a widget/chrome string field (`Background`, `Decorations`, `Separators`, `TooltipText`, …), use a **bare trailing colon**, never empty quotes. `FieldLoader.ParseString` returns the value verbatim (`FieldLoader.cs:161`), so `Separators: ""` parses as the literal two-character string `""`. That passes the `!string.IsNullOrEmpty` guards in the widgets, and the code then tries to load a chrome collection literally named `""` — e.g. `Sprite ""/separator was not found`. `Separators:` (bare colon) parses as null, `IsNullOrEmpty` fires, and the feature is skipped as intended.

### Maps must declare `Rules: rules.yaml`

A map's `rules.yaml` is loaded **only** when `map.yaml` names it under the top-level `Rules:` key. The engine maps that key to `Map.RuleDefinitions` (`Map.cs:176`, `required: false`); if it's absent, `RuleDefinitions` stays an empty MiniYaml (`Map.cs:364`) and the map loads only mod defaults. The map still renders and actors still spawn, so the omission is **silent** — LuaScript references, AutoTarget overrides, and every rule tweak are simply ignored. The same applies to `Weapons:`, `Sequences:`, etc.

## PITFALL comments (full spec: [`pitfalls.md`](pitfalls.md))

Recurring traps get a one-line `// PITFALL:` (`# PITFALL:` in YAML) **at the temptation site** — the line a careless reader is looking at when about to fall in. List all: `git grep PITFALL`. Add them during bug fixes when the root cause would surprise a reader; prune when stale (a wrong PITFALL is worse than none). Not for one-shot fixes, generic best practice, or universal anti-patterns (those go in a hook or the engine code rules below).

## Engine code rules (enforced by `tools/git-hooks/pre-commit`)

- **`[Sync]` on a trait that does not implement `ISync` hashes nothing and warns about nothing.** The type test is `Actor.cs:206`. Adding the attribute is not adding sync coverage — see architecture.md §"`[Sync]` is inert without `ISync`" for the rule, the effects equivalent, and the NUnit guard that now catches it.
- **No `Console.Write`/`WriteLine` in tick-path code** — use `Log.Write(channel, ...)`. Console output fires every tick and floods stdout. Allowlisted directories: `UtilityCommands/`, `UpdateRules/`, `/Lint/`, `OpenRA.Server/`, `OpenRA.Test/`, `OpenRA.Utility/`, `tools/`.

Hook install (once per clone): `ln -sf ../../tools/git-hooks/pre-commit .git/hooks/pre-commit`

### A green analyzer gate means what the TARGET GRAPH reaches, not what the solution lists

**Release builds have no analyzers at all.** `engine/Directory.Build.props:51-56` removes every `Analyzer` item when `Configuration=Release`. So any target that routes through a Release build contributes **zero** analyzer coverage, however many projects it compiles — and a `make` target that depends on it still goes green.

That is not hypothetical: it was the whole of the long-standing Windows/Linux gate asymmetry. Both platforms read the same solutions; they diverged on which **engine target** the mod's `check` depends on. `make.ps1` routes `check` into `engine\make.cmd check`, a Debug `-warnaserror` build of `engine/OpenRA.sln`; `Makefile:191` is `check: engine`, and the engine's `all` target is **Release**. Linux/macOS was not missing projects from a solution — it was building the right solution in the wrong configuration.

**Generalise this: when two CI lanes disagree about what they catch, diff the target graph, not the solution files.** `make.ps1` and `Makefile` are independent implementations of the same target names in this repo and have drifted before.

Two related traps in the same area:

- **Effective severity in `engine/.editorconfig` is the LAST assignment for an id, not the one under the explanatory comment.** `RCS1058` is set to `warning` at `:1098` and to `suggestion` at `:1396`, both inside the same `[*.{cs,csproj,yaml,lua,sh,ps1}]` section — a whole block of `SA`/`RCS` rules is silently downgraded this way. **Compute the final value** (`awk` over every `dotnet_diagnostic.<id>.severity`) before concluding a rule is enabled, disabled or broken, and especially before picking a rule to prove a gate is live with: a rule you believe is a `warning` may be reporting as a suggestion and failing nothing.
- **The `RUNTIME=mono` build path is a DIFFERENT gate, not the same gate run again.** *(It was a CI lane until `70fd483e` removed it — `.github/workflows/ci.yml` now has exactly two jobs, `Linux (.NET 6.0)` and `Windows (.NET 6.0)`. The path is still reachable via `make RUNTIME=mono`, so the trap below is live for anyone who runs it.)* `engine/Directory.Build.props:61-63` drops both Roslynator packages when `MSBuildRuntimeType` is `Mono` (upstream comment: they fail there with `AD0001`), so no `RCS*` rule can fire on that lane. It also builds a different TFM — `netstandard2.1` rather than `net6.0` (`:22-23`) — which is why several `System.*` `PackageReference`s that read as redundant at `net6.0` are load-bearing (`System.Collections.Immutable`, `System.Threading.Channels`, `System.Runtime.Loader`, `Microsoft.Win32.Registry`): the same file at `netstandard2.1` fails `CS0234` without them. **Do not delete a reference because one lane calls it redundant.**
- **`NuGetAudit`'s transitive reach is a target-framework effect, not an SDK effect.** The knob is `NuGetAuditMode`, which defaults to `direct` and only flips to `all` at `net10.0`. Measured on one package, one SDK (10.0.400), bare `dotnet restore`: `NU1902` is not raised at `net6.0` or `net8.0` and is raised at `net10.0`; forcing `-p:NuGetAuditMode=all` reproduces it at `net6.0` on demand. So an SDK pin is not what hides a transitive advisory — it surfaces on the TFM bump commit itself.
- **The mirror case — a gate covering MORE than you think: `Class=Unknown` does NOT hide a map folder from `--check-yaml`, because `HasFlag(0)` is always true.** `mods/ww3mod/mod.yaml:107` registers the autotest scenario tree as `Unknown`, which does keep it out of every UI tab. But `CheckYaml` calls `EnumerateMapDirPackagesAndNames()` with its default `MapClassification.System` (`MapCache.cs:212`), and the folder filter is `classification.HasFlag(packageClassification)` (`MapCache.cs:194`) — with `MapClassification.Unknown = 0` (`MapPreview.cs:35`), `HasFlag(0)` is `(x & 0) == 0`, true for every value. So the scenario maps are linted exactly like shipped content, and there is **no classification value that excludes them** — the sentinel makes it unfixable by reclassification alone. Two consequences: a per-map defect in the scenario tree is indistinguishable from one in shipped content unless you attribute each error back to its `Testing map:` header, and **error counts multiply by map** — one rules-level defect reports once per linted map, so a total can fall by hundreds without a defect being fixed. **Compare error classes, never totals.**
- **Method note: a `dotnet build` reporting `0 Warning(s)` may simply have been up-to-date.** Check for the `-> ….dll` line and a plausible elapsed time before believing a zero; `-t:Rebuild` forces `CoreCompile` to actually run.

## Shell scripts run under zsh — an unquoted `$var` is NOT word-split

The repo's scripts and the agent shell both run zsh, where `prog $args` passes the variable as **one** argument rather than splitting it on whitespace the way bash does. So the common bash idiom

```bash
for p in "--perturb 0" ""; do ./probe.sh $p; done     # zsh: passes ONE arg "--perturb 0"
```

hands `probe.sh` a single glued token that no flag parser matches. Use an array (`args=(--perturb 0); prog $args`) or `${=var}` to force splitting.

**Why this earns a place here rather than being generic shell trivia: the failure is silent and it inverts results.** The flag never parses, so the feature under test never activates, and the run completes normally — reporting IDENTICAL / PASS for a comparison that was never perturbed. It cost two false results in one day, including a self-test that passed *while believing it was perturbed*. **Prove the flag arrived (echo the received argv) before trusting a null difference or blaming a stale build.** Same family as the `| tail` verdict-swallowing trap in [`../recipes/AUTOTEST.md`](../recipes/AUTOTEST.md): the shell reports success for a thing that did not happen.

## Engine behaviors that surprise (debugging gotchas)

- **A diagonal cell step is produced by THREE independent code paths, and only one of them is the pathfinder — so a new movement rule placed in the graph is not in force.** (a) `DensePathGraph.GetConnections` → `GetPathCostToNode`, the multi-cell case; (b) **`PathFinder.FindPathToTargetCell` (`Traits/World/PathFinder.cs:106-113`), the one that is easy to miss** — for `source.Layer == target.Layer && (source - target).LengthSquared < 3` it returns the two-cell path **without building a graph at all**, and `LengthSquared == 2` *is* a diagonal, so every single-step diagonal (exactly the order a player issues when clicking just past a gap) bypasses the graph; (c) `Mobile.GetAdjacentCell`, the "back up to let others pass" sidestep, which walks all 8 `CVec.Directions` under `CanEnterCell`/`CanStayInCell` only. Any "you may not take this step" rule has to be taught to all three.
  - **And a rule whose blockage is NOT in the destination cell will spin `Move` forever unless it is also taught to `PopPath`'s escape** (`Move/Move.cs:296-303`). The blocked-handling block has exactly one path-clearing exit, and it was a plain `CanEnterCell` test — which returns *true* for a corner-squeeze, because the blockage lives in the two shoulder cells while the destination is ordinary open ground. The comment and the extra disjunct are at the site now. **General form: if your rule is a property of the *edge* rather than of the *cell*, every destination-only predicate in the movement stack is blind to it.**
  - **Both-shoulders vs either-shoulder is load-bearing, not a taste call.** `DirectedNeighbors` prunes each expansion to cells "not guaranteed to be reached more cheaply through our parent", a proof that assumes reachability is direction-independent. It survives a **both**-shoulders rule because for every neighbour the straight-incoming rows discard, the parent's diagonal to it has the currently-expanding (therefore passable) cell as one shoulder — so the parent's move can never be corner-denied. Under an **either**-shoulder rule that neighbour becomes deniable, the pruning silently drops reachable cells, and the search goes incomplete: paths vanish in tight terrain.
  - **Infantry are EXEMPT, deliberately — a solid wall corner does not stop them, and that is an accepted trade, not a bug.** `Locomotor.IsDiagonalSqueeze` (`Locomotor.cs:252`) returns early for `SharesCell` locomotors, so a subcell-capable actor still walks diagonally between two solid cells — including the two corners of a building, a cliff, or the outside corner of any structure. Full-cell occupants (every wheeled, tracked, walker, naval and landing-craft locomotor) are denied it. **Do not "fix" this** — it is a user decision of 2026-08-08, and the reasoning is in-code at `:254-257`. The criterion is occupancy, not unit class: `SharesCell` is not a *proxy* for subcell capability, it **is** the switch (`Mobile.cs:321` assigns `ToSubCell` straight from it), so the scoping cannot drift and a future cell-sharing unit is exempted with no list to edit. In this mod it partitions cleanly — `SharesCell: true` appears on exactly the four `foot*` locomotors (`world.yaml:32/47/64/80`, re-derived 2026-08-19) and nowhere else. It also had to be a *locomotor* property rather than a per-actor test: `DensePathGraph.DirectedNeighbors` prunes on direction-independent reachability, and a search runs against exactly one locomotor, so a locomotor-level exemption keeps the both-shoulders argument (above) intact for the whole search. Naval was flagged as the live edge and is a non-issue: those locomotors are vestigial RA carry-over and `rules/ingame/naval.yaml` has **zero** non-comment lines, so no ship exists to be blocked.
  - **Scope, as shipped: the rule is tank-traps-only.** It keys on a marker trait `BlocksDiagonalSqueeze` via `CellFlag.HasDiagonalSqueezeBlocker` (`Locomotor.cs:33`, set `:575`, read `:303`), carried by exactly `TANKTRAP1` and `TANKTRAP2` (`decoration.yaml:535`, `:548`). Deliberately **not** on `^Rock` or `^Tree` — an earlier, broader version keyed on generic impassability and closed tree-corner pockets all over the mod.
- **Vehicles CANNOT crush or drive through trees or hedges in this mod — a belief that has come up more than once and is wrong.** Crushing here is not the engine `Crushable` trait (no actor uses it); it is modelled through `Passable`, which carries `CrushedByRelationships` (`Passable.cs:29`). `SBAG`/`FENC`/`BARB` set their pass class **plus `CrushedByRelationships: Enemy`**, and the heavy vehicle locomotors list those classes in `Crushes` — so tanks really do crush sandbag, wire and barbed wire, and only an **enemy's**. But `^Tree` sets `PassClasses: tree` with **no `CrushedByRelationships` at all** (`decoration.yaml:13-14`), and `tree` appears in no vehicle locomotor's `Passes` or `Crushes` list — only the four `foot*` locomotors pass it. Trees are hard blocks to vehicles and walk-through cover for infantry.
- **A locomotor's `Crushes` classes ARE pass classes — `PassableClasses` is the UNION, so a crush-only class is not dead configuration.** `LocomotorInfo.RulesetLoaded` sets `PassableClasses = Passes.Union(Crushes)` (`Locomotor.cs:110`), and that union is what `IsBlockedBy` hands to `passable.PassableBy(...)` when deciding enterability (`:433-441`); `Passable.PassableInner` just tests `Info.PassClasses.Overlaps(passClasses)` (`Passable.cs:162`). Crushing itself happens **after** entry, in `Passable.OnBeingPassed`, which re-tests `passerMobile.Info.LocomotorInfo.Crushes.Overlaps(...)` before firing `OnBeingCrushed` (`Passable.cs:92-96`). So listing a class under `Crushes` alone both lets the unit in **and** crushes the occupant — `Passes` is the "walk over it, leave it alone" half, `Crushes` is "walk over it and kill it", and neither is a prerequisite for the other. **Do not read `IsBlockedBy`'s `Info.PassableClasses` as "the `Passes` field"** — it is a derived union computed at ruleset load, one indirection away from the YAML key it is named after, which is exactly the README §Four-shapes trap of citing a real line that does not do the work you think it does. *(This corrects a 2026-08-09 static analysis and the `[med]` bug it filed, which concluded that eight locomotors' `Crushes: fence` was inert and that 384 placed fence/wire actors were solid walls to every vehicle. The inference was inverted; the YAML is doing what it reads as doing.)*
- **Pausing `Mobile` is the engine's "halt this order and resume it later" primitive — it does NOT end the activity.** `Move.Tick` returns `false` while `mobile.IsTraitPaused` (`Move/Move.cs:167`), so granting a `Mobile.PauseOnCondition` condition stops a unit *mid-order* and revoking it resumes the same activity with no re-issue and no path re-plan. `MobileInfo` is a `PausableConditionalTraitInfo` (`Mobile.cs:26`), so this is available on any actor. Cancelling and re-queuing is the obvious alternative and is strictly worse — the interrupted order is exactly the thing that has to survive. Note `IsCanceling` is tested *before* the pause check (`:160`), so a paused unit can still be cancelled; a break-off does not have to un-pause first.
  - **The MiniYaml half, and it generalises past this trait: a condition EXPRESSION is a single field, so restating it on a child REPLACES the inherited one rather than adding to it.** The trait merges per-field; the boolean expression inside the field does not merge at all. `^Vehicle` carries `PauseOnCondition: !(!empdisable && !being-captured)` (`vehicles.yaml:38`), so a bare `PauseOnCondition: my-condition` on a derived actor would silently let an EMP'd or mid-capture unit drive away. The inherited terms must be restated — which TRUK does (`:564`, with the reason recorded in-file at `:561-563`). Applies to every single-field expression, not just this one.

- **`traitreport.log` counts trait interface QUERIES, not implementors — never read it as a census.** The tell is on its own first line: `IAirborneVisibility: 723287`, and no mod has 723k traits. No cooldown or hysteresis is needed and adding one would be wrong — the range, cluster and soft-overkill terms are bounded by construction to stay strictly inside one bucket, so **the band comparison IS the hysteresis**.
- **A killing hit fires `Damaged` AND `Killed`, so any per-hit handler with a death handler beside it runs BOTH.** `Health.cs` clamps damage (`:189`), builds the `AttackInfo` with the DamageState evaluated *post*-clamp but `Damage` left unclamped (`:191-197`), then fires `INotifyDamage.Damaged` (`:199-201`) and, on a fatal hit, `INotifyKilled.Killed` (`:216-220`). `Cargo` implements both — a per-hit passenger-damage curve at `:641` and a transport-death curve at `:855` — so passengers of a transport destroyed in one blow take **both**. The load-bearing detail when writing such a guard is that `DamageState.Dead >= DamageState.Heavy`, so a naive "bail out if badly hurt" threshold also matches death; `Cargo.ShouldEmergencyBail` (`:593-595`) spells the exclusion out as `current >= bailAt && current < DamageState.Dead`. One documented exception: the `Damaged` arm early-returns for actors with `GarrisonProtectionInfo` (`:646-647`), so "both curves always run" is not quite universal.
- **`Cargo.AfterUnloadDelay` is an EXIT delay, not a spacing delay, despite the name.** It is applied only in the `if (!unloadAll || !cargo.CanUnload())` branch (`Activities/UnloadCargo.cs:166-169`) — i.e. once, on the way out — and ww3mod sets it to `0` on every APC while aircraft use 40. The *spacing* between passengers is a separate mechanism: `NextUnloadDelay()` queued between passengers (`:179-186`), with `UnloadGroupSize = 2` and `InterGroupUnloadDelayMultiplier = 3` (`Cargo.cs:70`, `:85`). Tuning dismount pacing means the latter, never `AfterUnloadDelay`.
- **"Critical damage" names TWO thresholds 25 percentage points apart, and the `critical-damage` condition is the stricter one.** `Health.cs:95-100` puts `Critical` below **25%** MaxHP and `Heavy` below **50%**. In YAML, `critical-damage` is granted only at `Critical` (`defaults.yaml:194-196`, `ValidDamageStates: Critical`) while `heavy-damage-attained` covers Heavy **and** Critical (`:191-193`). Meanwhile the mod's "badly damaged" *design* cluster all fires at 50% — cook-off `StartIfBelow: 50`, smoke `StartFraction: 50`, and `VehicleCrew.EjectionDamageState = DamageState.Heavy`. **So a rule written against `critical-damage` because it "means badly damaged" fires at half the health the neighbouring rules do**, and the gap is silent. Pick the condition by threshold, not by name.
- **Selection priority is a GROUP FILTER, not a ranking.** `SelectableExts` (`engine/OpenRA.Game/SelectableExts.cs:96-103`) groups candidates by *exact* priority and returns only the top group — so a modifier cannot re-rank within a selection, it can only move a unit into or out of the winning band. `BaseSelectionPriority` seeds `int.MaxValue` (`:54-65`) and `ISelectionPriorityModifier` values are added afterwards (`:35-36`). The shipped ladder is **10, 8, 6, 4, 2, 1, 0** — there is deliberately nothing at 9, so a `-1` modifier demotes a unit out of its band without landing it in another one. Modifiers can be made conditional on a held key via `SelectionPriorityModifier.SuppressedBy` (`:31`, default `None`).
- **A commented-out trait block is not necessarily "disabled" — it can be a trait the engine no longer HAS.** `SmokeTrailWhenDamaged` exists in this tree only as an `UpdateRules` migration (`UpdateRules/Rules/20210321/RemoveSmokeTrailWhenDamaged.cs`); there is no such trait class. So a commented block naming it is not a feature someone switched off and could switch back on — uncommenting it would fail to load. **Before "re-enabling" a commented trait, check the class still exists**; the modern replacement here is `LeavesTrails`. Related authoring trap in the same family: `WeaponInfo.LoadWarheads` (`GameRules/WeaponInfo.cs:200-203`) collects warheads by a raw `StartsWith("Warhead")` with **no de-duplication**, unlike the trait path (which merges last-value-wins at the first key's position, above) — so two `Warhead@Smudge` blocks in one weapon really do both load.
- **Two WW3MOD-only filters drop a target on the AUTO path alone, and their asymmetry is diagnostic.** `AutoTarget.ChooseTarget` skips a candidate on **overkill** (`AutoTarget.cs:1373`, `Info.OverkillThreshold >= 0 && target.Actor.AverageDamagePercent >= OverkillThreshold`; default `100`, `:217`) and on **break-off** (`:1382-1385`, `Info.BreakOffCondition`, default `critical-damage`, `:232`). Break-off has a *second* site in `Activities/Attack.cs:214-217`, gated `!forceAttack`; overkill has none — grepping `AverageDamagePercent` across the attack classes finds only a comment. **So the two behave differently on a manual order: overkill is skip/fire/fire, break-off is skip/skip/fire.** If a unit refuses an auto-target but obeys a right-click, suspect overkill; if it refuses both but obeys force-fire, suspect break-off. There is also a **soft** overkill term (`SoftOverkillThreshold`, default `50`, `:221`) applied at `:1453` as a range-scaled priority penalty rather than a skip, and a `declinedShootableTarget` flag that records `LastHeldFireTick` when these filters are why nothing was chosen — use it rather than inferring.
- **The overkill mark is an ownerless accumulator on the TARGET that only decays — nothing releases it.** `Actor.AverageDamagePercent` is a plain public int (`Actor.cs:83`) and `MarkForDestruction` only ever *adds* (`:85-88`); the sole clearing mechanism is a halving every 60 ticks (`Actor.cs:309-310`, whose PITFALL records why the interval went 20 → 60: a 20-tick halving let other units re-target a tank mid-reload). **Consequences worth knowing before hunting a leak: killing the committing unit does not release its mark, and neither does retargeting, the attacker's own target dying, or the attacker entering a transport.** There is no leak to find — the value is self-clearing by construction, and self-clearing is the *only* way it clears. Equally, any source adding ≥ the threshold per 60 ticks holds it above the threshold indefinitely; it is unbounded upward. **The mark is applied once per COMMITMENT, not once per shot** (measured: a unit firing 8 times on a strict `BurstWait` cadence did not re-suppress its neighbours), so the `AttackFollow` opportunity-fire re-mark path (`:173`, `:189`, `OpportunityFire` default `true` at `:26`) does not re-apply on the reload cycle.
- **A single attacker's claim is capped at one kill's worth, and aggregate commitment is self-limiting by design.** `EstimatePercentDamage` returns `Math.Min(totalDamage * 100 / health.MaxHP, 100)` (`AutoTarget.cs:1591`) — before that cap, one MANPAD marked a 600-HP helicopter at 500 against an `OverkillThreshold` of 100, needing three halvings to clear. The intended shape is that attackers commit until the marked total covers the target's health and the rest stand down, which is correct in aggregate; the failure mode was **granularity at the fragile end**, not a runaway loop. Note the residual shape still holds: **suppression duration scales as `damage × 100 / MaxHP`, so the most fragile target is marked hardest and suppressed longest** — which is exactly the case a player expects a battery of AA to shred. The mark itself is invisible in the simulation (no cursor, no message, no target line); `WithHoldingFireDecoration` (render-only, reads `AutoTarget.LastHeldFireTick`, writes nothing) is what surfaces it.
- **Detection gates BOTH attack paths, so "auto dead / manual alive" is the wrong mental model.** An undetected actor stays clickable, but `Activities/Attack.cs:147` sets `useLastVisibleTarget = targetIsHiddenActor || !target.IsValidFor(self)` and `:164` then returns true — ending the activity — when that last-visible target is invalid. **`forceAttack` does not appear anywhere in that path**, and `AttackBase.AttackTarget` (`:657-674`) carries no visibility gate of its own, so a manual order on an undetected actor is accepted and then quietly does nothing. Visibility itself is strictly-greater (`Traits/Player/MapLayers.cs:579`, `ResolvedVisibility[puv] > visibility`) with shadow subtracted and floored at 1 (`:371-374`). Note `Map.ForestGroundShadow` became **superlinear above a knee** (`ForestShadowKneeDensity = 20`, `Map.cs:1102-1120`), so any extrapolation of tree-blinding past density 20 understates it.
- **A blocked airborne LOS deadlocks both attack paths, and this defect is LIVE.** `MoveWithinRange.ShouldStop` has **no LOS term** — it is `AtCorrectRange && CanInteractWithGroundLayer && CanStayInCell` (`MoveWithinRange.cs:38-43`), where `AtCorrectRange` is purely a distance test (`:73-76`). But `Attack.cs:269-272` folds `losBlocked` into `needsToMove` and `:296` queues a `MoveWithinRange` to fix it. A unit already at the correct range with blocked line of sight therefore queues a move that completes instantly having gone nowhere, and re-queues it forever: **the LOS term that created the need is invisible to the activity meant to satisfy it.** No guard has been added. Per-weapon gate is `Armament.cs:364` (`FiringLOS.HasClearLOS(self, target, Weapon.ClearSightThreshold)`, default `5`, `GameRules/WeaponInfo.cs:146`); the auto-path reject is `AutoTarget.cs:1357-1366`. Recall short-range immunity: `FiringLOS` returns true unconditionally inside two cells (above), so this can only bite at range.
- **`Player.RelationshipWith` returns `Ally` for ANY spectating player — so a defeated player reads as an ally the instant they lose.** `Player.cs:253-255`: *"Observers are considered allies to active combatants"* — `if (other == null || other.Spectating) return NonCombatant ? Neutral : Ally;`, checked **before** the alliance mask at `:257`. Since a `Lost` player is immediately `Spectating`, any loop that mutates `WinState` while its own team-membership test *reads* `WinState` through `RelationshipWith`/`IsAlliedWith` will progressively mis-classify everyone it has already processed — the mechanism behind "destroying one bot's Supply Route defeated every player slotted after it". **Snapshot team membership before the first mutation, and test membership with alliance masks (`SameTeam`), which are immune to `Spectating`.**
- **A passenger reserving space SILENTLY CANCELS the transport's whole activity queue — including a human player's shift-queue.** `Passenger.Reserve` → `Cargo.ReserveSpace` (`Cargo.cs:371-396`) calls `LockForPickup` (`:393`), which sets `state = Locked` and then calls **`self.CancelActivity()` on the transport** (`:412-419`). So a unit deciding to board wipes whatever the transport was doing or had queued, with no order issued by anyone and nothing in the log. This is the mechanism to suspect when a carrier abandons a queued route the moment infantry are told to board — and it is why "order the passengers, then queue the carrier's move in the same pass" is unsafe in both directions (see the bot-boarding rule at the end of this list).
- **`Move` and `ForceMove` are TWO order strings in this fork, and `ForceMove` bypasses every `IWrapMove` wrapper.** Stock OpenRA emits one `"Move"` order for both gestures; WW3MOD emits `mot.IsForceMove ? "ForceMove" : "Move"` (`Mobile.cs:1002`). `ResolveOrder` then treats them deliberately differently: `"Move"` is queued as `WrapMove(new Move(...))` (`:1021`), so every `IWrapMove` trait gets to interpose — `SmartMoveActivity` among them — while `"ForceMove"` queues a bare `Move` (`:1031-1033`, comment *"Force-move bypasses WrapMove — pure movement, no SmartMove wrapping"*, and additionally `NoReverse = true`). **So "the unit ignores plain Move but obeys Force-Move" is a precise diagnostic signature: the fault is in a move *wrapper*, not in the pathfinder, the locomotor or the order.** Anything that pins a wrapper pins ordinary movement while leaving force-move working, and an errand issued through `Mobile.MoveWithinRange` is wrapped too — so its target line can be drawn by an activity whose movement never runs.
- **`Activity.ActivitiesImplementing<T>()` is NOT "the current activity" — it descends into `ChildActivity` AND walks `NextActivity`** (`Activity.cs:286-304`). So guarding anything with `CurrentActivity.ActivitiesImplementing<IAttackActivity>()` also matches an autotarget attack nested *under* a player Move (`SmartMoveActivity` queues one as a child) — and acting on that match with `Actor.CancelActivity` cancels the **whole** top-level activity, silently destroying the player's move order. Read the top-level `self.CurrentActivity` type instead when you mean "what is this unit doing right now".
- **Ending a unit's attack activity does NOT mean it stays idle — `AutoTarget` hands it straight back.** `ScanOnIdle` defaults true (`AutoTarget.cs:65`), so the tick after an attack activity ends an idle unit rescans and queues a fresh attack. Crucially `ChooseTarget` calls the same ammo-blind `ChooseArmamentsForTarget` (`:1336`, `:1530`), so **a unit with zero ammo re-acquires perfectly well** — it is not passively ignored by the targeting layer, it actively signs up for fights. What actually stops the loop is a range coincidence: `ChooseTarget` filters armaments to those *already in range* whenever `allowMove` is false, which it is below `Hunt`, so a unit that halts **outside** its own weapon range finds no candidate and rests, while one sitting inside weapon range of a visible enemy cycles — queue attack, guard ends it, go idle, re-queue. The cycle is throttled to one pass per scan interval (16–32 ticks for WW3MOD infantry, `infantry.yaml:289-290`), not one per tick, and it cannot race the resupply it dispatches: `Actor.Tick`'s two arms are mutually exclusive (`Actor.cs:287-302`), so the tick that dispatches an errand is never the tick that re-issues an attack. Anything gating on `IsIdle` should expect it to **alternate** rather than latch for such a unit. Closing this properly belongs in `AutoTarget` — teaching the scan not to acquire for a unit that cannot fire — not in another guard in the activities.
- **Becoming idle CONSUMES `SharedRandom` — so a change to *whether* a unit idles is a determinism change, not only a behaviour change.** Idle is not a quiet state. `WithInfantryBody.TickIdle` draws **twice** per `Waiting → Idle` transition — `IdleSequences.Random(SharedRandom)` and `SharedRandom.Next(MinIdleDelay, MaxIdleDelay)` (`Render/WithInfantryBody.cs:206-207`) — gated on `IdleSequences.Length > 0`, which 12 soldier classes declare in `infantry.yaml`. That state **re-arms itself**: `Tick` calls `PlayStandAnimation`, which sets `state = Waiting` (`:128`, called from `:192`), whenever a unit in `Idle`/`IdleAnimating` becomes non-idle — so every idle→busy→idle cycle buys a fresh pair of draws, and a permanently idle soldier keeps drawing through the `Idle → IdleAnimating → PlayStandAnimation → Waiting` animation loop. `AutoTarget.ScanForTarget` draws once per scan to re-arm `nextScanTime` (`AutoTarget.cs:1087`). (`TurnOnIdle` draws too, but no ww3mod rule uses it.) Because `SharedRandom` is one synced stream folded into the sync hash, each draw shifts stream position for **every** later consumer in the match — the behavioural change is local, the RNG consequence is global. Practical consequence: any fix that lets units reach idle where they previously never did (releasing a stuck unit from an activity, say) invalidates tick-for-tick comparison against an older `@stable` baseline even where the tactical outcome is identical. **Re-take the baseline; do not diff replays across it.** See the `World.SharedRandom` rule above and the `Actor.IsIdle` rule below.
- **`IHitShape.CenterProximityPercent` is measured from the CENTRE, and only two of the four shapes return a percentage at all — so giving an actor a `Capsule` or `Polygon` hitshape silently breaks `TargetDamageWarhead`.** The method (renamed from the actively misleading `PercentFromEdge`) is consumed at exactly one site, as a direct percentage damage modifier: `TargetDamageWarhead.cs:83`. `Circle` (`HitShapes/Circle.cs:54`) is the only implementation the old name described — for a circle, percent-in-from-the-centre and percent-in-from-the-edge are the same number. `Rectangle` (`Rectangle.cs:123`) normalises against the half-**diagonal** (centre-to-corner) whichever direction the impact came from, so **only the four corners read 0**: on the Abrams shape (`vehicles-america.yaml:491-495`, `TopLeft: -365, -790` / `BottomRight: 365, 790`) dead centre is 100, mid-flank 58, nose-on 9 — a 6.4× swing that is an accidental armour-facing effect of hull aspect ratio, unrelated to `ArmorDirection`. `Capsule` (`Capsule.cs:92`) and `Polygon` (`Polygon.cs:110`) are verbatim copies of their own `DistanceFromEdge` with the `WDist` wrapper stripped: they return a raw world-unit distance with the **opposite sense** — 0 anywhere inside the shape — so a dead-centre hit deals **0** damage while a graze outside is handed a modifier in the hundreds. Both carry explanatory comments and are left as-is deliberately (correcting them is a balance change). **Exposure today is nil, which is what makes it dangerous:** every `Type: Capsule` block in `mods/ww3mod/` is commented out (`rules/ingame/naval.yaml`) and there is no `Type: Polygon` anywhere, so the first actor given one becomes immune to every `TargetDamageWarhead` in the game with no error and no log line. Working: [`WORKSPACE/audit/hitshape-percent-semantics.md`](../../WORKSPACE/audit/hitshape-percent-semantics.md).
- **Position-bin queries (`FindActorsInCircle`/`ActorsInBox`, and the Lua `Map.ActorsInCircle`/`ActorsInBox`) return NOTHING until the first world tick — a `WorldLoaded` query reports an empty world.** `World.FindActorsInCircle` (`WorldUtils.cs:79-85`) resolves to `ActorMap.ActorsInBox` (`ActorMap.cs:649`), which reads the position bins; `ActorMap.AddPosition` only queues into `addActorPosition` (`:593-596`) and the bins are filled in `TickFunction` (`:495-507`), invoked from `ITick.Tick` (`:473-476`) — i.e. after `WorldLoaded` has returned. The call is correct, the arguments are correct, there is no error, and the answer is wrong. **`ActorMap.GetActorsAt` is cell-keyed off the influence layers and updated on add, so it does NOT share this.** The dangerous shape is not the assertion that fails loudly but ordinary setup code — "find the units near X at load and put them on HoldFire" sets nothing, throws nothing, and the scenario runs to a confident verdict against a world that was never built. **When setup is driven by a query, assert the query returned something before acting on it**; an empty lookup must never be allowed to mean "nothing to do".
- **Resolving the Neutral player by `InternalName` is a silent-failure pattern — the world owner is guaranteed structurally, the name is not.** `CreateMapPlayers` throws at world creation unless some `PlayerReference` carries `OwnsWorld: True` (`CreateMapPlayers.cs:98-106`) and parks that player on `WorldActor.Owner` via `World.SetWorldOwner` (`World.cs:372-375`), so **`world.WorldActor.Owner` is non-null on every map that loads at all**, whatever the author named the player. Every shipped WW3MOD map happens to name it `Neutral`, which is precisely why the weakness is invisible in testing — it only bites on a hand-authored or third-party map. Both failure modes are bad in different ways: `FirstOrDefault(p => p.InternalName == "Neutral")` returns null and the feature quietly does nothing (`GarrisonManager.cs:226`, `HeliEmergencyLanding.cs:354`, both left alone because they degrade to a no-op), while `First(...)` throws an unhandled `InvalidOperationException` mid-match (`OwnerLostAction.cs:52`, whose `Owner` defaults to `"Neutral"`). **Prefer `WorldActor.Owner` to either** — `CaptureActor.cs:123` records the reasoning inline.
- **Eluant does not marshal Lua numbers to `float`.** A script-binding parameter typed `float` fails at call time with `Unable to convert parameter 0 to Single`; use `double` or `int` and cast inside (`Scripting/Global/TestGlobal.cs:104`, `public double SetZoom(double scale)`).
- **Ordering a bot passenger to board while queuing the carrier's Move in the SAME pass flies the transport EMPTY.** The `EnterTransport` orders land on the *infantry's* activity queues, but a queued `Move` on the *carrier's* own (empty, idle) queue starts IMMEDIATELY — so the carrier departs before any soldier boards. The engine gives no boarding-complete callback; boarding "completes" only when `Cargo.Load` fires, observable only by polling `Cargo.PassengerCount`. The correct shape (used by `MountedTransportBotModule` and now `HelicopterSquadBotModule.TryLaunchTransportMission`): stage a `Loading` task, dispatch the delivery only once `PassengerCount >= min` (or a partial on timeout), abort to the idle pool if nobody boarded — and queue the carrier's RETURN move right behind the `Unload` so it doesn't idle at the drop (a dedicated transport is free-pool-excluded, so nothing else re-collects it — see architecture.md §"The bot free pool self-heals").
