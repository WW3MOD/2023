# Coding Conventions — read before editing YAML or engine C#

## WDist notation

OpenRA uses `WDist` (World Distance) units throughout. Notation `NcXXX`:

- `1c0` = 1 cell = 1024 WDist units
- `1c512` = 1.5 cells (1024 + 512)
- `3c768` = 3.75 cells
- Plain `512` = 512 WDist units (half a cell)

## WAngle facing — counterclockwise (opposite of typical conventions!)

`WAngle` facings rotate **counterclockwise**, 0–1024 range. Easy to get wrong.

| WAngle | Direction | Screen (top-down) |
|--------|-----------|-------------------|
| 0      | North     | Up                |
| 256    | **West**  | **Left**          |
| 512    | South     | Down              |
| 768    | **East**  | **Right**         |

Map placement: units on the LEFT facing right → `Facing: 768` (East); on the RIGHT facing left → `Facing: 256` (West). Conversion: `WAngle.FromFacing(old)` where old RA facing × 4 = WAngle.

**Converting a bearing back to a cell step:** `WVec.FromSpeedAndAngle(speed, angle)` (`WVec.cs:94`) is the exact inverse of `WVec.Yaw` (`WVec.cs:66`). To turn a bearing `WAngle` (e.g. one built from a cell-space `WVec(dx,dy).Yaw`) back into a cell-space step, use `FromSpeedAndAngle` and take `Sign(X)/Sign(Y)` — it respects the "north = −Y" + counterclockwise convention automatically, avoiding hand-rolled `Cos()/Sin()` sign errors.

**A `RateOfTurn`-style field in YAML is a raw `WAngle`, not a facing — and this has now been mis-read three separate times.** `new WAngle(20)` is 20 raw units; consumers read `.Facing`, which is `Angle / 4` (`WAngle.cs:67`). So `HorizontalRateOfTurn: 20` (`Missile.cs:99`) means **5 facings/tick ≈ 7.03°/tick**, not 20 of anything a reader would guess. **Grep the consumer for `.Facing`, `>> 2` or `(sbyte)` before trusting any raw angle you see in YAML** — `WAngle`'s own `[0, 1023]` normalisation guarantees nothing about the range or units the *consumer* accepts. (Worked case in [`missiles.md`](missiles.md) §4: a field the engine re-decodes through `(sbyte)(Angle >> 2)` has a usable range of `[0, 511]`, and `Missile` decodes that one field three different ways.)

**`Mobile.Speed` in YAML is not the speed at the point of use.** `MovementSpeedForCell` appends the locomotor's per-terrain percentage to the modifier list before applying it (`Mobile.cs:826-831`), so a `lightwheeled` unit crossing `Clear` moves at **70%** of its declared figure (`world.yaml:98-101`) — a humvee's `Speed: 150` (`vehicles-america.yaml:70`) is 105 wdist/tick on open ground and only hits 150 on `Road`/`Bridge` at 100. Any timing or intercept arithmetic taken from the YAML number alone is ~30% optimistic over most of the map.

## YAML

### Templates (prefixed with ^)

```yaml
^Aircraft:          # Base template for fixed-wing planes
^Helicopter:        # Base template for helicopters
^Drone:             # Base template for drones
^Airborne:          # Common airborne traits
^NeutralAirborne:   # Airborne without faction-specific traits
^AirRadar:          # Radar trait for aircraft (range 24c0)
```

### Conditions system

**A condition variable resolves to its STACK DEPTH, so a band selector needs no engine code.** `Actor.UpdateConditionState` assigns `conditionCache[condition] = conditionState.Tokens.Count` (`Actor.cs:696`), and `VariableExpression` (`engine/OpenRA.Game/Support/VariableExpression.cs:131-136`) implements the full set of comparison operators against those variables. **So any trait that grants one token per unit of something exposes a countable quantity to YAML for free.** `AmmoPool` already does exactly this — one token pushed per remaining round, popped on spend (`AmmoPool.cs:817-821`) — which is what makes `RequiresCondition: ammo-primary == 2` on the Iskander's missile overlay (`vehicles-russia.yaml:1041`) work; `ammo-primary >= 6 && ammo-primary <= 10` is equally valid and needs no C#.

**Before adding a `FooHigh`/`FooMedium`/`FooLow` condition triple to a trait, grant one stacking token instead and let the YAML compare.** The thresholds then live with the actor that cares rather than baked into the C# field list. `SupplyProvider` had the triple (`:90`, `:94`, `:98`, each granted at most once) and could not express eighths; it now also offers `SupplyLevelCondition`/`SupplyLevelSteps` (`:109`, `:113`), defaulting to null/0 so no existing actor changes. **Note the operators require surrounding whitespace** — `ammo-primary>=6` throws *"Missing whitespace at index N"* (`VariableExpression.cs:532`, `:538`), a genuine exception rather than a silent false.

Traits grant and consume named conditions:

```yaml
GrantConditionOnDamageState:
    Condition: heavy-damage-attained    # Granted at heavy damage
SpeedMultiplier@HeavyDamage:
    Modifier: 90
    RequiresCondition: heavy-damage-attained
```

Common conditions: `airborne`, `cruising`, `moving`, `empdisable`, `dronedisable`, `heavy-damage-attained`, `critical-damage`, `rank-veteran`, `suppression-*`, `unit.docked`

**A consumed-but-ungranted condition is a `make test` ERROR (not a warning).** `ConditionalTraitInfo.RequiresCondition` is `[ConsumedConditionReference]` (`ConditionalTrait.cs:21`), so a trait gated on `foo || bar` marks BOTH names *consumed on that actor*. `CheckConditions` (`Lint/CheckConditions.cs:73-75`) calls `emitError` — which fails `make test` — for any condition an actor consumes but nothing grants. (The reverse, granted-but-unconsumed, is only a `emitWarning`, `:70-71`.) To make a name grantable-but-not-yet-fired (e.g. a seam for later Lua/warhead activation) without a live grant, declare an `ExternalCondition` whose `Condition` field is `[GrantedConditionReference]` (`Conditions/ExternalCondition.cs`) — it satisfies the lint at zero runtime cost and a later `GrantCondition("name")` resolves to it.

**The Fluent lint is bidirectional, and the unused-key half is a WARNING that rots.** `CheckFluentReferences` checks referenced-but-undefined (an error) *and* defined-but-unreferenced (`CheckUnusedKey`, `Lint/CheckFluentReferences.cs:447-455`, `emitWarning`), reached for every key of every non-external file — and a file under `mods/ww3mod/` is not external. Unused keys therefore only fail the run under `TREAT_WARNINGS_AS_ERRORS=true` (`UtilityCommands/CheckYaml.cs:51`), and they arrive in a pile nobody reads to the end. That is how the entire server/lobby notification block in `mods/ww3mod/languages/en.ftl` — 38 keys from `timeout-in` (`:84`) through `chat-temp-disabled` (`:129`) — came to be **dead**: not one of those bare names appears as a string literal anywhere in `engine/OpenRA.Game/` or `engine/OpenRA.Mods.Common/`, because the `[FluentReference]` consts name the `notification-`-prefixed forms that live in `engine/mods/common/fluent/common.ftl` (30 of the 38 have such a twin; the other 8 were renamed *and* reworded upstream). Editing the ww3mod copies changes nothing any player sees. **Treat a large standing warning count as the defect it is** — this one had a real bug hiding in it.

**Grants scoped to the actor:** `GrantConditionOnBotOwner` grants only on the actor it sits on, checking `self.Owner.IsBot && Bots.Contains(self.Owner.BotType)` (`Conditions/GrantConditionOnBotOwner.cs:46`). A **unit** trait's `RequiresCondition` sees only conditions granted on that *unit*, so gating a unit trait to bot-only needs a per-unit `GrantConditionOnBotOwner` on the unit template — a Player-actor grant (e.g. the `enable-ai-experimental` grants in `ai.yaml`) does nothing for a unit trait.

### Faction-specific files

Each unit type has a base template file and two faction files:

- `aircraft.yaml` → `aircraft-america.yaml` + `aircraft-russia.yaml`
- `infantry.yaml` → `infantry-america.yaml` + `infantry-russia.yaml`
- `vehicles-america.yaml` + `vehicles-russia.yaml`

A unit type is defined in three tiers: an abstract template `^E6` and a bare concrete `E6:` (`Inherits: ^E6`) live in the base file (`infantry.yaml`); the buildable faction variants `E6.america:` / `E6.russia:` (each `Inherits: ^E6`, adding `Buildable`/`RenderSprites`) live in the faction file (`infantry-america.yaml:95`, etc.). Keys are declared uppercase but actor lookup is case-insensitive. **To annotate every variant at once, override the `^Template`** — a trait added to `^E6` reaches the bare concrete and both faction variants in one line; single-hull tweaks (`bradley`, `bmp2`) go on the concrete key.

This is also the reliable way to add a trait from **map/test `rules.yaml`**: override a `^Template` (e.g. `^Combatant`) or a bare hull key (`t90`, `bradley`), as `demo-wgm-suite/rules.yaml` does. Overriding a **faction-suffixed** concrete key (`ar.america`) from map rules has been observed to throw `LoadFromManifest<Rules>, duplicate values found for the following keys: ar.america: [ActorInfo,ActorInfo]` at load — prefer the template.

### Weapon `ValidTargets`: `Air` ⊃ `Helicopter` (the two are NOT disjoint)

**An airborne helicopter carries BOTH `Air` and `Helicopter`.** `^Helicopter` inherits `^Airborne` → `^NeutralAirborne`, whose `Targetable@Airborne` grants `Air, AirDetonateAttack` while the `airborne` condition holds (`rules/ingame/aircraft.yaml:42-44`), and `^Helicopter` adds its own *unconditional* `Targetable@Helicopter: Helicopter` (`:178-179`). Nothing in `rules/` removes `Targetable@Airborne`. A **landed** helicopter is `Ground, Vehicle` + `Helicopter` and is no longer `Air`; a fixed-wing aircraft is only ever `Air`. So:

- `Helicopter` is the **heli-only** selector — it is how a weapon engages helicopters *without* being able to touch fixed-wing.
- `Air` **sweeps both** helicopters and planes (while airborne).

That asymmetry is the design: ground autocannons and MGs list `Helicopter` and so can shoot helis without becoming air-defence — `^7.62mm` is `Infantry, Unarmored, Helicopter` (`weapons/weapons-ballistics.yaml:144`), `^12.7mm` adds `Light` (`:343`), and even Tunguska's dedicated `30mm.Tunguska.AA` autocannon is `ValidTargets: Helicopter` (`:662`), so it cannot engage a jet. Guided SAMs list `Air`: `MANPAD`/`Stinger`/`Stinger.quad`/`9M311` (`weapons/weapons-missiles.yaml:481,529,565,599`; `9M311 Inherits: Stinger`), which is how Tunguska gains true air-defence — via its `9M311` missile (`vehicles-russia.yaml:860`), not its gun. An "is this an air-defence weapon?" test must therefore key on the literal `Air` target type; keying on `Helicopter` sweeps in every MG-armed vehicle.

**Consequence for `CreateEffect` warheads:** an air-impact effect wants `ValidTargets: Air` alone. Writing `Air, Helicopter` also matches a *landed* helicopter, which the template's ordinary `Ground` warhead already covers — so the impact draws two explosions stacked on one hit. Note also that an in-flight ballistic missile (`^ShootableMissile`, `rules/defaults.yaml:952`) is `ICBM` and **not** `Air`, and that one unlisted target type on the victim suppresses the whole effect rather than degrading it (`CreateEffectWarhead.DoImpact` early-returns on `ImpactActorType.Invalid`, `:124-125`).

**The suppression is caused by BYSTANDERS, not only by the intended victim — an actor with a `HitShape` and no enabled `Targetable` swallows the explosion and the sound of any shell landing on it.** `ActorTypeAtImpact` (`CreateEffectWarhead.cs:67-96`) walks `FindActorsOnCircle(pos, WDist.Zero)` and, for every actor whose hitshape contains the impact point, sets `anyInvalidActor = true` unless the warhead `IsValidAgainst` it (`:89-92`) — and `IsValidAgainst` fails immediately when `GetEnabledTargetTypes()` is empty (`:107`). One such actor is enough: the method returns `Invalid` and `DoImpact` returns before the sprite and before `Game.Sound.Play` (`:155`). Because `^1x1Shape` spans a whole cell, an untargetable full-cell actor silences *every* shell in its cell. **Damage is unaffected** — `CreateEffectWarhead` and `WarheadAS.IsValidImpact` (`WarheadAS.cs:75-85`) are the only two sites carrying this early-out; `DamageWarhead.DoImpact` has no position-level gate. So "the shell did nothing" and "the shell did damage but looked and sounded like nothing" are different defects. Since `db01b0ae` both sites skip cosmetic ground cover (`victim.IsGroundCover()`, `CreateEffectWarhead.cs:82`, `WarheadAS.cs:48`), which is what un-silenced shells landing on `^CivField`; any *other* untargetable-but-hitshaped actor still swallows them.

### An armour class is a TARGET TYPE, so a weapon can reach a victim by a channel neither of them names

`Targetable` decides whether a shot is **legal**; `Armor` decides what it **does on arrival**. They are independent axes — `DamageWarhead.DamageVersus` resolves `Versus:` multipliers from the victim's `Armor` trait only (`Warheads/DamageWarhead.cs:104-106`, `victim.TraitsImplementing<Armor>()` filtered by `a.Info.Type`) and never consults target types. But the *class name* appears on both axes, and an actor that advertises its armour class as a target type becomes reachable by every weapon that lists that class.

**Aircraft and ground vehicles carry the class in structurally different places, which is why this went unnoticed for months.** A vehicle folds it into its always-on ground targetable — `TargetTypes: Ground, Vehicle, Light` (`vehicles-america.yaml:62`) — which is correct, because a vehicle is never airborne. Aircraft split it into a separate `Targetable@Armor`, and while `^NeutralAirborne` gates its other three targetables carefully (`aircraft.yaml:39-47`: `Targetable@Ground` on `!airborne`, `Targetable@Airborne` on `airborne`, `Targetable@REPAIR` on `!airborne && damaged`), the per-airframe armour entry was the one nobody gated. Until `15b6201a` every airframe therefore announced its armour class **in flight**, and `GrenadeLauncher` — `ValidTargets: Infantry, Unarmored, Light` (`weapons-ballistics.yaml:451`), naming neither `Air` nor `Helicopter` — could shoot a hovering littlebird out of the sky through `Light`.

**Rule: any `Targetable` on an actor that has an `airborne` condition must be gated on it.** All 10 `Targetable@Armor` declarations now carry `RequiresCondition: !airborne`, pinned by `AirborneArmorTargetableTest.EveryArmorClassTargetableIsGroundOnly`, which parses the three aircraft rules files from disk rather than a hardcoded roster — so a new airframe **in those files** is caught automatically (one added to a fourth rules file would not be). Note 10 is the count of *declarations*; there are 12 airframe actors, `A10.Airstrike` and `FROG.Airstrike` inheriting the gate from their parents.

**The two deliberate ungated entries must stay ungated:** `Targetable@Helicopter` on `^Helicopter` (`aircraft.yaml:178-179`) and `Targetable@Drone` on `^Drone` (`:336-337`). They are the designed channels by which small arms and `DroneJammer` engage rotorcraft and drones — not the same defect. Verified safe by building the full weapon×airframe reachability matrix from the parsed corpus: **every AA weapon in the mod reaches air via `Air` or `Helicopter`, none via an armour class**, so the gate disarms nothing.

### `InvalidTargets` beats `ValidTargets`, so an armour class can silently cancel a declared capability

`WeaponInfo.IsValidTarget` is `ValidTargets.Overlaps(t) && !InvalidTargets.Overlaps(t)` (`engine/OpenRA.Game/GameRules/WeaponInfo.cs:218`) — **the exclusion wins.** `^5.56mm` declares `ValidTargets: Infantry, Vehicle, Helicopter` (`weapons-ballistics.yaml:83`) with `InvalidTargets: Light, Medium, Heavy` (`:84`), plainly intending "rifles hit helicopters but not armour". Every helicopter in the mod is `Light` or `Heavy` — the six are TRAN, littlebird, HALO (Light) and HELI, HIND, MI28 (Heavy); **none is Medium** — so while the armour class leaked, the exclusion tripped on every one of them and the rifle's declared anti-helicopter capability was **100% dead**. `^9mm`, `^7.62mm` and `^12.7mm` name `Helicopter` without excluding armour and worked fine, making assault rifles the only small arm in the game that could not shoot a helicopter.

**When a weapon both grants a capability in `ValidTargets` and excludes an armour class in `InvalidTargets`, check that no target of that capability advertises the excluded class.** The grant fails silently: there is no lint for a `ValidTargets` entry that can never match. See also [§A change believed made, documented as made, and inert](#a-change-believed-made-documented-as-made-and-inert) — this is one of its worked instances.

### A duplicate trait key inside ONE actor: LAST value wins, at the FIRST key's position

**Scope first, because the rule inverts.** What follows holds while **one source** declares the actor. The moment a *second* source names it — a map's `rules.yaml`, or another mod rules file — the merge inspects the accumulated child list and a duplicate key becomes an `ArgumentException` **at rules load** (`MergePartial` → `IntoDictionaryWithConflictLog`, `MiniYaml.cs:522-529` → `Exts.cs:484-491`; that helper throws, despite the name). A shipped duplicate is therefore not "inert" — it is a latent load error armed against anyone who overrides the actor, and since overriding a `^Template` from map rules is the recommended idiom (below), a duplicate inside a template is the sharpest form. `^CivField` carries one today. Details and a no-build reproduction: `WORKSPACE/DISCOVERIES.md` 2026-08-17. With a single source:

Two same-named trait nodes inside a single actor do **not** produce two traits and do **not** throw. `ResolveInherits` hands each child to `MergeIntoResolved` (`engine/OpenRA.Game/MiniYaml.cs:427-447`), which on a repeat key finds the earlier node's index and writes `existingNodes[existingNodeIndex] = existingNode.WithValue(MergePartial(...))` (`:444`). So the survivor **keeps the FIRST occurrence's position in the node list but takes the LAST occurrence's field values** — and the merge is per-field, so a later block that sets only *some* fields overrides only those and inherits the rest from the earlier one. (`MergeSelfPartial`, `:497`, is a *different* function that de-dupes only **top-level** keys per source and never sees this case.)

**The blast radius is bigger than a wrong number: the dead block is invisible to every reader AND to `make test`.** The YAML lint does not flag duplicate child keys, so an actor can carry a plausible-looking stat the engine has never used, indefinitely. Any balance pass that reads top-down and stops at the first `Health:` tunes a value with no effect. (Real instance: `tunguska` declared `HP: 14000` and then `HP: 8000` thirteen lines later, and the actor fielded **8000**.)

- **`./utility.sh --resolved-rules <actor>` settles "which value wins" in one command** (`UtilityCommands/OutputResolvedRulesCommand.cs`) — it needs only a successful build, launches no match, and so is not gated by the no-autonomous-test-runs rule. Actor names are **case-sensitive** here even though actor lookup elsewhere is not — and the key it matches is the **YAML key verbatim**, not the lowercased ruleset key: `humvee` resolves, `mi28` returns *"Could not find actor"*, `MI28` resolves. Copy the key as written in the rules file. **Use it rather than hand-rolling a resolver for bulk "which actors carry trait X" sweeps.** A two-stage script (merge each actor across rule files, then apply `Inherits:`) must carry `-Trait:` nodes *through* the merge stage; the natural implementation applies each removal as it merges, where the definition table is still empty, so the node matches nothing and is then not carried forward. The removal vanishes and every descendant reports the trait as present — silently, and in the **over**-reporting direction. That is how `^CivBuilding`'s five `-Capturable*`/`-CaptureManager` lines (`civilian.yaml:6-10`) disappeared from a sweep. If a script is unavoidable, cross-check it against the utility on at least one actor with an explicit removal.
- **Technique worth reusing for any "clean up this YAML without changing behaviour" task:** capture `--resolved-rules <actor>` before and after and `diff`. Identical output is a byte-exact proof of behaviour-neutrality across the *whole* actor — inheritance, `-Removals`, faction variants and all — far stronger than eyeballing the edited lines, and it catches the blank-line/adjacent-entry merge accident below as a side effect.
- **Corollary when de-duplicating: preserving the resolved value is NOT the same as keeping the block you would expect.** Because the survivor sits at the *first* position but carries the *last* values, the behaviour-neutral edit is "keep the earlier block's slot, write the later block's values into it, delete the later block". Deleting the *first* block also preserves behaviour but silently relocates the trait in the file. **Deleting the second block while keeping the first block's values is the one option that changes behaviour — and it is the one that looks most obviously correct.**

### `Versus`: an OMITTED armor class is FULL damage, the opposite of a zero

`DamageWarhead.DamageVersus` (`Warheads/DamageWarhead.cs:96-110`) starts at `damage = 100`. An **empty** `Versus` early-returns that full damage (`:101-102`). A **non-empty** one filters the victim's armors to the classes it *lists* — `Versus.ContainsKey(a.Info.Type)` (`:105`) — so an **unlisted** class matches nothing, `ApplyPercentageModifiers` runs over an empty sequence, and the victim takes the unmodified **100%**. **A table that zeroes six classes and omits a seventh is a full-damage weapon against the seventh, not a weak one.**

WW3MOD's armor population is exactly nine: `Concrete, Heavy, Indestructable, Kevlar, Light, Medium, None, Unarmored, Wood`. Two traps follow from that list:

- **`Kevlar` is `^Soldier`'s armor** (`infantry.yaml:173-174`) and reaches essentially the whole combat-infantry roster by inheritance, while non-`^Soldier` actors keep `^Infantry`'s `Type: None` (`:34-35`). So a `Versus` table that zeroes `None` but omits `Kevlar` is harmless to a civilian and **lethal at full damage to every soldier** — selective in exactly the way that survives eyeballing.
- **Writing a class name that does not exist is silently a no-op.** A shipped table zeroing `Brick` accomplishes nothing, because `Brick` is not an armor class in this mod.

**So any "this weapon cannot hurt anything" judgement must be made against the ruleset's armor population, never against the table alone** — and three further shapes make such a judgement unprovable outright, because each ends at the same empty filter and therefore **fails open to full damage**: a null `ArmorInfo.Type`, a **conditional** `Armor` (it is a `ConditionalTraitInfo`, so it can be absent at runtime, and the filter also drops `IsTraitDisabled`), and a non-empty `HitShapeInfo.ArmorTypes` that excludes the class. `DangerFieldLayer.RulesetArmorTypes`/`WarheadIsHarmless` implement this test and fail open on all three; they are NUnit-pinned in `DangerFieldKernelTest`.

### Weapons live under `Weapons:`, and a warhead override REPLACES rather than merges

Two authoring traps that both end in a confident wrong answer rather than an error.

**A map's weapon overrides belong in the file named by `Weapons:` in `map.yaml`, never `Rules:`.** They are separate manifest keys (`Map.cs:180` maps `Weapons` to `WeaponDefinitions`, distinct from `RuleDefinitions`). Put a weapon block in the rules file and the loader reads the weapon name as an **actor** and its `Warhead@…` children as **traits**, producing `Cannot locate type: WarheadInfo` — an error naming neither the file nor the weapon. The game then never reaches the Lua, no verdict is written, and the runner reports a **timeout rather than a rules error**. *Check `debug.log` for "Failed to load rules" before treating a hang as a hang.*

**`Inaccuracy` is a field of the `Projectile:` SUB-BLOCK, not of the weapon** — it is declared on `BulletInfo` (`Projectiles/Bullet.cs:31`), and `WeaponInfo` has no such field. Writing it as a direct child of the weapon leaves the resolved value at whatever the parent projectile block set. **Re-opening the sub-block MERGES with the inherited parent rather than replacing it** — `MiniYaml.cs:538` recurses into the children (`MergePartial`), so `Speed`, `Image` and the rest survive alongside the new value, confirmed in a resolved dump. *(This is stated deliberately against the warhead paragraph below, which describes the opposite behaviour for `Warhead@…` nodes. The two are not obviously reconcilable and the discrepancy has not been run to ground — if you are overriding either kind of sub-block, verify with a resolved dump rather than trusting either sentence.)*

> **Do not repeat the 2026-08-21 claim that a misplaced weapon field is silent.** It is not: `CheckUnknownWeaponFields` walks every file in `Manifest.Weapons` and emits *"refers to a weapon field `X` that does not exist"* for any weapon-level child that is not a `WeaponInfo` field, `Projectile`, `Warhead` or `Inherits` (`Lint/CheckUnknownWeaponFields.cs:107-108`), and `mods/ww3mod/lint-baseline.txt` records no such waiver. The misplacement is a hard `--check-yaml` error.

**The countermeasure for "did my override actually take?" is the resolved dump, not care.** `./tools/combat-sim/scripts/dump-stats.sh` runs `--dump-balance-json` off `utility.ModData.DefaultRules` (`DumpBalanceJsonCommand.cs:41`) — i.e. post-inheritance — into `tools/combat-sim/data/stats.json` with lowercased keys. It is the only artefact that can tell you a value landed. The tell that one did *not*: the regenerated file is **byte-identical** to the previous one. (Check `_meta.generated_at` before trusting a committed copy; it is routinely stale.) `./utility.sh --resolved-rules <actor>` is the equivalent for traits.

**When overriding an existing warhead, restate its TYPE and every field the consumer reads.** `WeaponInfo.LoadWarheads` (`GameRules/WeaponInfo.cs:200-206`) builds each warhead with `Game.CreateObject<IWarhead>(node.Value.Value + "Warhead")` — **the node's *value* names the type**, so `Warhead@Spread:` written bare resolves `"Warhead"` and fails; write `Warhead@Spread: SpreadDamage`. And because the object is constructed fresh and `FieldLoader` fills only the fields present, **every omitted field falls back to the ENGINE default, not to the mod's value.** This is the opposite of the trait path, which merges per-field (see the duplicate-trait-key section above). The worked example: an override that restated only `Damage` and omitted `Penetration: 15` silently got the engine's `Penetration = 1` (`Warheads/DamageWarhead.cs:24`), which against a `Thickness: 10` target took the reduction branch and cut the intended effect by an order of magnitude — **and the scenario still completed and reported `pass`**, returning a confident number about a world that was never built.

### Blank lines are significant

Templates and top-level entries must be separated by a blank line. The MiniYaml parser silently merges adjacent ones, producing confusing override behavior — not a parse error. If a template "isn't taking effect," check the blank lines first.

### Removing an inherited trait: `-Key` matches the FULL node key

`-TraitName:` removes an inherited node only by **exact key match, including any `@label`** — `ResolveInherits` does `resolved.RemoveAll(r => r.Key == removed)` and throws `There are no elements with key '<key>' to remove` if nothing matched (`MiniYaml.cs:482-483`). So `-SquadManagerBotModule:` does **not** remove `SquadManagerBotModule@experimental.america.fixedwing`; you must write `-SquadManagerBotModule@experimental.america.fixedwing:`. There is no "remove all instances of this trait type" wildcard form — each labeled instance must be listed.

**A REDUNDANT removal is a hard error too, and inside a map's `rules.yaml` that error is SWALLOWED.** Stripping a trait on a base actor and then stripping it again on a derived actor that already `Inherits:` the stripped parent leaves the second `-Key:` with nothing to match, so it throws like any other mismatch. In mod rules that surfaces as a load-error dialog; in **map** rules it does not — `Map.PostInit` wraps the whole rules load in a `catch`, logs `Failed to load rules for <title> with error` to `debug.log`, sets `InvalidCustomRules`, and **falls back to `Ruleset.LoadDefaultsForTileSet`** (`Map.cs:540-547`; the scenario-rules loader has an identical catch at `:698-704`). Every actor type the map defined then ceases to exist. The map does not report a rules problem — it dies later and elsewhere, typically in the density pass at `actorsRules[actorType]` (`Map.cs:988`) with `KeyNotFoundException: The given key '<your custom actor>' was not present in the dictionary`, which reads exactly like a typo in the map's actor list and is nothing of the sort. **On a `KeyNotFoundException` naming a map-defined actor type, grep `debug.log` for `Failed to load rules` before debugging the actor list.**

### Resolve the ruleset before you trust an inheritance edit: `--dump-balance-json`

```sh
Mod=ww3mod ./utility.sh --dump-balance-json      # exits 0 only if the whole ruleset resolves
```

**Run this after any change to YAML inheritance — a `-Trait:` removal, a template reparent, a new `Inherits@`.** The command reads `utility.ModData.DefaultRules` (`UtilityCommands/DumpBalanceJsonCommand.cs:41`) and then walks every actor and every weapon, so it forces the full `ResolveInherits` pass that the game itself runs at startup. It takes seconds, needs no scenario and steals no window focus, and `utility.sh` runs under `set -e` so a load failure propagates as a non-zero exit.

**It catches a class of breakage that both other gates miss.** A change landed on 2026-08-27 that compiled clean and passed the whole NUnit suite and would still have stopped the mod from starting, because the failure is neither a compile error nor a unit-testable one — it is a rules-resolution error raised at load. Unit tests do not resolve mod YAML; the build does not read it at all.

**It also gives a removal POSITIVE evidence, which is otherwise hard to come by.** Because a `-Key:` matching nothing is fatal rather than ignored (see [§Removing an inherited trait](#removing-an-inherited-trait--key-matches-the-full-node-key)), a clean exit proves the node was really there and really came out. Without that, "I removed the trait" and "I wrote a line that did nothing" look identical in the diff.

This is the cheap gate; it is not the thorough one. It proves the ruleset *resolves* — not that lint is clean and not that anything behaves. `make test` remains the lint authority.

### WW3MOD's map grid is `Rectangular`, not `RectangularIsometric`

`mod.yaml:319` sets `MapGrid: Type: Rectangular`. So cell neighbours are the plain `(x±1, y±1)` grid, a Manhattan/Chebyshev disc maps directly to spatial adjacency, and `CellLayer.Contains(CPos)` has no `X<Y` isometric rejection. This is what lets the density-neighbour idiom (`CohesionMoveModifier.CoverScore`, and the Phase-1 map layers) step cells with raw `CVec` offsets.

### Disabling a string field: bare colon, not `""`

To clear a widget/chrome string field (`Background`, `Decorations`, `Separators`, `TooltipText`, …), use a **bare trailing colon**, never empty quotes. `FieldLoader.ParseString` returns the value verbatim (`FieldLoader.cs:161`), so `Separators: ""` parses as the literal two-character string `""`. That passes the `!string.IsNullOrEmpty` guards in the widgets, and the code then tries to load a chrome collection literally named `""` — e.g. `Sprite ""/separator was not found`. `Separators:` (bare colon) parses as null, `IsNullOrEmpty` fires, and the feature is skipped as intended.

### Maps must declare `Rules: rules.yaml`

A map's `rules.yaml` is loaded **only** when `map.yaml` names it under the top-level `Rules:` key. The engine maps that key to `Map.RuleDefinitions` (`Map.cs:176`, `required: false`); if it's absent, `RuleDefinitions` stays an empty MiniYaml (`Map.cs:364`) and the map loads only mod defaults. The map still renders and actors still spawn, so the omission is **silent** — LuaScript references, AutoTarget overrides, and every rule tweak are simply ignored. The same applies to `Weapons:`, `Sequences:`, etc.

### Which YAML gate catches a misspelled trait field — the fast ones do not

`FieldLoader.UnknownFieldAction` is bound at `CheckYaml.cs:66`, **before** the branch on whether a map argument was supplied, so the handler is armed in both modes. What differs is what each mode then *evaluates*:

- **Pathless** (`./utility.sh --check-yaml`, no map argument) calls `CheckRules(modData, modData.DefaultRules)` (`:73-74`). Evaluating `DefaultRules` forces the ruleset load, constructing an `ActorInfo` for every non-abstract actor (`Ruleset.cs:125-127`) and therefore every `TraitInfo` — **including the `Player` actor's bot modules**. A misspelled field on an `ai.yaml` module block *is* reported here. **`make test` runs exactly this form** (`Makefile:252-254`), so the repo's own gate does cover it.
- **Map-scoped** (`--check-yaml <map>`) never makes that call; it reaches `CheckRules(modData, map.Rules)` only when the map defines custom rules (`:148-151`). It lints the map, not the default ruleset.
- **`--dump-balance-json`** never binds `UnknownFieldAction` at all (grep `DumpBalanceJsonCommand.cs`: zero hits).

**Practical rule:** the per-map shortcut and `--dump-balance-json` are not substitutes for `make test` when you have added or renamed a trait field, or removed an inherited trait. They remain worth running — `--dump-balance-json` forces the full `ResolveInherits` pass in seconds and catches load-order and resolution failures neither of the others reaches, which makes it the cheap smoke test for an **inheritance** edit (a `-Trait:` removal that finds nothing throws *"There are no elements with key … to remove"*, `MiniYaml.cs:483`, so an exit-0 dump is positive evidence a removal bit). But a delta that touches AI YAML has not been linted until the pathless form has seen it; if you must skip it, cross-check the block's keys against the `Info` class's `public readonly` fields by hand.

## A change believed made, documented as made, and inert

**The most expensive defect shape in this codebase is not a missing mechanism. It is a mechanism that is present, documented, wired up, lint-clean — and evaluates to nothing.** Six separate defects fixed on 2026-08-22 were all this shape, and none of them was found by reading the code, because reading is exactly what these survive: the comment beside them is accurate about intent, the citation is real, the field is genuinely set, the trait is genuinely mounted. What is false is the *value the expression produces at the inputs the mod actually supplies*.

**Operational rule: when something has absorbed several fixes that each looked correct and changed nothing, stop hunting for a missing mechanism and start computing what the present one evaluates to.** Substitute the mod's real configured numbers into the expression and reduce it. Four of the first six below were found that way and could not have been found any other way. A companion habit, cheap and high-yield: when a field is set in YAML, grep for every *reader* of the field, not just its declaration — three of those six are fields with zero effective readers.

**Both habits have a blind spot, and 2026-08-27 walked into it four times.** Reducing an expression needs an expression to reduce, and grepping for readers needs a field that was written down. Instances 7 and 8 are fields **nobody set**, where the default did the damage; instances 9 and 10 are correctly-named call sites whose *callee* does something else. None of the four is visible in the diff, the YAML, or a reader census. What finds them is reading the body of the thing you are about to trust, one level down — which is the same corrective as the rest of this section, applied to a callee rather than to a value.

This is the code-side twin of [`README.md` §"Four shapes of confident correctness claim with nothing behind it"](README.md), which covers the same failure in prose claims. Both reduce to the same corrective: **name the line you would delete to break the property, and check that deleting it would change anything.**

### Four shapes, ten instances

The list grew from six to ten on 2026-08-27 and a flat list stopped being navigable. The instances keep their original numbers — they are cited by number elsewhere in this file and in `WORKSPACE/DISCOVERIES.md` — but they sort into four shapes, and **the shape is the reusable part**:

| Shape | Instances | What to run |
|---|---|---|
| **The expression reduces to nothing at the mod's real inputs.** Integer division, a threshold outside its own domain, a count × interval too small to see. | 1, 2 | Substitute the shipped numbers and compute. |
| **A gate cannot bind what it names.** Disjoint sets, an exclusion that covers the whole grant, a narrowing that leaves another channel open, an interface that is never enumerated. | 3, 4, 5, 6 | Enumerate what can satisfy *both* sides — and, per instance 3, over *time* as well as over inputs. |
| **An unset field's DEFAULT does the damage.** Nothing is written in YAML, so nothing looks wrong; the default is a live value that silently rewrites the result. | 7, 8 | For every field a warhead/trait reads, ask what it equals when nobody sets it — and whether that value is *reachable* on your delivery path. |
| **The right trigger wired to the wrong action.** The condition is correct and fires on schedule; what it then does is not what the comment beside it says. | 9, 10 | Read the body of the thing the condition calls. Do not infer it from the call site's name. |

The first two shapes were the whole list until 2026-08-27. The last two are newer and, unlike the first two, **cannot be found by reducing an expression** — there is no expression, only a name that does not describe its body.

### The instances (1–6 as of `main @ 12e0addd`; 7–10 as of `main @ eb2c4585`)

1. **An effect mounted, tuned to imperceptibility.** `WithHealFlash` has been on `^ExistsInWorld` since `82938ec8` (2026-03-28), applied at `defaults.yaml:13`. Its C# defaults are `Alpha = 0.3f`, `Count = 2`, `Interval = 2` (`Traits/Render/WithHealFlash.cs:22-31`). `FlashTarget.Render` tints only when `tick % interval == 0` (`Effects/FlashTarget.cs:64`) and the effect dies at `++tick >= count * interval` (`:58`) — so `Count 2, Interval 2` is **two single-tick tints 120 ms apart**, not 240 ms of tint. The user reported "no effect when medics heal" about a feature that had shipped, working, for five months. `Interval: 1` is the only way to get a continuous glow; the mod now sets `Count: 6, Interval: 1` (`defaults.yaml:14-22`).
2. **A scoring term that is integer-zero across its entire domain.** The medic's patient scorer carried `score += dist / 10240` under the comment *"slight distance tiebreaker (1 point per 10 cells)"* (added `e305be21`). That is integer division on a WDist length, and `^MEDI`'s `SearchRange` is `8c0` = 8192 (`infantry.yaml:2170`). **8192 / 10240 == 0 at every reachable distance**, so distance never affected patient choice at all and ties fell to enumeration order. Now `DistancePenaltyPerCell` in cell units, with the trap preserved as a `[Desc]` at `HealerAutoTarget.cs:52-54`.
3. **A mutual-exclusion lockout between two things that can never contend — and the one entry in this list that was itself wrong.** The Tunguska's 9M311 armament is paused by `firing-primary` (`vehicles-russia.yaml:896`). `firing-primary` is granted by `GrantConditionOnPreparingAttack@1` with `ArmamentNames: primary` (`:868-870`); `primary` is the AG gun (`:851-853`) with `ValidTargets: Infantry, Vehicle, Defense` (`weapons-ballistics.yaml:648`), while the 9M311 is `ValidTargets: Air`. **No actor in the mod advertises `Air` alongside `Vehicle`/`Infantry`/`Defense`** — aircraft split those by the `airborne` condition — so the two armaments can never be valid against one target. `Armament.CanFire` also rejects on `IsValidAgainst` at `:337`, *before* `PreparingAttack` is notified at `:420`, so the AG gun cannot grant the condition **while engaging air**.
   Both observations are true. **The conclusion drawn from them — "the whole condition evaluates to nothing" — was wrong, corrected 2026-08-27 after a playtest report**, and this entry committed the exact error the section exists to warn about: it reduced the expression for *one target at one instant* and never asked how long the condition outlives the shot that granted it. The two armaments never need to contend for a single target, because **the pause is not simultaneous — it is a residue.** The gun grants `firing-primary` while engaging **ground**, where it is entirely valid; the helicopter that arrives afterwards meets a Tunguska whose missiles are still paused. `PreparingAttack` pushed a token **per shot with no `MaximumInstances` cap** while `Tick` pops **one per `RevokeDelay`** (50 ticks, `RevokeAll` defaulting false), so emptying the 180-round pool left 180 tokens draining over 9000 ticks — **540 s of missile lockout at Timestep 60**, with a full missile pool. Note which quantity drives it: *shots fired*, not the empty magazine. Running dry clears `ammo-primary` and thereby *stops* the granting, so exhaustion is merely the most visible moment at which the count is guaranteed large. It compounds with the `AutoTarget` scan-radius collapse ([§Engine behaviors that surprise](#engine-behaviors-that-surprise-debugging-gotchas)): with the guns dry (`!ammo-primary`) **and** `firing-primary` stuck, all three armaments are paused, `GetMaximumRange()` returns `WDist.Zero`, and the Tunguska stops *seeing* aircraft as well as shooting them. Fixed by capping the stack in `GrantConditionOnPreparingAttack.ShouldGrantInstance`, pinned by `PreparingAttackTokenStackTest`; the condition now clears one `RevokeDelay` after the last shot however many were fired. **The lesson survives but is sharper than it was written: reduce the expression over *time*, not only over inputs — a condition's value includes how long it persists.**
4. **A re-gate that shipped as a comment and never took effect.** `12.7mm.Hind` carries a dated, specific, confident comment (`weapons-ballistics.yaml:369-371`): *"GROUND ONLY as of 260815 — Helicopter moved to 12.7mm.Hind.AA."* The edit it describes was really made — `Helicopter` is absent from its `ValidTargets` (`:372`) and `12.7mm.Hind.AA` exists (`:392`). **It just did nothing**, because the gun kept reaching Light helicopters (littlebird, TRAN, HALO) through the `Light` armour class it still lists. The artefact left behind is *more* convincing than no artefact would have been, and is exactly what stops the next person checking.
5. **A declared capability cancelled by an exclusion list.** `^5.56mm` declares `ValidTargets: … Helicopter` (`:83`) and `InvalidTargets: Light, Medium, Heavy` (`:84`). Exclusion wins (`WeaponInfo.cs:218`), every helicopter is Light or Heavy, so the declared anti-helicopter capability was **100% dead** while armour classes leaked into flight. Full detail in [§`InvalidTargets` beats `ValidTargets`](#invalidtargets-beats-validtargets-so-an-armour-class-can-silently-cancel-a-declared-capability).
6. **A load-time guard that was never enumerated, and compiled clean.** `Ruleset.cs:51` iterates `a.TraitInfos<IRulesetLoaded>()` — the **non-generic** interface, which is the only one carrying `ITraitInfoInterface` (`TraitsInterfaces.cs:621-622`). A `TraitInfo` that declares only `IRulesetLoaded<ActorInfo>` implements an identical method signature, **compiles with no error and no warning, and is never invoked** — `TraitInfos<T>()` cannot match it. The correct form is the bare `IRulesetLoaded` on the class with the method implemented explicitly as `void IRulesetLoaded<ActorInfo>.RulesetLoaded(…)`; the interface named on the class and the one named on the method are deliberately different, which is precisely why the wrong version looks right. `AmmoPoolInfo` (`AmmoPool.cs:20`, method at `:155`) is the corrected reference. **A validation that never runs is worse than no validation, because everyone who reads it afterwards banks it as safety.**

7. **An omitted field whose default silently divides the damage away.** `DamageWarhead.Penetration` defaults to **1** (`Warheads/DamageWarhead.cs:24`), and `ApplyPenetration` returns `damage * penetration / thickness` whenever penetration is under the victim's armour (`:127-133`). So a `TargetDamage` warhead that simply **does not mention** `Penetration` delivers `damage / thickness` — against a 280mm tank, **0.4% of the number written in the YAML**. Both ballistic missiles shipped this way: `IskanderExplosion` and `HIMARSExplosion` were the only large `TargetDamage` warheads in the mod with no value at all, while every comparable weapon sets one (`^12.7mm` 15, `^30mm` 70, `ATGM` 100, `RPG` 500, `^TankRound` 800, `Ataka` 900, `^ArtilleryRound` 1000 — all re-derived from the caliber templates 2026-08-27). **Nothing in the YAML looked wrong, because nothing was written.** The reviewable artefact of an omission is absent by construction — which is what makes this shape different from instances 1–6, where there was always a line to read. Sizing note: the thickest armour in the mod is **2000** (`MSLO`, `structures-defenses.yaml:1106`, no `Distribution` so never discounted by hit direction), not the 280 of a T-90 — a "kills anything in one shot" warhead has to clear 2000.
8. **An unset field whose default is a plausible value, in the wrong coordinate space.** `WarheadArgs.ImpactPosition` was assigned by **projectiles only** — seven projectile types (`Bullet`, `Missile`, `GravityBomb`, `LaserZap`, `Railgun`, `AreaBeam`, `InstantHit`) plus the `WarheadArgs(ProjectileArgs)` constructor (`WeaponInfo.cs:51`). The **projectile-less** path, `WeaponInfo.Impact(in Target, Actor firedBy)`, built its args with an object initializer that never mentioned it, so it stayed `WPos.Zero` — **the map origin**, a perfectly valid `WPos` that no guard rejects. Everything delivered by `Explodes` / `SpawnedExplodes` takes that path, including both ballistic missiles (`Explodes.cs:133`). `TargetDamageWarhead` then scales damage by `CenterProximityPercent(victim, args.ImpactPosition)`, measured from the map corner: against a T-90's 1030-unit half-diagonal that is **−2782%**, and `Health.InflictDamage` does `HP = (HP - damage).Clamp(0, MaxHP)` (`Health.cs:189`) — **so the direct-hit warhead healed its target.** `SpreadDamageWarhead` reads the same field for impact *orientation*, so every `Explodes` splash was also computing hit direction from the origin. Fixed at `WeaponInfo.cs:307`; `TargetDamageWarhead.ProximityDamagePercent` (`:31`) now additionally floors the percentage at zero, because `Spread` admits victims by distance from the hitshape **edge** while `CenterProximityPercent` normalises against the **centre-to-corner** distance, and on a long thin hull those disagree. **A negative damage number is not a rounding artefact in this engine; it is a heal.**
9. **The right trigger wired to the wrong action.** `Armament.CheckFire` tested exactly the right condition for restarting an interrupted burst — and then called `UpdateBurst`, which is the **per-shot advance**. It ran `--Burst`, so the "reset" removed a shot: a burst broken off with R shots left came back delivering **R−1**. At `R = 1` the decrement hit 0, which *completes* a burst and resets the counter to full — so one case in the family was accidentally correct, which is exactly why the bug read as intermittent rather than systematic. It also emitted a spurious `INotifyBurstComplete.FiredBurst` and scheduled an `AfterFireSound` with no shot fired. **The call site named the intent and the callee did the opposite; nothing about the line was reducible.** Now `ResetBurst` (`Armament.cs:433-436`), with the reset clock keyed off `BurstSequence.StaleTick` — see [`missiles.md` §9](missiles.md).
10. **A value computed, then overwritten on the very next line — while still consuming a synced RNG draw.** `Armament.ResetBurst` called `SharedRandom.Next(...)` into `Burst` for `WeaponInfo.BurstRandomize`, and then assigned the modifier-adjusted `Burst` over it immediately. Three weapons set the field (`5.56mm.AR`, `25mm.Bradley`, and one further `^30mm` derivative), so **the draw really was being consumed and the value really was discarded** — the field has never had an effect, and the balance of those three was tuned with it inert. The dead computation was removed 2026-08-27; the field is kept, with its `[Desc]` (`WeaponInfo.cs:118-121`) now saying NOT IMPLEMENTED, because implementing it would put `SharedRandom` back in the firing path and change those weapons' output. **Grepping for readers would NOT have found this one** — the field had a reader, on the correct line, doing the correct arithmetic. Only reading the next line finds it.

11. **A leash declared on the MASTER and enforced on the SLAVE, in different units.** `CarrierMasterInfo.MaxSlaveDistance` has **zero readers engine-wide** — as do `MaxSlaveDistanceCheckInterval` and `SpawnIsMissile` (declarations at `CarrierMaster.cs:22`, `:39`, `:43`; every other hit in the tree is a comment or a test). `^DR` set `MaxSlaveDistance: 20c0`, so the YAML asserted a 20-cell leash while the game enforced the slave-side `CarrierSlave.MaxDistance` (`CarrierSlave.cs:131`, `:138`) — **denominated in CELLS, not `WDist`**, so the two fields are not even the same kind of number. The dead line has been removed and all three engine fields now carry `[Desc("UNREAD - setting this does nothing…")]` naming the field that actually bites. **The general shape: in a master/slave trait pair, the half you are configuring is not necessarily the half that enforces** — grep the *other* class before tuning either.

### The same failure in comments: an asserted duration the code does not produce

**RA-era 25 ticks/second is the default assumption of anyone writing a duration comment, and it is wrong for this mod everywhere.** WW3MOD's `default` game speed is `Timestep: 60` (`mod.yaml:382`) = **16.67 tps**, so a tick count annotated "N seconds at 25 tps" really runs **1.5× longer**. This is not an incident; four fresh sites turned up on 2026-08-22 alone, on top of the two already banked. `SupplyRouteContestation`'s `BaseTicks: 1500` was annotated "60s" (really 90 s), `MinTicks: 500` "20s" (30 s), `BaseRecoveryTicks: 3000` "120s" (180 s). **Grep `at 25 tps` before trusting any duration comment**, and prefer expressing tick-domain quantities in ticks with the seconds figure derived, not asserted.

**There is a THIRD tick base, and it is the one that decides what a correction should aim at.** Beyond wall-clock 16.67 and the harness's 25, the engine's own Lua converter computes `ticksPerSecond = 1000 / defaultGameSpeed.Timestep` in **integer** arithmetic (`DateTimeGlobal.cs:31`), so `DateTime.Seconds(n)` runs at **16**, not 16.67. A scenario mixing `DateTime.Seconds` with `AssertWithin` is mixing two bases whose ratio is 25/16 = 1.5625, not 1.5. **Consequence: if `TestHarness.TicksPerSecond` is ever corrected, the target is `16` — correcting it to the mathematically exact 16.67 would open a fresh 4% divergence against the engine converter, of exactly the kind being closed.** The same integer division is why `TimeLimitManager.cs:110` runs time limits ~4% short (below, §Engine behaviors that surprise). Both tripwire scenarios and all three constants are pinned by `engine/OpenRA.Test/OpenRA.Mods.Common/AutotestTickRateTest.cs`, which fails at `dotnet test` rather than silently in a game nobody reran.

**Census of surviving sites (as of 2026-08-30, `5eb27755`), so "still live at ten other sites" is checkable rather than asserted.** Comments whose seconds figure is *wrong*: `SmartMove.cs:25` ("~3 sec at 25 tps", really 4.5 s), `EvacDriveOffMath.cs:32` ("25 ticks/s ⇒ 20s"), `TournamentConfig.cs:100` ("standard 40 ms tick"), `SupportPower.cs:24` ("Parsed at 25 ticks/second"), `mods/ww3mod/scripts/scenario.lua:31` (`briefingDuration = 375`, "~15 seconds", really 22.5 s), `test-missile-hellfire-probe.lua:168`. Comments that correctly *describe the harness base* rather than the game's, and are fine: `test-autotarget-preempt-air.lua:140`, `test-stance-redirect-midadjust.lua:50`, `test-stance-anchor-move.lua:46`. Three were corrected on 2026-08-30 — `test-dry-inrange-idle-oscillation.lua:21` (250 ticks is 15 s not 10 s), `test-critical-no-panic.lua:10` (300 ticks is 18 s not 12 s), and `test-visual-concealment-gauge.lua:45`, **which was wrong in the diagnostic direction**: it divided `TimeToBeStill: 200` (`infantry.yaml:142`) by 25, got 8.0 s, and concluded the capture request's "12.0" was mistaken. 200 ÷ 16.67 is exactly 12.0 — the request was right and the comment argued the reader out of a correct number. `Map.cs:265` is a throughput note where the rate is not load-bearing.

**It is not only code comments — on 2026-08-27 two instances were found in the docs themselves**, one of them inside this curated bank: `game-model.md` described the clearing `CaptureDelay: 1000` as "~40 s" (it is **60 s**), and `DOCS/recipes/TELEMETRY.md` sized its log volume at "25 ticks/sec". Both are now corrected. **Grepping the source tree for this error is not sufficient — grep `DOCS/` too**, and note that neither instance contained the string `25 tps`: one had done the division silently and only the *result* was wrong. The reliable tell is a seconds figure sitting beside a tick count; recompute it rather than scanning for a phrase. The harness-side instance is the widest-reaching and is covered in [`DOCS/recipes/AUTOTEST.md`](../recipes/AUTOTEST.md); the `world.Timestep`-vs-`GameSpeed.Timestep` mechanism is under [§Engine behaviors that surprise](#engine-behaviors-that-surprise-debugging-gotchas).

### Detectors worth running before you believe a mechanism works

- **Reduce the expression at the mod's real inputs.** Integer division, a threshold compared against a range, a percentage of a small base — substitute the shipped numbers and compute. `distance / 10240` against an 8192 radius is zero; `Count × Interval` at 2×2 is two frames.
- **Grep every reader of a field you are about to tune**, not its declaration. Zero readers is common and silent: `InaccuracyPerProjectile`, `DamageAtMaxRange` and `MovementInaccuracy` are all set in shipped YAML and all inert. **A reader is not enough — read the line AFTER it too.** `BurstRandomize` (instance 10) had a reader, on the right line, doing the right arithmetic, into a variable the next statement overwrote.
- **Ask what each field a code path reads equals when NOBODY sets it.** The dangerous default is not zero-as-disabled; it is a live value that looks legitimate — `Penetration` defaults to 1 (a divisor, not a no-op), `ImpactPosition` defaults to the map origin (a valid coordinate). Then ask the second half: is that default *reachable on my delivery path*? An `Explodes` payload never goes near the projectile code that would have set it.
- **When a comment names an intent, open the function it calls.** Instance 9 was a correct trigger calling a decrement named as a reset. The call site read exactly as intended and there was nothing to reduce.
- **For a gate or exclusion, enumerate what can actually satisfy both sides.** A lockout between disjoint target sets, or an exclusion covering every member of a granted capability, is a no-op with a convincing name.
- **For a guard, prove it FAILS against the thing it forbids before trusting it** — hand-author a violation and watch it error. A green build is not evidence that a validation ran. (Same RED-first discipline the behavioural work already follows; see [`DOCS/recipes/AUTOTEST.md` §"A green run is not evidence unless something could have made it RED"](../recipes/AUTOTEST.md).)
- **When a re-gate works by narrowing `ValidTargets`, narrowing is not sufficient** — confirm the target no longer advertises anything *else* the weapon still accepts. Neither the lint nor the type system checks for a `ValidTargets` entry that can never match, or for a removal that changes no behaviour. The only reliable instrument is a reachability matrix built from the parsed corpus and diffed across the change. **Sampling will not find these, because the sample you would skip is the one the comment tells you is already handled.**

## PITFALL comments (full spec: [`pitfalls.md`](pitfalls.md))

Recurring traps get a one-line `// PITFALL:` (`# PITFALL:` in YAML) **at the temptation site** — the line a careless reader is looking at when about to fall in. List all: `git grep PITFALL`. Add them during bug fixes when the root cause would surprise a reader; prune when stale (a wrong PITFALL is worse than none). Not for one-shot fixes, generic best practice, or universal anti-patterns (those go in a hook or the engine code rules below).

## Engine code rules (enforced by `tools/git-hooks/pre-commit`)

- **`[Sync]` on a trait that does not implement `ISync` hashes nothing and warns about nothing.** The type test is `Actor.cs:206`. Adding the attribute is not adding sync coverage — see architecture.md §"`[Sync]` is inert without `ISync`" for the rule, the effects equivalent, and the NUnit guard that now catches it.
- **No `Console.Write`/`WriteLine` in tick-path code** — use `Log.Write(channel, ...)`. Console output fires every tick and floods stdout. Allowlisted directories: `UtilityCommands/`, `UpdateRules/`, `/Lint/`, `OpenRA.Server/`, `OpenRA.Test/`, `OpenRA.Utility/`, `tools/`.

Hook install (once per clone): `ln -sf ../../tools/git-hooks/pre-commit .git/hooks/pre-commit`

### A green analyzer gate means what the TARGET GRAPH reaches, not what the solution lists

**Release builds have no analyzers at all.** `engine/Directory.Build.props:51-56` removes every `Analyzer` item when `Configuration=Release`. So any target that routes through a Release build contributes **zero** analyzer coverage, however many projects it compiles — and a `make` target that depends on it still goes green.

That is not hypothetical: it was the whole of the long-standing Windows/Linux gate asymmetry. Both platforms read the same solutions; they diverged on which **engine target** the mod's `check` depends on. `make.ps1` routes `check` into `engine\make.cmd check`, a Debug `-warnaserror` build of `engine/OpenRA.sln`; `Makefile:191` is `check: engine`, and the engine's `all` target is **Release**. Linux/macOS was not missing projects from a solution — it was building the right solution in the wrong configuration.

**Generalise this: when two CI lanes disagree about what they catch, diff the target graph, not the solution files.** `make.ps1` and `Makefile` are independent implementations of the same target names in this repo and have drifted before.

Two related traps in the same area:

- **Effective severity in `engine/.editorconfig` is the LAST assignment for an id, not the one under the explanatory comment.** `RCS1058` is set to `warning` at `:1098` and to `suggestion` at `:1396`, both inside the same `[*.{cs,csproj,yaml,lua,sh,ps1}]` section — a whole block of `SA`/`RCS` rules is silently downgraded this way. **Compute the final value** (`awk` over every `dotnet_diagnostic.<id>.severity`) before concluding a rule is enabled, disabled or broken, and especially before picking a rule to prove a gate is live with: a rule you believe is a `warning` may be reporting as a suggestion and failing nothing.
- **The `RUNTIME=mono` build path is a DIFFERENT gate, not the same gate run again.** *(It was a CI lane until `70fd483e` removed it — `.github/workflows/ci.yml` now has exactly two jobs, `Linux (.NET 6.0)` and `Windows (.NET 6.0)`. The path is still reachable via `make RUNTIME=mono`, so the trap below is live for anyone who runs it.)* `engine/Directory.Build.props:61-63` drops both Roslynator packages when `MSBuildRuntimeType` is `Mono` (upstream comment: they fail there with `AD0001`), so no `RCS*` rule can fire on that lane. It also builds a different TFM — `netstandard2.1` rather than `net6.0` (`:22-23`) — which is why several `System.*` `PackageReference`s that read as redundant at `net6.0` are load-bearing (`System.Collections.Immutable`, `System.Threading.Channels`, `System.Runtime.Loader`, `Microsoft.Win32.Registry`): the same file at `netstandard2.1` fails `CS0234` without them. **Do not delete a reference because one lane calls it redundant.**
- **`NuGetAudit`'s transitive reach is a target-framework effect, not an SDK effect.** The knob is `NuGetAuditMode`, which defaults to `direct` and only flips to `all` at `net10.0`. Measured on one package, one SDK (10.0.400), bare `dotnet restore`: `NU1902` is not raised at `net6.0` or `net8.0` and is raised at `net10.0`; forcing `-p:NuGetAuditMode=all` reproduces it at `net6.0` on demand. So an SDK pin is not what hides a transitive advisory — it surfaces on the TFM bump commit itself.
- **The mirror case — a gate covering MORE than you think: `Class=Unknown` does NOT hide a map folder from `--check-yaml`, because `HasFlag(0)` is always true.** `mods/ww3mod/mod.yaml:107` registers the autotest scenario tree as `Unknown`, which does keep it out of every UI tab. But `CheckYaml` calls `EnumerateMapDirPackagesAndNames()` with its default `MapClassification.System` (`MapCache.cs:212`), and the folder filter is `classification.HasFlag(packageClassification)` (`MapCache.cs:194`) — with `MapClassification.Unknown = 0` (`MapPreview.cs:35`), `HasFlag(0)` is `(x & 0) == 0`, true for every value. So the scenario maps are linted exactly like shipped content, and there is **no classification value that excludes them** — the sentinel makes it unfixable by reclassification alone. Two consequences: a per-map defect in the scenario tree is indistinguishable from one in shipped content unless you attribute each error back to its `Testing map:` header, and **error counts multiply by map** — one rules-level defect reports once per linted map, so a total can fall by hundreds without a defect being fixed. **Compare error classes, never totals.**
- **Method note: a `dotnet build` reporting `0 Warning(s)` may simply have been up-to-date.** Check for the `-> ….dll` line and a plausible elapsed time before believing a zero; `-t:Rebuild` forces `CoreCompile` to actually run.

## A build that fails and launches anyway indicts the WRONG code, every time

When a launcher runs the game after a failed build, the engine loads new YAML against a stale `engine/bin` and reports **the first trait it cannot resolve** — which is a trait added *after* the last successful build, i.e. whatever the reader edited most recently. The error is maximally misdirecting: it points at real, freshly-written code and says something false about it, and there is no route from the symptom back to the cause. **A `Cannot locate type: <recently added trait>` stack trace is a stale-binary tell first and a YAML bug second** — check that the build actually succeeded before reading it. The concrete incident cost a session to a 60-line trace naming a trait that was fine.

Three mechanisms in this repo made that reachable; all are now closed, and the reasoning is carried in-code at each site.

- **`find … -exec` is never a safe way to run something whose exit code matters — `find` exits 0 regardless of what the command it ran returned** (verified: `find . -maxdepth 0 -exec sh -c 'exit 7' \;` yields `$? = 0`). The `Makefile`'s `all` target used it to build the mod solution, so a failed build reported success to every consumer including `make test`'s `all` prerequisite. It is now `@set -e; for sln in $(MOD_SOLUTION_FILES); do …` (`Makefile:183` mono, `:186` otherwise), with the reason in a comment above it. **This never bit anyone only by luck** — `WW3MOD.sln` currently holds just `OpenRA.Game` and `OpenRA.Mods.Common`, both built earlier by the `engine:` prerequisite through a sub-`make` that *does* propagate, so a compile error always failed sooner. Add one mod-specific project to that solution and the hole reopens. Note `clean` still uses `find -exec` (`:192`, `:194`), which is fine — nothing gates on it.
- **A launcher must test the build's exit code explicitly.** `launch-game.cmd` invokes `make.ps1 … all` and now gates on `if %errorlevel% neq 0 goto buildfailed` (`:5`). Deliberately `neq 0` rather than `if errorlevel 1`: the latter is a signed `>= 1` test, so a `powershell.exe` dying on an access violation (`-1073741819`) would slip through it and launch on stale binaries.
- **"The muxer is on `PATH`" is not "the pinned SDK is installed".** `global.json` pins `6.0.428` with `rollForward: latestFeature`, which **cannot cross a major version**, so a machine carrying only 8.x/10.x resolves `dotnet` fine and still fails every project. Do not reimplement the `rollForward` matrix in a shell script — it drifts away from what `dotnet` really does. `dotnet --version` honours `global.json`, costs nothing, and fails with exactly the error a build would hit, which makes it an authoritative pre-flight that cannot rot. Both entry points ask it and nothing else: `Makefile:163` (`check-dotnet-sdk`, a prerequisite of `all`) and `make.ps1:241` (`CheckForDotnetSdk`, called at `:406` for `all`/`clean`/`check`). Running it before anything compiles reports the one real cause instead of burying it under a per-project wall of identical muxer errors.

**Generalising past this repo: any pipeline that *can* run the game after a failed build will eventually produce a misdirecting crash, and the person reading it has no way to know.** The cheap guard is at the launcher, not at the build.

## Shell scripts run under zsh — an unquoted `$var` is NOT word-split

The repo's scripts and the agent shell both run zsh, where `prog $args` passes the variable as **one** argument rather than splitting it on whitespace the way bash does. So the common bash idiom

```bash
for p in "--perturb 0" ""; do ./probe.sh $p; done     # zsh: passes ONE arg "--perturb 0"
```

hands `probe.sh` a single glued token that no flag parser matches. Use an array (`args=(--perturb 0); prog $args`) or `${=var}` to force splitting.

**Why this earns a place here rather than being generic shell trivia: the failure is silent and it inverts results.** The flag never parses, so the feature under test never activates, and the run completes normally — reporting IDENTICAL / PASS for a comparison that was never perturbed. It cost two false results in one day, including a self-test that passed *while believing it was perturbed*. **Prove the flag arrived (echo the received argv) before trusting a null difference or blaming a stale build.** Same family as the `| tail` verdict-swallowing trap in [`../recipes/AUTOTEST.md`](../recipes/AUTOTEST.md): the shell reports success for a thing that did not happen.

**`utility.sh` and `utility.cmd` are NOT equivalent, and docs that give one form for both are wrong.** `utility.sh:62` injects the mod id for you (`… OpenRA.Utility.dll "${LAUNCH_MOD}" "$@"`); `utility.cmd`'s `argC GEQ 2` branch passes `%*` verbatim. So `./utility.sh --regen-shadows <path>` becomes `.\utility.cmd ww3mod --regen-shadows <path>` on Windows, not the same string. Known and deliberately **unfixed** (a `%MOD_ID%` injection would double it for existing script callers that already pass one, and a correct first-arg test needs verifying on Windows); documented in place at the branch. Related, and fixed on 2026-08-30: `utility.cmd` used **bare `find`** for its VERSION check, which with Git-for-Windows on PATH resolves to GNU `find.exe`, errors, falls through to `:noengine` and sits on `pause` **forever at ~0% CPU**. It looks exactly like a slow computation — an agent waited ten minutes believing shadows were being generated. Now called as `%SystemRoot%\System32\find.exe` by absolute path. **Both are the same family as the exit-code traps above: a failure wearing the costume of progress.**

## Engine behaviors that surprise (debugging gotchas)

- **A diagonal cell step is produced by THREE independent code paths, and only one of them is the pathfinder — so a new movement rule placed in the graph is not in force.** (a) `DensePathGraph.GetConnections` → `GetPathCostToNode`, the multi-cell case; (b) **`PathFinder.FindPathToTargetCell` (`Traits/World/PathFinder.cs:106-113`), the one that is easy to miss** — for `source.Layer == target.Layer && (source - target).LengthSquared < 3` it returns the two-cell path **without building a graph at all**, and `LengthSquared == 2` *is* a diagonal, so every single-step diagonal (exactly the order a player issues when clicking just past a gap) bypasses the graph; (c) `Mobile.GetAdjacentCell`, the "back up to let others pass" sidestep, which walks all 8 `CVec.Directions` under `CanEnterCell`/`CanStayInCell` only. Any "you may not take this step" rule has to be taught to all three.
  - **And a rule whose blockage is NOT in the destination cell will spin `Move` forever unless it is also taught to `PopPath`'s escape** (`Move/Move.cs:296-303`). The blocked-handling block has exactly one path-clearing exit, and it was a plain `CanEnterCell` test — which returns *true* for a corner-squeeze, because the blockage lives in the two shoulder cells while the destination is ordinary open ground. The comment and the extra disjunct are at the site now. **General form: if your rule is a property of the *edge* rather than of the *cell*, every destination-only predicate in the movement stack is blind to it.**
  - **Both-shoulders vs either-shoulder is load-bearing, not a taste call.** `DirectedNeighbors` prunes each expansion to cells "not guaranteed to be reached more cheaply through our parent", a proof that assumes reachability is direction-independent. It survives a **both**-shoulders rule because for every neighbour the straight-incoming rows discard, the parent's diagonal to it has the currently-expanding (therefore passable) cell as one shoulder — so the parent's move can never be corner-denied. Under an **either**-shoulder rule that neighbour becomes deniable, the pruning silently drops reachable cells, and the search goes incomplete: paths vanish in tight terrain.
  - **Infantry are EXEMPT, deliberately — a solid wall corner does not stop them, and that is an accepted trade, not a bug.** `Locomotor.IsDiagonalSqueeze` (`Locomotor.cs:252`) returns early for `SharesCell` locomotors, so a subcell-capable actor still walks diagonally between two solid cells — including the two corners of a building, a cliff, or the outside corner of any structure. Full-cell occupants (every wheeled, tracked, walker, naval and landing-craft locomotor) are denied it. **Do not "fix" this** — it is a user decision of 2026-08-08, and the reasoning is in-code at `:254-257`. The criterion is occupancy, not unit class: `SharesCell` is not a *proxy* for subcell capability, it **is** the switch (`Mobile.cs:321` assigns `ToSubCell` straight from it), so the scoping cannot drift and a future cell-sharing unit is exempted with no list to edit. In this mod it partitions cleanly — `SharesCell: true` appears on exactly the four `foot*` locomotors (`world.yaml:32/47/64/80`, re-derived 2026-08-19) and nowhere else. It also had to be a *locomotor* property rather than a per-actor test: `DensePathGraph.DirectedNeighbors` prunes on direction-independent reachability, and a search runs against exactly one locomotor, so a locomotor-level exemption keeps the both-shoulders argument (above) intact for the whole search. Naval was flagged as the live edge and is a non-issue: those locomotors are vestigial RA carry-over and `rules/ingame/naval.yaml` has **zero** non-comment lines, so no ship exists to be blocked.
  - **Scope, as shipped: the rule is tank-traps-only.** It keys on a marker trait `BlocksDiagonalSqueeze` via `CellFlag.HasDiagonalSqueezeBlocker` (`Locomotor.cs:33`, set `:575`, read `:303`), carried by exactly `TANKTRAP1` and `TANKTRAP2` (`decoration.yaml:535`, `:548`). Deliberately **not** on `^Rock` or `^Tree` — an earlier, broader version keyed on generic impassability and closed tree-corner pockets all over the mod.

- **Vehicles CANNOT crush or drive through trees or hedges in this mod — a belief that has come up more than once and is wrong.** Crushing here is not the engine `Crushable` trait (no actor uses it); it is modelled through `Passable`, which carries `CrushedByRelationships` (`Passable.cs:29`). `SBAG`/`FENC`/`BARB` set their pass class **plus `CrushedByRelationships: Enemy`**, and the heavy vehicle locomotors list those classes in `Crushes` — so tanks really do crush sandbag, wire and barbed wire, and only an **enemy's**. - **Two WW3MOD-only filters drop a target on the AUTO path alone, and their asymmetry is diagnostic.** `AutoTarget.ChooseTarget` skips a candidate on **overkill** (`AutoTarget.cs:1458`, `Info.OverkillThreshold >= 0 && target.Actor.AverageDamagePercent > OverkillThreshold`; default `100`) and on **break-off** (`:1467-1468`, `Info.BreakOffCondition`, default `critical-damage`, `:244`). **The overkill comparison is strictly `>`, not `>=`, and that is load-bearing** — `EstimatePercentDamage` caps one shooter's claim at 100 (`:1692`) and the threshold is 100, so under `>=` a single committed shooter tripped the skip exactly and blinded every other unit; the PITFALL at `:1450-1457` records the measurement. The consequence to carry: **one committed shooter can never deter a second**, deliberately. Break-off has **three further sites** beyond the scan: `Activities/Attack.cs:217` (the `AttackFrontal` activity) and, since 2026-08-27, both of `AttackFollow`'s targets — `RequestedTarget` (`AttackFollow.cs:182-185`) and `OpportunityTarget` (`:208-209`). All are scoped through `AttackBase.BreakOffApplies` (`AttackBase.cs:672`), which exempts deliberate and force-attack orders. Overkill still has exactly one site. **So the two behave differently on a manual order: overkill is skip/fire/fire, break-off is skip/skip/fire.** If a unit refuses an auto-target but obeys a right-click, suspect overkill; if it refuses both but obeys force-fire, suspect break-off. - **The overkill mark is a sum on the TARGET of per-attacker RESERVATIONS, and a reservation is released when the shot resolves.** `Actor.AverageDamagePercent` is a plain public int (`Actor.cs:83`) that any code may read, but write it through the claim API: `Actor.ClaimForAttack` (`:98`) reserves a share and `Actor.ReleaseAttackClaim` (`:106`) hands it back, both delegating to `OverkillClaim` (`engine/OpenRA.Game/OverkillClaim.cs`). **The release fires from `Armament`'s delayed fire action (`Armament.cs:483`) — at the trigger pull, above the target re-validation return, so a shot that misses, expires short, spawns no projectile, or is aborted because the target died in the `FireDelay` gap all release too.** Two invariants follow from the claim having an owner, and both are pinned in `engine/OpenRA.Test/OverkillClaimTest.cs`: **one shooter is one claim** (re-committing replaces rather than stacks, so a unit re-acquiring the same target every rescan cannot inflate the tally alone), and **a claim taken and released leaves the tally where it started**. `MarkForDestruction` (`:85-92`) is still the raw ownerless `+=` — it has no way back and decays out instead, so prefer `ClaimForAttack` from anything representing a shooter.
  - **What is still NOT released, and decays out rather than being handed back:** a claim whose holder dies before firing, one whose holder is ordered elsewhere before firing, and any raw `MarkForDestruction` bump. So killing the committing unit does not clear its mark. The halving every 60 ticks (`Actor.cs:345-346`, whose PITFALL records why the interval went 20 → 60: a 20-tick halving let other units re-target a tank mid-reload) is the cleanup path for exactly those cases.
  - **Release is clamped at zero** (`OverkillClaimMath.Release`, `OverkillClaim.cs:90`) because the decay runs underneath a live claim: a claim of 100 held across two halvings is worth 25 on the tally when it comes back, and subtracting the recorded 100 unclamped would go negative. The clamp can under-count while another shooter still holds a claim — that errs toward units engaging, which is the safe direction.
  - **Before 2026-08-21 nothing released the mark at all** and the halving was the only downward force, so commitments accumulated and a target under sustained attention read as permanently over-committed. If you are reading a comment, a scenario or a commit older than that which says the mark is ownerless and self-clearing, that was true when written.
- **A single attacker's claim is capped at one kill's worth, and aggregate commitment is self-limiting by design.** `EstimatePercentDamage` returns `Math.Min(totalDamage * 100 / health.MaxHP, 100)` (`AutoTarget.cs:1591`) — before that cap, one MANPAD marked a 600-HP helicopter at 500 against an `OverkillThreshold` of 100, needing three halvings to clear. The intended shape is that attackers commit until the marked total covers the target's health and the rest stand down, which is correct in aggregate; the failure mode was **granularity at the fragile end**, not a runaway loop. Note the residual shape still holds: **suppression duration scales as `damage × 100 / MaxHP`, so the most fragile target is marked hardest and suppressed longest** — which is exactly the case a player expects a battery of AA to shred. The mark itself is invisible in the simulation (no cursor, no message, no target line); `WithHoldingFireDecoration` (render-only, reads `AutoTarget.LastHeldFireTick`, writes nothing) is what surfaces it.
- **Detection gates BOTH attack paths, so "auto dead / manual alive" is the wrong mental model.** An undetected actor stays clickable, but `Activities/Attack.cs:147` sets `useLastVisibleTarget = targetIsHiddenActor || !target.IsValidFor(self)` and `:164` then returns true — ending the activity — when that last-visible target is invalid. **`forceAttack` does not appear anywhere in that path**, and `AttackBase.AttackTarget` (`:657-674`) carries no visibility gate of its own, so a manual order on an undetected actor is accepted and then quietly does nothing. Visibility splits into two comparisons and they are not interchangeable: **cell** queries about fog and exploration are strictly-greater (`Traits/Player/MapLayers.cs:579`, `IsVisible`, `ResolvedVisibility[puv] > visibility`), while **actor detection** is non-strict (`MapLayers.IsDetected`, reached via `Detectable`) — a matching observer strength reveals. Shadow is subtracted from the OBSERVER and floored at 1 (`:371-374`). A unit already at the correct range with blocked line of sight therefore queues a move that completes instantly having gone nowhere, and re-queues it forever: **the LOS term that created the need is invisible to the activity meant to satisfy it.** No guard has been added. - **Becoming idle CONSUMES `SharedRandom` — so a change to *whether* a unit idles is a determinism change, not only a behaviour change.** Idle is not a quiet state. `WithInfantryBody.TickIdle` draws **twice** per `Waiting → Idle` transition — `IdleSequences.Random(SharedRandom)` and `SharedRandom.Next(MinIdleDelay, MaxIdleDelay)` (`Render/WithInfantryBody.cs:206-207`) — gated on `IdleSequences.Length > 0`, which 12 soldier classes declare in `infantry.yaml`.
