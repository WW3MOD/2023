The influence stack is the fog-respecting bots' **fog-legal strategic substrate**: a per-player memory of where the enemy has been seen, projected into danger and territory fields, then consumed by the offense/heli/truck layers to route around threats and repoint attacks — all without reading ground truth through the fog. It is built in layers that are each **inert data** until a later stage consumes them. Byte-identity is guaranteed for every **non-participating** actor by construction; the participants are the two fog-respecting bots (`@experimental` + `@stable`) plus humans (fields for the overlay only, no behavioural consumer). `@stable` is a **frozen validated snapshot** of `@experimental` — since the 2026-08-02 parity promotion it participates and sets the same fog-legal consumer flags, and the tournament A/Bs live `@experimental` against it.

Stage naming (as in the source file headers): **0** heli standoff (engine-provided seam), **A** belief store, **B** danger fields, **C** control field + overlay, **D** heli danger nav, **E** ground danger nav, **F** strategic repoint.

## Participation & staggering — the shared gate

`InfluenceStack` (static helper, `InfluenceStack.cs`) is the single place that decides *who* gets a field and *when* it recomputes, so all three world layers narrow to the same participant set.

- **`Participates(player)`** (`InfluenceStack.cs:42-52`): a player reads the stack iff it is a combatant AND either a **fog-respecting bot** — `@experimental` OR `@stable` (`player.BotType == "experimental" || "stable"`, `:47-48`) — or a **human combatant** (`player.Playable`, `:51`). **`@stable` participates since the 2026-08-02 parity promotion** (`ExperimentalBotType`/`StableBotType`, `:35-36`, with the rationale inline at `:30-34`): it is a frozen validated snapshot of `@experimental`, so it builds the same fields and sets the same fog-legal consumer flags — the tournament A/Bs live `@experimental` against it. Only legacy/other bot profiles and non-combatants are excluded → they never build a field → byte-identical. Humans participate because the overlay is a human-facing read; the choice is a **sim-legal proxy for "the overlay viewer"** — it deliberately never reads `world.RenderPlayer` (that would make simulation depend on the render path and desync; see the header comment `:1-21`).
- **Staggering** (`GatherParticipants` `:52-58`, `SubInterval` `:62-69`): each layer round-robins **one participant per sub-slot** so no single tick rebuilds every player's field. Over `UpdateInterval` ticks each participant is refreshed exactly once.

## Stage A — belief store (`BeliefStore.cs`)

Per-player table of **believed enemy contacts** — the commander's memory of where the enemy was seen, not ground truth. Generalises the engine's `FrozenActorLayer` (which persists *structures* under fog) to mobile units, with confidence on top.

- **Contact lifecycle** lives in the pure, world-free `PlayerBeliefContacts` (`:61-114`, split out for NUnit like `UnitRoleResolver`'s facts/Classify split). Each recompute: `InjectLive` → `InjectFrozenStatics` → `ResolveUnobserved` (`:199-201`).
- **Fog discipline (no cheating, by construction):** live sightings come only from enemy actors the player can legally see right now — `Actor.CanBeViewedByPlayer(player)` + a `HealthInfo` filter to skip crates/props (`InjectLive`, `:216/:219`). Remembered statics come only from the player's own `FrozenActorLayer.FrozenActorsInRegion(…, onlyVisible: true)` — the fog-frozen last-seen set (`InjectFrozenStatics`, `:232`).
- **Static vs mobile decay is the load-bearing split.** Structures/defences are `IsStatic` (no `MobileInfo`, no `AircraftInfo`, `:273-278`) and are **exempt from decay** — they persist until verified gone, refreshed at the `FrozenConfidence` ceiling (60, `:132`) while their frozen ghost shows. Mobiles are NOT refreshed from ghosts; they **decay** by `MobileDecayPercent` (75%, `:136`) each recompute and drop below `MinConfidence` (15, `:139`) — "assumed still there, fading" (`DecayUnrefreshed`, `:98-113`).
- **Verified-clear:** a contact whose cell is currently visible (`player.MapLayers.IsVisible(c.Cell, 1)` — the `1` = "currently unfogged" threshold) with nothing live there is removed immediately (`ResolveUnobserved`, `:263`). A commander does not claim a cell he can see is empty.
- Fresh sighting confidence = 100 (`:126`); `UpdateInterval` = 25 ticks (`:123`); deterministic first-tick stagger offset = **0** (`:168`, NOT a `SharedRandom` draw — see Invariants).
- **Inert in Stage A:** pure data; the query seam is `Contacts(player)` (`:289`). Only Stage B reads it.

## Stage B — per-domain danger fields (`DangerFieldLayer.cs`)

Two per-player threat-projection channels stamped from the belief store: **ANTI-GROUND** (`DangerChannel.Ground`) and **ANTI-AIR** (`DangerChannel.Air`, `:51`). A contact contributes to a channel only if it carries a weapon that can hit that domain; each contact stamps a radial kernel whose **radius ← weapon range**, **intensity ← damage throughput × durability/cost weight × confidence**.

- **Air-channel discriminator** (`DangerKernelMath.WeaponThreatensAir`, `:135-138`): keys on `ValidTargets.Contains("Helicopter") || Contains("Air")` — a ground MG that lists `Helicopter` genuinely threatens our helis. This is **deliberately broader** than `UnitRoleResolver`'s `ShortRangeAD`, which keys on `"Air"` alone to find dedicated SAMs. *Danger = "what can shoot me down"; AD role = "what is a SAM".*
- **Ground discriminator** (`WeaponThreatensGround`, `:142-149`): any `ValidTarget` that is not an air-domain type. Air-domain types are `{Air, Helicopter, ICBM}` (`:130`) — the `ICBM` exclusion stops SAM/CRAM/interceptors (which carry `"Air, ICBM"`) stamping a spurious anti-ground aura at full AA range.
- **Kernel math** (`Compute`, `:153-175`): `radius = range/1024 + RangeBufferCells` capped at `MaxRadiusCells` (32); `intensity = throughput × durabilityWeight/DurabilityBase × confidence/100`, where `durabilityWeight = DurabilityBase(100) + HP/HealthDivisor(10) + Cost/CostDivisor(50)` — a tank's aura is denser than a rifleman's at equal throughput. Facts are read from **actual armament data at map load** (`ExtractKernelFacts`, `:481-517`; `WeaponInfo` resolved by `WorldLoaded`) — never hard-coded per unit.
- **Stamp** (`:350-379`): linear falloff `intensity × (r−d+1)/(r+1)` (`ISqrt` radial distance), **additive** across contacts so stamp order does not matter.
- **The territory baseline is GROUND-ONLY** — the single most load-bearing Stage-B fact. `DangerKernelMath.BaselineChannels(contribution) => (contribution, 0)` (`:182`): the baseline derives from believed enemy *ground* weapon reach, so it must not paint the air channel. `StampBaseline` writes both channels but the air term is 0 (`:453-457`). This is what lets Stage D use `AirDangerSafeThreshold = 0` as a literal "outside every believed AA envelope" test — a non-zero `AirDanger` reading means a believed weapon can *actually* shoot a heli there, not merely "near enemy ground" (the invariant is flagged in the code at `:177-181`).
- **Territory baseline projection** (`ProjectTerritoryBaseline`, `:390-420`, a Stage-C seam so it needs the control field): wherever the player believes the enemy *holds* ground (`ControlOwner.Enemy`), project a low-intensity danger (`BaselineIntensity` = 5, `:217`) outward to the believed enemy ground-weapon envelope — the "a spotter/drone could arrive" danger. It is **data-driven** — the envelope is the longest ground range among current believed contacts (`BelievedEnemyGroundEnvelopeCells`, `:466-477`), never a hard-coded "arty = 40 cells" (the fallback knob `BaselineFallbackEnvelopeCells` defaults **0 = off**, `:223`). Stamped only from the **frontier** of enemy territory (`IsBelievedEnemyFrontier`, `:424-430`), capped at `BaselineMaxProjectionCells` (24). Because it stamps **additively** across every frontier cell, a dense sector's baseline **stacks** and can exceed 40 easily — do not assume it is a small constant (this is why Stages E/F need thresholds *above* it and a strict-improvement rule, below).
- `UpdateInterval` = 25 (`:192`); deterministic stagger offset = **`UpdateInterval/3`** (`:292`). Query seam: `GroundDanger` / `AirDanger` / `Danger(channel)` (`:543-560`), `ActiveCells` (`:574`).

## Stage 0 — heli standoff (engine seam, `HelicopterStates` / `HelicopterSquadBotModule`)

Not part of the field pipeline, but the seam Stage D rides on. The engine *already* stands a hovering/sliding attack heli off at weapon range (`FlyAttack.cs:183-198`, `Fly.cs:187-190` — see [`architecture.md` §Attack standoff](architecture.md)); heli **overflight** was a bot-order artifact (a bare `Order("Attack", …)` at a single distant target). Stage 0 fixes it with a default-off `StandoffEngagement` flag (`HelicopterSquadBotModule.cs:64`): when on, the squad FSM issues `AttackMove` toward the target cell so `AutoTarget` engages the nearest in-range threat at standoff and only advances when clear (`HelicopterStates.cs:152-155/:395`). Guard: `BusyAttackMove` (`HelicopterStates.cs:213`) detects the nested `AttackMoveActivity` so re-issuing the order each tick doesn't cancel an in-progress `FlyAttack`. Off ⇒ `@stable`/controls/human byte-identical.

## Stage C — control field (`ControlField.cs`) + danger overlay (`DangerOverlay.cs`)

### Control field: believed territory

Per participating player, every coarse grid cell (`CellSize` = 2 map cells, `:177`) carries a believed-ownership **score**: `> 0` ours, `< 0` enemy, `|score| ≤ GrayBand` contested. Pure math in `ControlFieldMath` (`:93-168`, split for NUnit).

- **`ScoreAt` sign convention** (`:531`): **positive = ours, negative = enemy, 0 = no field**. `OwnerAt` buckets it via `Classify` (`:146-154`): `> GrayBand` → `Own`, `< −GrayBand` → `Enemy`, else `Contested`. `GrayBand` = 150 (`:205`).
- **Seed:** Voronoi by proximity to each player's public home beachhead (`SeedVoronoi` from `HomeLocation`, `:347-367`; `SeedScore` `:98-109`) — nearest home owns the cell at `±SeedStrength` (500, `:184`), a tie reads the contested midline (0). Home positions are public map facts, so seeding is not a fog leak. **Synthetic-scenario trap:** a map/rules block that strips `MapStartingLocations` leaves the spawn assigner null, so `Player.HomeLocation` falls back to `PlayerReference.HomeLocation` = `CPos.Zero` for BOTH sides (`Player.cs:182`); every cell is then equidistant from (0,0) ⇒ seeds Contested everywhere and the whole-map Voronoi wash vanishes, leaving only presence + site-anchor cells painted. Real play always assigns spawns, so this only bites demos — set `HomeLocation: x,y` explicitly per `PlayerReference` in the demo `map.yaml`.
- **Presence update** (`GatherPresence` `:386-420`, `UpdateScore` `:112-132`): own/allied **armed** units (`AttackBaseInfo` or `AutoTargetInfo`, `:402` — trucks/civilians don't hold ground) paint toward + (`+PresenceGain` = 250, `:190`); believed enemy contacts (from the belief store *only*, `:411-419`) erode toward − and eventually flip the sign (capture). Both present → actively contested, bled toward gray at `ContestErodePercent` (40%). Verified-clear → relax to gray immediately (`VerifiedClearErodePercent` = 100). No evidence → lingers, decaying at `PersistDecayPercent` (8%) so the front doesn't flicker. Clamped to `±MaxScore` (1000, `:187`).
- **Site anchors — the anchor-floor semantics (load-bearing for Stage F).** `IsSiteAnchor` = a non-mobile structure carrying `SupplyProviderInfo` OR `CaptureManagerInfo` (`:493-501`) — Supply Routes and capturable income/utility (derricks). Each recompute, `ApplyAnchors` (`:424-467`) re-asserts: home beachheads + own/allied site structures as **self** anchors, and **believed-enemy** site structures (from the belief store, fog-legal) as **enemy** anchors. `StampAnchor` (`:469-489`) floors a disc out to `AnchorRadiusCells` (4, `:211`): self anchors `Math.Max(score, +strength)`, enemy anchors `Math.Min(score, −strength)` (`ApplyAnchor`, `:137-143`), tapering `AnchorStrength(800) × (r−d+1)/(r+1)`. At grid distance 4 the taper still reads ≈ **−160** — below `−GrayBand` (150) — so **the whole radius-4 disc around any enemy site reads Enemy regardless of who surrounds it.** This is *why* Stage F must read the surrounding ring, not the target cell (below).
- **Verification memory:** `LastVerified[gx,gy]` records the tick a cell was last observed; `IsVerifiedFresh` (`:544-552`) returns true only within `StalenessWindow` (500 ticks) — the overlay's perishable green→gray relax.
- **Frontline contour = a binary half-plane split, not a sign flip** (`ControlFieldMath.IsFrontlineEdge`, `:168`). An edge between two grid cells is a frontline edge iff exactly one side classifies `Enemy`: `scoreA < −GrayBand != scoreB < −GrayBand`. Keyed on enemy-vs-not-enemy (believed-ours AND the contested no-man's-land both count as "our side") on purpose — the verified-clear rule relaxes every observed-empty cell to 0, opening a wide neutral buffer between the armies, and a strict ± sign-flip contour vanishes in that buffer (0 is neither sign), whereas the half-plane boundary is always a continuous closed contour around the believed-enemy region. Consumed **render-only** by `TerritoryOverlay` (hold-`T`) and `DangerOverlay` Control mode (`TerritoryOverlay.cs:241/:248`, `DangerOverlay.cs:178/:184`); no sim consumer.
- `UpdateInterval` = 25; deterministic stagger offset = **`UpdateInterval/2 + 1`** (`:283`).

### Danger overlay (`DangerOverlay.cs`) — dev, render-only

`/danger` chat command (`CommandName` = "danger", `:46`) cycles **Off → DangerGround → DangerAir → Control → Off** (`:75/:104`). Primary read is **safety, tri-state** (`DangerColor`, `:152-162`): danger > 0 → **red** (own units in a danger zone read red too); else recently observed (`IsVerifiedFresh`) → **green** (verified safe); else → **gray** (unobserved). `Control` mode demotes the control field to a secondary owner-colour/margin wash (`ControlColor`, `:165-181`). Render-only: `world.RenderPlayer ?? world.LocalPlayer`, reads the viewer's own layers (`:115`) — `RenderPlayer` is legal here because this is NOT sim code; OFF by default, never ships on hold-Space.

## Stage D — heli danger nav (`HeliDangerNav.cs`)

Pure-function navigation math over an **anti-air** danger sampler (`Func<CPos,int>`), split from `HelicopterStates` like the math classes above. Rides on Stage 0: `avoid = standoff && DangerFieldAvoidanceEnabled(owner)` (`HelicopterStates.cs:372`) — with standoff off there is no attack-move destination to steer, so avoidance is inert rather than conflicting. Gated by default-off `DangerFieldAvoidance` (`HelicopterSquadBotModule.cs:71`).

- **AA-safe leash** (`LeashedEngageCell`, `:71-95`): the cell nearest the target (expanding Chebyshev rings, fixed scan order) whose air-danger ≤ `AirDangerSafeThreshold` — fire from the AA-safe edge instead of diving onto a target buried in AA. The threshold defaults **0** (`HelicopterSquadBotModule.cs:75`), meaningful *only because* the air channel carries no baseline (Stage B).
- **Lateral detour** (`DetourWaypoint`, `:102-142`): when the straight approach's max air-danger (`PathMaxAirDanger`, `:47`) exceeds the threshold, pick the perpendicular midpoint offset (±`lateralCells` × {1,2}) whose two-leg worst-case is strictly lower — route around the SAM, don't fly through it.
- **Spike withdraw** (`SafestAirCellOnRing`, `:148-173`): the lowest-air-danger cell on a Chebyshev ring — a deterministic retreat toward the least-covered heading when a new AA lights up.
- Off-map/invalid cells are fed as `Impassable = int.MaxValue` (`:32`) so no search steers off the playable area. **Zero random draws** (see Invariants).

## Stage E — ground danger nav (`GroundDangerNav.cs`)

The Stage-D pattern for **ground** movers, deliberately kept a **separate** pure class (HeliDangerNav stays byte-identical). Two perceived behaviours reduce to ONE decision — `DetourWaypoint` (`:91-141`):

- **Flow around strongpoints** and **high-value movers pull back / go lateral / re-enter** are the same function: when the straight route's max ground-danger (`PathMaxGroundDanger`, `:58`) exceeds `safeThreshold`, insert the perpendicular waypoint (±`lateralCells` × {1..`maxSteps`}) whose two-leg worst-case is **strictly less** than direct (`worst < best`, seeded at `best = direct`, `:110/:132`).
- **The rear-lateral route EMERGES from the Stage-B/C gradient — it is not scripted.** Because the ground field carries the territory baseline (deep believed-enemy ground reads expensive, the friendly rear ~0), the exposure-minimising side of the detour *is* the rear; a larger `maxSteps` just pushes the safe waypoint deeper. There is no rear-seeking code.
- **Correctness against the ambient baseline is the strict-improvement rule, not the threshold.** The baseline stacks additively and will exceed any fixed threshold in a contested approach, so the threshold is only a cheap early-out. Where danger is roughly *uniform* every lateral candidate reads the same worst-case as direct, nothing beats it, and the function returns null → go direct. A dogleg is emitted only where a genuine local peak makes a lateral lane measurably cheaper.
- **Waypoint passability is guarded, the line-walk is not.** A rear water/cliff cell reads `GroundDanger 0` (maximally "safe") and would be actively preferred, then the Move no-ops; so the chosen waypoint cell is filtered through a `waypointPassable` predicate (`:125`, a locomotor terrain check on the WAYPOINT ONLY). The line-walk sampler is deliberately left terrain-blind (feeding impassable line cells as Impassable would make a route merely clipping a water edge read max-exposed — the declared v2 terrain-flow problem), so a route whose straight legs cross unreachable ground is a documented v1 limitation left to the pathfinder.
- **Implementation is a two-leg queued order, not A* cost-field integration.** The consumer emits `AttackMove(waypoint)` then `AttackMove(target, queued)` (Move for trucks), so the A* layer is untouched; cost per request is O(steps·pathLen) sampler reads at the module's slow re-eval cadence (PoiOffensive 100 ticks, SupplyFollower 150). Tradeoff: a coarse single dogleg, not a true least-cost path (v1).

## Stage F — strategic repoint (`PoiMap.cs` + `PoiOffensiveBotModule.cs`)

Completes the `@experimental` fog migration for **attack-axis selection and expansion**: drops the omniscient threat term from the base offense score and re-derives it from the **believed** control + danger fields.

- **The omniscient read that was migrated is the THREAT term, not POI discovery.** The single omniscient grid feeding attack-axis selection is `PoiMap.SampleThreat` → `InfluenceMap.GetEnemyInfluence` (`InfluenceMap.Recompute` scans `world.Actors` with no fog check). POI *discovery* (`PoiMap.Discover`) also scans `world.Actors` but only finds **static structures** whose locations are public map facts — so it is left as-is; the belief store re-derives mobile-unit threat.
- **Suppress-in-PoiMap, reshape-in-module.** `GetOffensiveTargets(perspective, bool suppressOmniscientThreat = false)` (`PoiMap.cs:297`): when true it sets `enemyInfluence = 0` → threat-neutral safe bucket AND skips the `GetEnemyInfluence` snapshot entirely (`:296/:351`), so the repoint path never touches the omniscient grid. **Default false ⇒ byte-identical** for every caller that doesn't opt in (control-bot `MountedTransportBotModule` ×2); since `stable-0802` **both** offense twins opt in (`StrategicRepointEnabled: true` — `@experimental` `ai.yaml:274`, `@stable` `:991`). The base `ScoredPoi` score is a product `value × distFactor × threatFactor × ownershipMul` (`PoiScoring.Score`, `:596-597`) then `× bias/100` (`ApplyBias`, `:602-603`, the lossy truncation) — so suppressing at source and re-multiplying in the module beats dividing the omniscient factor back out.
- **Consumer** (`PoiOffensiveBotModule.RescaleByBelievedFields`, `:699-759`): gated `repoint = StrategicRepointEnabled && controlField != null` (`:504`, inert if no control field). Two pure factors from `PoiOffenseMath`, then `mul = bop × dangerMul / 100` (`:726`), re-sorted with the same `PoiScoring.CompareForOrder` comparator PoiMap uses.
- **Balance-of-power reads the SURROUNDING RING, not the target's own cell — and this is not optional.** Every Attack/Pressure target is a site-anchor structure whose own cell (and a disc out to `AnchorRadiusCells`) is floored to ≈ −800 by the enemy anchor (Stage C) — so `ScoreAt(targetCell)` is *always* deeply enemy and the boost could never fire. `NeighborhoodControlScore(scoreAt, gx, gy, radius)` (`PoiOffenseMath` `:1556`) averages the 8 cardinal+diagonal cells at grid `radius = AnchorRadiusCells + 1` (`:708`) — one cell past the anchor footprint, so the floored disc is **excluded entirely** (the target's own cell is never sampled). `BalanceOfPowerFactor(neighborhoodScore, grayBand, boost, damp)` (`:1575`) then buckets on the **same `GrayBand` the control field classifies by** (`:701`): ring `> +GrayBand` (we hold the surroundings → encircled → PRESS, boost) / `< −GrayBand` (deep enemy → damp) / contested → neutral 100. An off-grid ring sample reads 0 (biasing edge targets toward neutral — a safe direction).
- **Believed danger is on a DIFFERENT scale than InfluenceMap.** `BelievedDangerFactor(groundDanger, mild, hostile, safeMul, mildMul, hostileMul)` (`:1591`) reads `DangerFieldLayer.GroundDanger` at the target cell and buckets safe/mild/hostile. Its thresholds (`BelievedDangerMildThreshold` = 40, `HostileThreshold` = 120, `PoiOffensiveBotModule.cs:188/:192`) are on the **danger-field throughput scale**, deliberately set *above* the territory-baseline intensity so ambient "deep enemy ground" danger doesn't damp every axis — only a genuine believed weapon envelope does. Reusing the InfluenceMap `ThreatMildThreshold` (20) here would class almost everything hostile.
- **All sub-multipliers default 100 (inert)** (`BopBoostMultiplier`/`BopDampMultiplier`/`BelievedDanger*Multiplier`, `:177-204`), so a bare `StrategicRepointEnabled: true` changes only the threat *source*, not the ranking, until the YAML supplies active values. Current `@experimental` tuning (`ai.yaml:275-281`, 2026-07-24): boost ×150, damp ×60, believed-danger safe ×100 / mild ×60 / hostile ×20 (`DangerFieldRouting: true` at `:263`, `StandoffEngagement`/`DangerFieldAvoidance` at `:855/:859`).

## Invariants (load-bearing — do not break)

- **Zero `SharedRandom`/`LocalRandom` draws in the entire stack.** The always-on world layers (BeliefStore/DangerFieldLayer/ControlField tick for *every* profile) must not draw from the synced `SharedRandom` at load to self-stagger — that would shift the RNG stream for `@stable`/control games and break replay/benchmark byte-identity even though the trait is behaviour-inert. Instead each uses a **distinct deterministic offset**: BeliefStore **0** (`BeliefStore.cs:168`), DangerFieldLayer **Interval/3** (`DangerFieldLayer.cs:292`), ControlField **Interval/2+1** (`ControlField.cs:283`). The nav/scoring math is integer walks over fixed candidate orders with iteration-order tie-breaks — zero draws (`HeliDangerNav.cs:18-21`, `GroundDangerNav.cs`, `PoiOffenseMath` fixed `NeighborhoodDirections` `:928-931`).
- **Byte-identity when flags off.** Every consumer flag defaults off/inert and every `PoiMap`/nav seam has a default that reproduces the frozen path, so non-`@experimental` profiles and the `@stable` twin are byte-identical.
- **Two gating patterns — know which applies.** For a consumer on a **per-profile** trait instance (e.g. `PoiOffensiveBotModule@experimental` is already `RequiresCondition: enable-ai-experimental`, and `@stable` is a separate instance), a default-off flag set only on the experimental block is sufficient. For a consumer bolted onto a **shared** instance (`SupplyFollowerBotModule@supply` on `enable-ai-any`, fired for Normal/Rush/Turtle too), the flag alone is not enough — it must be double-gated `Info.Flag && InfluenceStack.Participates(player)` (`SupplyFollowerBotModule.cs:109`). Copy the double-gate for any future consumer on a shared module.
- **The territory baseline feeds the GROUND channel only** (`DangerKernelMath.BaselineChannels`, `DangerFieldLayer.cs:182`) — the Stage-D air consumer depends on `AirDanger == 0` meaning "AA-clear".

## @experimental consumers beyond D/E/F

The nav/repoint stages (D/E/F) are not the only fog-legal consumers. Several later `@experimental` levers read the belief/danger/control fields directly. Each is a **default-off flag on a per-profile trait instance** (the first gating pattern above — `@stable`/normal never touch the field), all enabled in current `@experimental` tuning (`ai.yaml`, as of 2026-07-31):

- **Capture escort right-sizing** (`CaptureCoordinatorBotModule`, `EscortTierSizingEnabled`, `:188`). `ResolveEscortTier` (`:1018`) buckets a capture target None/Light/Full from the ring-averaged `ControlField` score + `DangerFieldLayer.GroundDanger` + distance-from-own-SR, via the pure `EscortSizingMath.Resolve`. It is **reduction-only** — applied only to targets NOT already flagged contested, it can only *lower* the escort (None ⇒ the technician goes alone, no combat units reserved) — so it composes with, never fights, the contest bump below. Freed units need no redirection system: escorts are issued as a tick-local grouped `AttackMove` and are never committed to the `PoiGoalGuard` ledger, so an idle escort is immediately re-eligible for the offense. Reads the **ring** at grid `AnchorRadiusCells + 1`, not the target cell (the site anchor floors its own disc — same geometry as Stage F).
- **Contest-aware capture support** (`CaptureCoordinatorBotModule`, `ContestAwareSupportEnabled`, `:163`). `IsContestedNeighbourhood` (`:944`) bumps the escort 2→4 and pre-summons defenders when a target's surroundings read contested. Its predicate is `GroundDanger > threshold` **OR** the control ring reads specifically `Enemy` — deliberately NOT "`OwnerAt != Own`": `ControlFieldMath.Classify` buckets score-0 (unobserved / no-man's-land) as `Contested`, so a "gray = contested" predicate would fire on nearly every open-ground derrick and collapse the very distinction the lever draws. (The believed-danger channel has no such problem — it reads above baseline only where a believed weapon envelope actually reaches.)
- **Threat-reactive SR-defense purchasing** (`AdaptiveProductionBotModule`, `SupplyRouteDefenseEnabled`, `:56`). Classifies believed contacts near any owned SR from `BeliefStore.Contacts` by their own actor type (Air / Armor / Infantry), accumulates believed value per class, and pre-buys the matched counter pool — bypassing the `MinEnemySightings` gate a 2-tank rush never trips. The belief store is the correct seam because the scalar `DangerFieldLayer.GroundDanger` deliberately discards attacker identity (a lone rifleman saturates any "armor" threshold; `WeaponThreatensGround` keys on the *target* domain, so an attack heli stamps the ground channel) — "what should I build to counter this" needs identity, which only the belief store retains.
- **Frontier-distance standoff** (`PoiOffensiveBotModule` + `HelicopterSquadBotModule`, `MinFrontierDistanceCells`, default 0). `ControlField.RecomputePlayer` computes a `DistanceToEnemyFrontier` multi-source BFS (seeded row-major from every `Classify==Enemy` cell, 4-connectivity, capped at `MaxFrontierDistanceCells`) at the tail of the score-field recompute — so it rides the same per-player `Participates` gate + `UpdateInterval` cadence with no new timer, and `@stable`/normal never build the array (they get no `PlayerControl`). Two consumers hold behind that front: the fires echelon anchor (`PoiOffensiveBotModule.cs:1028`) and the heli engage cell both reduce to one pure decision — `FrontierStandoffMath.RearwardSteps` (`FrontierStandoffMath.cs:59`) walks rearward along the away-from-target axis one coarse cell per hop until frontier distance ≥ min, bounded by a small step budget so it is never a free search. The step is **Chebyshev-scaled** (max-norm) so a diagonal hop still crosses a whole coarse cell instead of under-advancing ~0.7 of one. Off-grid cells read the same "far" sentinel a populated-but-enemy-free field gives, so `RearwardSteps` takes an explicit `onGrid` predicate and hard-stops at the boundary rather than trusting the sampler; `FrontierDistanceAt` returning that sentinel for no-field/off-grid ⇒ zero push ⇒ byte-identical until the field is populated.
- **Transport standoff drop** (`MountedTransportBotModule`, `BelievedDangerStandoff`, `:102`). The drop-off picker still selects its candidate from the omniscient `GetFrontline`/`GetFriendlyInfluence` (see Known gaps), but `ApplyStandoff` (`:621`) then backs the chosen cell out of the believed anti-ground danger envelope (`DangerFieldLayer.GroundDanger`) — a fog-legal *post-adjust*, an identity pass-through when the field is absent (`@poi`/frozen twin). Paired with a pickup corridor (`PickupCorridorCells`).

## Frontline reachability & staging (Phases 0–4)

The radial danger/control fields are terrain-blind by construction, so a river-split front, crossings-as-chokepoints, and "where do idle units muster" were all unrepresented (the old §Known-gaps "terrain-aware v2"). Phases 0–4 add a terrain/frontier layer that the `@experimental` offense module reads. **Every lever is a default-off Info flag on `PoiOffensiveBotModule` and reproduces the frozen path when off** — so `@stable`/legacy stay byte-identical even though `@stable` now participates in the shared world layers.

- **CrossingMap** (`Traits/World/CrossingMap.cs`) — a map-static geometry layer built once at load. `CrossesGroundBarrier(a, b)` (`:459`) walks the straight SR→POI line and flags any cell whose terrain type is in `WaterTerrainTypes = {Water, River}` (`:336`) — keyed on **water terrain type, not foot-impassability**, so cliffs/walls are not misread as a barrier (`:373-377`). It exposes two crossing sources that avenue-mapping must union: **`CrossingCells`** (`:453`) = intact land spans across water, and **`Crossings`** (`:427`) = `GroundCrossing` structs for *repairable/destroyed-bridge* huts (their cells are water, so the span detector never adds them — they live only here, carrying the hut's `CellX/CellY`). `CrossingMapInfo.GroundLocomotor` (`:324`, default `"tracked"`) picks the reference locomotor for component classification.
- **Locomotor water table is the load-bearing subtlety** (`mods/ww3mod/rules/world.yaml`). "The river as a barrier" is NOT a component-count of the army locomotor, because the common ground locomotors treat water differently: `Locomotor@TRACKED` (`:153`) has `River: 10` (nonzero ⇒ **fords rivers**), `Locomotor@LIGHTTRACKED` (`:126`) has `RiverShallow: 75` but **no `River`** (river-blocked — this is the bulk of the offense free pool: bradley/m109/m270), and `Locomotor@FOOT` (`:28`) has **no `River`/`Water`** (deep water impassable) but `Rock: 50` (crosses mountains). So the `tracked` graph over-estimates reachability for the real army, and mountains — not the river — split the `tracked` graph. Barrier detection therefore keys on the water TERRAIN TYPE directly rather than any locomotor's passability. On a river map where all POIs sit in one fordable `tracked` component, the *binary reachability* factor is inert and the active lever is DISTANCE (next bullet).
- **Through-crossing distance** (`PoiReachabilityMath.ThroughCrossingDistanceCells`, `Traits/BotModules/PoiReachability.cs:71`) replaces a far-bank POI's crow-flies distance with the SR→crossing→POI detour (`sum of two legs, clamped ≥ direct`). Wired into scoring as a gated `Func<CPos,int?>` provider built at `PoiOffensiveBotModule.cs:768-774` (guarded `ReachabilityGatingEnabled && crossingMap != null`, default false `:214`) and passed into `PoiMap.GetOffensiveTargets` (`:778`); **null ⇒ exact Euclidean ⇒ byte-identical off**. This de-concentrates the axis distribution: far-bank central-crossing POIs stop scoring as if adjacent, so the bot secures its own bank + pressures the enemy SR instead of lunging across the river.
- **Forward staging** (`ForwardStagingMath.StagingCell`, `Traits/BotModules/ForwardStagingMath.cs:88-138`; gate `ForwardStagingEnabled`, default false `:363`). Musters the idle free pool forward off the SR road by **steepest descent on `ControlField.FrontierDistanceAt`** (the frontier-distance BFS gradient — the SR sits deep in the rear at large distance; each descent step goes toward the nearest front), halting `StagingStandoffCells` short of the line and never stepping into a danger cell above threshold. A **flat field** (no believed enemy) has no improving neighbour ⇒ returns the SR ⇒ inert. This is NOT `FrontierStandoffMath.RearwardSteps` (which walks *away* from a known target); the free pool is target-less, so the descent gradient is the natural primitive. **Correction to earlier research:** the free pool is not a standing reservoir — `AllocateProportional` drains it to 0 most evals (`free==0` logged every eval in the small-army case), so staging only bites when units are WITHHELD (a losing axis skipped by `NoReinforceLostFights`, an under-min release, a retreating batch no axis reclaims) — e.g. large late-game armies or a sustained losing axis.
- **Retreat-oscillation damper** (`RetreatDamperMath`, `Traits/BotModules/RetreatDamperMath.cs`; gate `RetreatDamperEnabled`, default false `:399`). The base retreat FSM (`CombatRetreatMath.Step`) already had ENTRY hysteresis (a sustained losing streak + asymmetric re-engage band), so the damper does NOT touch entry. It adds the missing anti-oscillation pieces: a post-retreat **re-advance DWELL** and an **advance-strength floor**. The load-bearing safety property: `StepReadvanceHold` returns 0 whenever the axis is Retreating (`:55-56`) — the damper can only delay a RE-advance or filter massing, **never delay a genuine withdrawal**.
- **Frontline strength profile** (`FrontlineProfileMath`, `ControlField.cs:280`; gate `FrontlineProfileEnabled`, default false `PoiOffensiveBotModule.cs:420`). An explicit per-sector OWN/ENEMY strength profile + weakest-enemy-sector query built on top of the control field. **This is the case that forces the gating recipe below** — see next section's note.
- **Man-the-line + weakest-point + sector posture-hold** (`FrontlineAllocationMath`; three default-off gates on `PoiOffensiveBotModule` / `LayeredDefenceBotModule`). Three numbers-only decisions over the Phase-4 profile: (a) **man-the-line** (`AllocateAcrossAvenues`, consumed at `LayeredDefenceBotModule.cs:585`) spreads a reserve budget across crossing avenues — COVERAGE first (every avenue whose believed enemy strength ≥ `ManTheLineMinThreat` gets one picket, enemy-desc/index-asc order) then largest-remainder (Hamilton) MASS weighted by `max(0, enemy−own)`, so surplus concentrates where we are outnumbered while a sector we hold keeps only its picket; (b) **weakest-point bias** (`WeakestSectorBiasFactor`, gate `WeakestPointBiasEnabled` `:431`) a ×100 score MULTIPLIER (inert at 100) boosting an axis whose target sits in the believed-thinnest enemy sector; (c) **sector posture-hold** (gate `SectorPostureHoldEnabled` `:447`) HOLDS an axis whose target sector reads believed-enemy ≥ `SectorPostureHoldRatioPct`% (default 200) of our own strength there. **The posture-hold "never blocks a genuine retreat" guarantee is POSITIONAL, not conditional:** `CommitAndOrder` runs three fall-back gates *in order* — genuine retreat (`:1622`, RETURNS for a `Retreating` axis) → retreat damper (`:1639`) → posture-hold (`:1653`) — so placing posture-hold AFTER the retreat gate that already returned means it can only ever fire on a NON-retreating axis, with no re-check. All three reuse the SAME `OrderRetreat(stagingAnchor ?? rallyCell)` grouped fall-back (one order stream that composes with the retreat FSM instead of fighting it) and must RETURN before the mission-commitment snapshot (`:1671`), or a held axis marked `Committed` would let `PartitionHeldAxes` freeze it holding forever. A target's frontier sector is a pure column-bucket of its map-cell X (`SectorOfTargetCell` → `FrontlineProfileMath.SectorOfMapCellX`, `:1244`), shared by weakest-point and posture-hold and needing nothing from the ControlField internal grid. `ControlField.AvenuesForSector` ALLOCATES a fresh `List` per call (`:977-979`), so the man-the-line consumer reads `ControlField.Avenues` (map-static, deterministically ordered) ONCE per scan and buckets in one pass (`TryBuildAvenueData`), never per-unit.
- **Engineer route-opening** (`EngineerRouteOpenBotModule`, gate `RouteOpenEnabled`, default false; declared only in the `@experimental` block). The one Phase that MANUFACTURES a new land axis rather than spending the force it has: when the weakest enemy sector's avenue is a REPAIRABLE destroyed bridge (`CrossingStatus.Repairable`), dispatch an `e6` (`RepairsBridges`) with the `RepairBridge` order plus a small free-pool combat screen, stake both in the shared `PoiGoalGuard` ledger (engineer under `bridge-repair:<hutId>`, each screen unit under `bridge-screen:<hutId>` — the same `CommitOnOrderMath.ShouldCommit` gate every executor uses), and on success release everyone so the now-intact avenue folds back into Phase-5 man-the-line for free (no separate attack path). Opts THIS player into the frontline profile via `RequestFrontlineProfile` (the per-player recipe below). Two load-bearing facts: **(1)** a repairable avenue's `Cell` IS the bridge hut's `Location` — `CrossingMap.RevalidateCrossings` records the repairable `GroundCrossing` with `CellX/CellY = hut.Location` (`CrossingMap.cs:744-745`) and `ControlField.AddAvenue` (`:829`) carries it into `FrontlineAvenue.Cell`, so the hut is resolved by exact `a.Location == avenue.Cell` over `world.Actors` filtered on `LegacyBridgeHutInfo`/`BridgeHutInfo`, no hut→avenue map; the engineer is identified by TRAIT (`HasTraitInfo<RepairsBridgesInfo>()`), never a name list. **(2)** the `e6` uses `EnterBehaviour.Dispose`, so it is CONSUMED at hut-entry while the bridge repairs — the mission must gate "repair in progress" BEFORE its engineer-died failure check (same ordering discipline as posture-hold); see [conventions.md §Engine behaviors that surprise](conventions.md).

**Gating recipe — a NEW per-`@experimental` read on a SHARED world layer must be a per-player OPT-IN, not a world-trait/`world.yaml` global.** Because `@stable` (and humans) now `Participate`, every one of them gets a `PlayerControl` and runs `RecomputePlayer` — so gating new work by a flag on `ControlFieldInfo` set in `world.yaml` would build it for `@stable` and humans too, breaking the frozen-snapshot control and the byte-identity of the overlay read. The fix (`FrontlineProfileMath`): `ControlField.RequestFrontlineProfile(player)` (`:933`) adds the player to a `HashSet<Player> profileEnabled` (`:500`); `RecomputePlayer` builds the profile only for members (`:579`). The master flag is the per-profile `PoiOffensiveBotModule.FrontlineProfileEnabled` (default false), and only the `@experimental` module calls `RequestFrontlineProfile` — `@stable`/human never opt in ⇒ zero profile work ⇒ byte-identical. This is a third gating pattern on top of the two in §Invariants: **per-player opt-in for reads bolted onto an always-on shared world layer that `@stable` now shares.**

## Known gaps / deferred

- **Capture + garrison threat is MIGRATED (item 24, merge `646515bd`); the omniscient callers that remain are deliberate.** Capture ordering (`CaptureCoordinatorBotModule`, gate `StrategicCaptureRepointEnabled`, default false `:155`) and garrison ordering+sizing (`PoiGarrisonBotModule`, gate `DefendRepointEnabled`, default false `:106`) now re-derive threat from the **believed** `DangerFieldLayer.GroundDanger` instead of the omniscient `InfluenceMap`. Each asks PoiMap for a threat-neutral base via the `suppressOmniscientThreat` seam (`GetCaptureTargets`/`GetDefendTargets`, `PoiMap.cs:266/:391`), which **skips `SampleThreat` entirely** (`PoiMap.cs:427/:495`) — that method's `FindActorsInCircle` fallback (`:531-535`) is itself omniscient, so nulling the layer is not enough; the sampler must be skipped. Then a fog-legal factor is re-applied: capture DAMPS (`RescaleCaptureByBelievedDanger` → `PoiScoring.BelievedThreatFactor`, `CaptureCoordinatorBotModule.cs:578-597`), garrison RAISES (the mirror; `RescaleDefendByBelievedDanger` → `PoiScoring.BelievedDefendFactor`, `PoiGarrisonBotModule.cs:374-393`). **Garrison is TWO reads, not one:** ordering (`:238`) AND size — `TargetThreat` (`:360-366`) reads the believed danger carried back in the repurposed `EnemyInfluence` field, and the size bump keys on `BelievedDangerHostileThreshold` (not the InfluenceMap `ThreatMildThreshold`) via `sizeThreatThreshold` (`:289`). Both gates default off on the engine class ⇒ @stable/normal byte-identical; enabled in `@experimental` tuning (`ai.yaml:180` capture, `:309` garrison, as of 2026-07-29). **Still deliberately omniscient (not scoped for migration):** `LayeredDefenceBotModule` (`GetFriendlyInfluence`/`GetEnemyInfluence` `:248-249`, `GetFrontline` `:234`), `MountedTransportBotModule` (`GetFrontline` `:550`, `GetFriendlyInfluence` `:554` — but note its drop cell is now *post-adjusted* off the believed danger field when `BelievedDangerStandoff` is on, see [§consumers beyond D/E/F](#experimental-consumers-beyond-def); the omniscient read only picks the candidate cell, not the final drop), and the render-only debug `FrontlineOverlay` (`GetFrontline` `:77/:79` — not sim code, and distinct from the `ControlField`-based `IsFrontlineEdge` contour in Stage C).
- **The Stage-F benchmark re-baseline is RUN** (2026-07-29 — `WORKSPACE/ai-bench/runs/260728_rebaseline_result.md`, instrument `main @ e5b7bbcc`, post-item-26/28). 40 measured + 20 cal matches. With item-24 belief-repoint held OFF (the clean zero per user decision) and item-25 `StrategicRepointEnabled` ON, `@experimental` **underperforms `@stable`** on both rungs (S2 net-swing median ≈ −$1,425; S1 win 3–7), a regression vs the pre-26/28 `260721` "Exp ≈ Stable" baseline attributed to the global item-26/28 changes. Item-24 gate-enablement pricing is a SEPARATE later A/B against this zero. (Note: item-24 gates were found shipped **ON** in `ai.yaml:180/:309` — flagged to user; the re-baseline forced them off temporarily to exclude item-24 from the zero.)
- **Danger kernels are radial v1** (`DangerFieldLayer.cs:24-26`); terrain-aware *flow* (routing the danger field itself around a river) is still v2, and the Stage-E line-walk terrain-blindness (above) is the same boundary. The **reachability/crossing** side of that gap is now partially addressed by the default-off Phases 0–4 layer (see §Frontline reachability & staging) — a river-split front and crossings-as-chokepoints are represented for POI distance/scoring, but the danger *kernels* remain radial.
