# The @experimental influence stack (Stages 0 + A–F)

> Verified against code 2026-07-24 at `main @ b93eda58` (stack code-complete; final merge `36bd3b9e`). Every claim below cites the file:line it was checked against. The design docs (`WORKSPACE/plans/260722_influence_stack_design.md`, `260721_terr_offense_bias.md`) are secondary — where a plan and the code disagree, the code wins.
>
> Curation update 2026-07-29 at `main @ e5b7bbcc`: the §Known gaps capture/garrison item was re-verified and rewritten after item 24 shipped (merge `646515bd` — capture/garrison threat migrated to the belief-side danger field). Other sections retain the 2026-07-24 verification.

The influence stack is the `@experimental` bot's **fog-legal strategic substrate**: a per-player memory of where the enemy has been seen, projected into danger and territory fields, then consumed by the offense/heli/truck layers to route around threats and repoint attacks — all without reading ground truth through the fog. It is built in layers that are each **inert data** until a later stage consumes them, and it is **byte-identical for every non-`@experimental` profile** by construction.

Stage naming (as in the source file headers): **0** heli standoff (engine-provided seam), **A** belief store, **B** danger fields, **C** control field + overlay, **D** heli danger nav, **E** ground danger nav, **F** strategic repoint.

## Participation & staggering — the shared gate

`InfluenceStack` (static helper, `InfluenceStack.cs`) is the single place that decides *who* gets a field and *when* it recomputes, so all three world layers narrow to the same participant set.

- **`Participates(player)`** (`InfluenceStack.cs:38-48`): a player reads the stack iff it is a combatant AND either an `@experimental` bot (`player.BotType == "experimental"`, `:33/:44`) or a **human combatant** (`player.Playable`, `:47`). Normal/Rush/Turtle/`@stable` bots are excluded → they never build a field → byte-identical. Humans participate because the overlay is a human-facing read; the choice is a **sim-legal proxy for "the overlay viewer"** — it deliberately never reads `world.RenderPlayer` (that would make simulation depend on the render path and desync; see the header comment `:1-21`).
- **Staggering** (`GatherParticipants` `:52-58`, `SubInterval` `:62-69`): each layer round-robins **one participant per sub-slot** so no single tick rebuilds every player's field. Over `UpdateInterval` ticks each participant is refreshed exactly once.

## Stage A — belief store (`BeliefStore.cs`)

Per-player table of **believed enemy contacts** — the commander's memory of where the enemy was seen, not ground truth. Generalises the engine's `FrozenActorLayer` (which persists *structures* under fog) to mobile units, with confidence on top.

- **Contact lifecycle** lives in the pure, world-free `PlayerBeliefContacts` (`:61-114`, split out for NUnit like `UnitRoleResolver`'s facts/Classify split). Each recompute: `InjectLive` → `InjectFrozenStatics` → `ResolveUnobserved` (`:199-201`).
- **Fog discipline (no cheating, by construction):** live sightings come only from enemy actors the player can legally see right now — `Actor.CanBeViewedByPlayer(player)` + a `HealthInfo` filter to skip crates/props (`InjectLive`, `:216/:219`). Remembered statics come only from the player's own `FrozenActorLayer.FrozenActorsInRegion(…, onlyVisible: true)` — the fog-frozen last-seen set (`InjectFrozenStatics`, `:232`).
- **Static vs mobile decay is the load-bearing split.** Structures/defences are `IsStatic` (no `MobileInfo`, no `AircraftInfo`, `:273-278`) and are **exempt from decay** — they persist until verified gone, refreshed at the `FrozenConfidence` ceiling (60, `:132`) while their frozen ghost shows. Mobiles are NOT refreshed from ghosts; they **decay** by `MobileDecayPercent` (75%, `:136`) each recompute and drop below `MinConfidence` (15, `:139`) — "assumed still there, fading" (`DecayUnrefreshed`, `:98-113`).
- **Verified-clear:** a contact whose cell is currently visible (`player.MapLayers.IsVisible(c.Cell, 1)` — the `1` = "currently unfogged" threshold) with nothing live there is removed immediately (`ResolveUnobserved`, `:263`). A commander does not claim a cell he can see is empty.
- Fresh sighting confidence = 100 (`:126`); `UpdateInterval` = 25 ticks (`:123`); deterministic first-tick stagger offset = **0** (`:168`, NOT a `SharedRandom` draw — see Invariants).
- **Inert in Stage A:** pure data; the query seam is `Contacts(player)` (`:289`). Only Stage B reads it.

## Stage B — per-domain danger fields (`DangerFieldLayer.cs`)

Two per-player threat-projection channels stamped from the belief store: **ANTI-GROUND** (`DangerChannel.Ground`) and **ANTI-AIR** (`DangerChannel.Air`, `:51`). A contact contributes to a channel only if it carries a weapon that can hit that domain; each contact stamps a radial kernel whose **radius ← weapon range**, **intensity ← damage throughput × durability/cost weight × confidence**.

- **Air-channel discriminator** (`DangerKernelMath.WeaponThreatensAir`, `:135-138`): keys on `ValidTargets.Contains("Helicopter") || Contains("Air")` — a ground MG that lists `Helicopter` genuinely threatens our helis. This is **deliberately broader** than `UnitRoleResolver`'s `ShortRangeAD`, which keys on `"Air"` alone to find dedicated SAMs. *Danger = "what can shoot me down"; AD role = "what is a SAM".*
- **Ground discriminator** (`WeaponThreatensGround`, `:142-149`): any `ValidTarget` that is not an air-domain type. Air-domain types are `{Air, Helicopter, ICBM}` (`:130`) — the `ICBM` exclusion stops SAM/CRAM/interceptors (which carry `"Air, ICBM"`) stamping a spurious anti-ground aura at full AA range.
- **Kernel math** (`Compute`, `:153-175`): `radius = range/1024 + RangeBufferCells` capped at `MaxRadiusCells` (32); `intensity = throughput × durabilityWeight/DurabilityBase × confidence/100`, where `durabilityWeight = DurabilityBase(100) + HP/HealthDivisor(10) + Cost/CostDivisor(50)` — a tank's aura is denser than a rifleman's at equal throughput. Facts are read from **actual armament data at map load** (`ExtractKernelFacts`, `:481-517`; `WeaponInfo` resolved by `WorldLoaded`) — never hard-coded per unit.
- **Stamp** (`:350-379`): linear falloff `intensity × (r−d+1)/(r+1)` (`ISqrt` radial distance), **additive** across contacts so stamp order does not matter.
- **The territory baseline is GROUND-ONLY** — the single most load-bearing Stage-B fact. `DangerKernelMath.BaselineChannels(contribution) => (contribution, 0)` (`:182`): the baseline derives from believed enemy *ground* weapon reach, so it must not paint the air channel. `StampBaseline` writes both channels but the air term is 0 (`:453-457`). This is what lets Stage D use `AirDangerSafeThreshold = 0` as a literal "outside every believed AA envelope" test — a non-zero `AirDanger` reading means a believed weapon can *actually* shoot a heli there, not merely "near enemy ground" (the invariant is flagged in the code at `:177-181`).
- **Territory baseline projection** (`ProjectTerritoryBaseline`, `:390-420`, a Stage-C seam so it needs the control field): wherever the player believes the enemy *holds* ground (`ControlOwner.Enemy`), project a low-intensity danger (`BaselineIntensity` = 5, `:217`) outward to the believed enemy ground-weapon envelope — the "a spotter/drone could arrive" danger. It is **data-driven** — the envelope is the longest ground range among current believed contacts (`BelievedEnemyGroundEnvelopeCells`, `:466-477`), never a hard-coded "arty = 40 cells" (the fallback knob `BaselineFallbackEnvelopeCells` defaults **0 = off**, `:223`). Stamped only from the **frontier** of enemy territory (`IsBelievedEnemyFrontier`, `:424-430`), capped at `BaselineMaxProjectionCells` (24). Because it stamps **additively** across every frontier cell, a dense sector's baseline **stacks** and can exceed 40 easily — do not assume it is a small constant (this is why Stages E/F need thresholds *above* it and a strict-improvement rule, below).
- `UpdateInterval` = 25 (`:192`); deterministic stagger offset = **`UpdateInterval/3`** (`:292`). Query seam: `GroundDanger` / `AirDanger` / `Danger(channel)` (`:543-560`), `ActiveCells` (`:574`).

## Stage 0 — heli standoff (engine seam, `HelicopterStates` / `HelicopterSquadBotModule`)

Not part of the field pipeline, but the seam Stage D rides on. The engine *already* stands a hovering/sliding attack heli off at weapon range (`FlyAttack.cs:183-198`, `Fly.cs:187-190` — see [`architecture.md` §Attack standoff](architecture.md)); heli **overflight** was a bot-order artifact (a bare `Order("Attack", …)` at a single distant target). Stage 0 fixes it with a default-off `StandoffEngagement` flag (`HelicopterSquadBotModule.cs:64`): when on, the squad FSM issues `AttackMove` toward the target cell so `AutoTarget` engages the nearest in-range threat at standoff and only advances when clear (`HelicopterStates.cs:152-155/:395`). Guard: `BusyAttackMove` (`HelicopterStates.cs:213`) detects the nested `AttackMoveActivity` so re-issuing the order each tick doesn't cancel an in-progress `FlyAttack`. Off ⇒ `@stable`/controls/human byte-identical.

## Stage C — control field (`ControlField.cs`) + danger overlay (`DangerOverlay.cs`)

### Control field: believed territory

Per participating player, every coarse grid cell (`CellSize` = 2 map cells, `:177`) carries a believed-ownership **score**: `> 0` ours, `< 0` enemy, `|score| ≤ GrayBand` contested. Pure math in `ControlFieldMath` (`:93-168`, split for NUnit).

- **`ScoreAt` sign convention** (`:531`): **positive = ours, negative = enemy, 0 = no field**. `OwnerAt` buckets it via `Classify` (`:146-154`): `> GrayBand` → `Own`, `< −GrayBand` → `Enemy`, else `Contested`. `GrayBand` = 150 (`:205`).
- **Seed:** Voronoi by proximity to each player's public home beachhead (`SeedVoronoi` from `HomeLocation`, `:347-367`; `SeedScore` `:98-109`) — nearest home owns the cell at `±SeedStrength` (500, `:184`), a tie reads the contested midline (0). Home positions are public map facts, so seeding is not a fog leak.
- **Presence update** (`GatherPresence` `:386-420`, `UpdateScore` `:112-132`): own/allied **armed** units (`AttackBaseInfo` or `AutoTargetInfo`, `:402` — trucks/civilians don't hold ground) paint toward + (`+PresenceGain` = 250, `:190`); believed enemy contacts (from the belief store *only*, `:411-419`) erode toward − and eventually flip the sign (capture). Both present → actively contested, bled toward gray at `ContestErodePercent` (40%). Verified-clear → relax to gray immediately (`VerifiedClearErodePercent` = 100). No evidence → lingers, decaying at `PersistDecayPercent` (8%) so the front doesn't flicker. Clamped to `±MaxScore` (1000, `:187`).
- **Site anchors — the anchor-floor semantics (load-bearing for Stage F).** `IsSiteAnchor` = a non-mobile structure carrying `SupplyProviderInfo` OR `CaptureManagerInfo` (`:493-501`) — Supply Routes and capturable income/utility (derricks). Each recompute, `ApplyAnchors` (`:424-467`) re-asserts: home beachheads + own/allied site structures as **self** anchors, and **believed-enemy** site structures (from the belief store, fog-legal) as **enemy** anchors. `StampAnchor` (`:469-489`) floors a disc out to `AnchorRadiusCells` (4, `:211`): self anchors `Math.Max(score, +strength)`, enemy anchors `Math.Min(score, −strength)` (`ApplyAnchor`, `:137-143`), tapering `AnchorStrength(800) × (r−d+1)/(r+1)`. At grid distance 4 the taper still reads ≈ **−160** — below `−GrayBand` (150) — so **the whole radius-4 disc around any enemy site reads Enemy regardless of who surrounds it.** This is *why* Stage F must read the surrounding ring, not the target cell (below).
- **Verification memory:** `LastVerified[gx,gy]` records the tick a cell was last observed; `IsVerifiedFresh` (`:544-552`) returns true only within `StalenessWindow` (500 ticks) — the overlay's perishable green→gray relax.
- `UpdateInterval` = 25; deterministic stagger offset = **`UpdateInterval/2 + 1`** (`:283`).

### Danger overlay (`DangerOverlay.cs`) — dev, render-only

`/danger` chat command (`CommandName` = "danger", `:46`) cycles **Off → DangerGround → DangerAir → Control → Off** (`:75/:104`). Primary read is **safety, tri-state** (`DangerColor`, `:152-162`): danger > 0 → **red** (own units in a danger zone read red too); else recently observed (`IsVerifiedFresh`) → **green** (verified safe); else → **gray** (unobserved). `Control` mode demotes the control field to a secondary owner-colour/margin wash (`ControlColor`, `:165-181`). Render-only: `world.RenderPlayer ?? world.LocalPlayer`, reads the viewer's own layers (`:115`) — `RenderPlayer` is legal here because this is NOT sim code; OFF by default, never ships on hold-Space.

## Stage D — heli danger nav (`HeliDangerNav.cs`)

Pure-function navigation math over an **anti-air** danger sampler (`Func<CPos,int>`), split from `HelicopterStates` like the math classes above. Rides on Stage 0: `avoid = standoff && DangerFieldAvoidanceEnabled(owner)` (`HelicopterStates.cs:372`) — with standoff off there is no attack-move destination to steer, so avoidance is inert rather than conflicting. Gated by default-off `DangerFieldAvoidance` (`HelicopterSquadBotModule.cs:71`).

- **AA-safe leash** (`LeashedEngageCell`, `:71-95`): the cell nearest the target (expanding Chebyshev rings, fixed scan order) whose air-danger ≤ `AirDangerSafeThreshold` — fire from the AA-safe edge instead of diving onto a target buried in AA. The threshold defaults **0** (`HelicopterSquadBotModule.cs:75`), meaningful *only because* the air channel carries no baseline (Stage B).
- **Lateral detour** (`DetourWaypoint`, `:102-142`): when the straight approach's max air-danger (`PathMaxAirDanger`, `:47`) exceeds the threshold, pick the perpendicular midpoint offset (±`lateralCells` × {1,2}) whose two-leg worst-case is strictly lower — route around the SAM, don't fly through it.
- **Spike withdraw** (`SafestAirCellOnRing`, `:148-173`): the lowest-air-danger cell on a Chebyshev ring — a deterministic retreat toward the least-covered heading when a new AA lights up.
- Off-map/invalid cells are fed as `Impassable = int.MaxValue` (`:32`) so no search steers off the playable area. **Zero random draws** (see Invariants).

## Stage E — ground danger nav (`GroundDangerNav.cs`)

The Stage-D pattern for **ground** movers, deliberately kept a **separate** pure class (HeliDangerNav stays byte-identical). Two perceived behaviours reduce to ONE decision — `DetourWaypoint` (`:91-141`):

- **Flow around strongpoints** and **high-value movers pull back / go lateral / re-enter** are the same function: when the straight route's max ground-danger (`PathMaxGroundDanger`, `:58`) exceeds `safeThreshold`, insert the perpendicular waypoint (±`lateralCells` × {1..`maxSteps`}) whose two-leg worst-case is **strictly less** than direct (`worst < best`, seeded at `best = direct`, `:110/:132`).
- **The rear-lateral route EMERGES from the Stage-B/C gradient — it is not scripted.** Because the ground field carries the territory baseline (deep believed-enemy ground reads expensive, the friendly rear ~0), the exposure-minimising side of the detour *is* the rear; a larger `maxSteps` just pushes the safe waypoint deeper. There is no rear-seeking code.
- **Correctness against the ambient baseline is the strict-improvement rule, not the threshold.** The baseline stacks additively and will exceed any fixed threshold in a contested approach, so the threshold is only a cheap early-out. Where danger is roughly *uniform* every lateral candidate reads the same worst-case as direct, nothing beats it, and the function returns null → go direct. A dogleg is emitted only where a genuine local peak makes a lateral lane measurably cheaper.
- **Waypoint passability is guarded, the line-walk is not.** A rear water/cliff cell reads `GroundDanger 0` (maximally "safe") and would be actively preferred, then the Move no-ops; so the chosen waypoint cell is filtered through a `waypointPassable` predicate (`:125`, a locomotor terrain check on the WAYPOINT ONLY). The line-walk sampler is deliberately left terrain-blind (feeding impassable line cells as Impassable would make a route merely clipping a water edge read max-exposed — the declared v2 terrain-flow problem), so a route whose straight legs cross unreachable ground is a documented v1 limitation left to the pathfinder.
- **Implementation is a two-leg queued order, not A* cost-field integration.** The consumer emits `AttackMove(waypoint)` then `AttackMove(target, queued)` (Move for trucks), so the A* layer is untouched; cost per request is O(steps·pathLen) sampler reads at the module's slow re-eval cadence (PoiOffensive 100 ticks, SupplyFollower 150). Tradeoff: a coarse single dogleg, not a true least-cost path (v1).

## Stage F — strategic repoint (`PoiMap.cs` + `PoiOffensiveBotModule.cs`)

Completes the `@experimental` fog migration for **attack-axis selection and expansion**: drops the omniscient threat term from the base offense score and re-derives it from the **believed** control + danger fields.

- **The omniscient read that was migrated is the THREAT term, not POI discovery.** The single omniscient grid feeding attack-axis selection is `PoiMap.SampleThreat` → `InfluenceMap.GetEnemyInfluence` (`InfluenceMap.Recompute` scans `world.Actors` with no fog check). POI *discovery* (`PoiMap.Discover`) also scans `world.Actors` but only finds **static structures** whose locations are public map facts — so it is left as-is; the belief store re-derives mobile-unit threat.
- **Suppress-in-PoiMap, reshape-in-module.** `GetOffensiveTargets(perspective, bool suppressOmniscientThreat = false)` (`PoiMap.cs:288`): when true it sets `enemyInfluence = 0` → threat-neutral safe bucket AND skips the `GetEnemyInfluence` snapshot entirely (`:296/:351`), so the repoint path never touches the omniscient grid. **Default false ⇒ byte-identical** for every existing caller (control-bot `MountedTransportBotModule` ×2, the `@stable` offense twin). The base `ScoredPoi` score is a product `value × distFactor × threatFactor × ownershipMul` (`PoiScoring.Score`, `:596-597`) then `× bias/100` (`ApplyBias`, `:602-603`, the lossy truncation) — so suppressing at source and re-multiplying in the module beats dividing the omniscient factor back out.
- **Consumer** (`PoiOffensiveBotModule.RescaleByBelievedFields`, `:485-530`): gated `repoint = StrategicRepointEnabled && controlField != null` (`:317`, inert if no control field). Two pure factors from `PoiOffenseMath`, then `mul = bop × dangerMul / 100` (`:512`), re-sorted with the same `PoiScoring.CompareForOrder` comparator PoiMap uses.
- **Balance-of-power reads the SURROUNDING RING, not the target's own cell — and this is not optional.** Every Attack/Pressure target is a site-anchor structure whose own cell (and a disc out to `AnchorRadiusCells`) is floored to ≈ −800 by the enemy anchor (Stage C) — so `ScoreAt(targetCell)` is *always* deeply enemy and the boost could never fire. `NeighborhoodControlScore(scoreAt, gx, gy, radius)` (`PoiOffenseMath` `:945-952`) averages the 8 cardinal+diagonal cells at grid `radius = AnchorRadiusCells + 1` (`:494`) — one cell past the anchor footprint, so the floored disc is **excluded entirely** (the target's own cell is never sampled). `BalanceOfPowerFactor(neighborhoodScore, grayBand, boost, damp)` (`:964-971`) then buckets on the **same `GrayBand` the control field classifies by** (`:487`): ring `> +GrayBand` (we hold the surroundings → encircled → PRESS, boost) / `< −GrayBand` (deep enemy → damp) / contested → neutral 100. An off-grid ring sample reads 0 (biasing edge targets toward neutral — a safe direction).
- **Believed danger is on a DIFFERENT scale than InfluenceMap.** `BelievedDangerFactor(groundDanger, mild, hostile, safeMul, mildMul, hostileMul)` (`:980-988`) reads `DangerFieldLayer.GroundDanger` at the target cell and buckets safe/mild/hostile. Its thresholds (`BelievedDangerMildThreshold` = 40, `HostileThreshold` = 120, `PoiOffensiveBotModule.cs:172/:176`) are on the **danger-field throughput scale**, deliberately set *above* the territory-baseline intensity so ambient "deep enemy ground" danger doesn't damp every axis — only a genuine believed weapon envelope does. Reusing the InfluenceMap `ThreatMildThreshold` (20) here would class almost everything hostile.
- **All sub-multipliers default 100 (inert)** (`BopBoostMultiplier`/`BopDampMultiplier`/`BelievedDanger*Multiplier`, `:161-188`), so a bare `StrategicRepointEnabled: true` changes only the threat *source*, not the ranking, until the YAML supplies active values. Current `@experimental` tuning (`ai.yaml:232-239`, 2026-07-24): boost ×150, damp ×60, believed-danger safe ×100 / mild ×60 / hostile ×20 (`DangerFieldRouting: true` at `:221`, `StandoffEngagement`/`DangerFieldAvoidance` at `:722/:726`).

## Invariants (load-bearing — do not break)

- **Zero `SharedRandom`/`LocalRandom` draws in the entire stack.** The always-on world layers (BeliefStore/DangerFieldLayer/ControlField tick for *every* profile) must not draw from the synced `SharedRandom` at load to self-stagger — that would shift the RNG stream for `@stable`/control games and break replay/benchmark byte-identity even though the trait is behaviour-inert. Instead each uses a **distinct deterministic offset**: BeliefStore **0** (`BeliefStore.cs:168`), DangerFieldLayer **Interval/3** (`DangerFieldLayer.cs:292`), ControlField **Interval/2+1** (`ControlField.cs:283`). The nav/scoring math is integer walks over fixed candidate orders with iteration-order tie-breaks — zero draws (`HeliDangerNav.cs:18-21`, `GroundDangerNav.cs`, `PoiOffenseMath` fixed `NeighborhoodDirections` `:928-931`).
- **Byte-identity when flags off.** Every consumer flag defaults off/inert and every `PoiMap`/nav seam has a default that reproduces the frozen path, so non-`@experimental` profiles and the `@stable` twin are byte-identical.
- **Two gating patterns — know which applies.** For a consumer on a **per-profile** trait instance (e.g. `PoiOffensiveBotModule@experimental` is already `RequiresCondition: enable-ai-experimental`, and `@stable` is a separate instance), a default-off flag set only on the experimental block is sufficient. For a consumer bolted onto a **shared** instance (`SupplyFollowerBotModule@supply` on `enable-ai-any`, fired for Normal/Rush/Turtle too), the flag alone is not enough — it must be double-gated `Info.Flag && InfluenceStack.Participates(player)` (`SupplyFollowerBotModule.cs:109`). Copy the double-gate for any future consumer on a shared module.
- **The territory baseline feeds the GROUND channel only** (`DangerKernelMath.BaselineChannels`, `DangerFieldLayer.cs:182`) — the Stage-D air consumer depends on `AirDanger == 0` meaning "AA-clear".

## Known gaps / deferred

- **Capture + garrison threat is MIGRATED (item 24, merge `646515bd`); the omniscient callers that remain are deliberate.** Capture ordering (`CaptureCoordinatorBotModule`, gate `StrategicCaptureRepointEnabled`, default false `:127`) and garrison ordering+sizing (`PoiGarrisonBotModule`, gate `DefendRepointEnabled`, default false `:106`) now re-derive threat from the **believed** `DangerFieldLayer.GroundDanger` instead of the omniscient `InfluenceMap`. Each asks PoiMap for a threat-neutral base via the `suppressOmniscientThreat` seam (`GetCaptureTargets`/`GetDefendTargets`, `PoiMap.cs:266/:391`), which **skips `SampleThreat` entirely** (`PoiMap.cs:427/:495`) — that method's `FindActorsInCircle` fallback (`:531-535`) is itself omniscient, so nulling the layer is not enough; the sampler must be skipped. Then a fog-legal factor is re-applied: capture DAMPS (`RescaleCaptureByBelievedDanger` → `PoiScoring.BelievedThreatFactor`, `CaptureCoordinatorBotModule.cs:578-597`), garrison RAISES (the mirror; `RescaleDefendByBelievedDanger` → `PoiScoring.BelievedDefendFactor`, `PoiGarrisonBotModule.cs:374-393`). **Garrison is TWO reads, not one:** ordering (`:238`) AND size — `TargetThreat` (`:360-366`) reads the believed danger carried back in the repurposed `EnemyInfluence` field, and the size bump keys on `BelievedDangerHostileThreshold` (not the InfluenceMap `ThreatMildThreshold`) via `sizeThreatThreshold` (`:289`). Both gates default off on the engine class ⇒ @stable/normal byte-identical; enabled in `@experimental` tuning (`ai.yaml:180` capture, `:309` garrison, as of 2026-07-29). **Still deliberately omniscient (not scoped for migration):** `LayeredDefenceBotModule` (`GetFriendlyInfluence`/`GetEnemyInfluence` `:248-249`, `GetFrontline` `:234`), `MountedTransportBotModule` (`GetFrontline` `:497`, `GetFriendlyInfluence` `:501`), and the render-only debug `FrontlineOverlay` (`GetFrontline` `:77/:79` — not sim code).
- **The Stage-F benchmark re-baseline is RUN** (2026-07-29 — `WORKSPACE/ai-bench/runs/260728_rebaseline_result.md`, instrument `main @ e5b7bbcc`, post-item-26/28). 40 measured + 20 cal matches. With item-24 belief-repoint held OFF (the clean zero per user decision) and item-25 `StrategicRepointEnabled` ON, `@experimental` **underperforms `@stable`** on both rungs (S2 net-swing median ≈ −$1,425; S1 win 3–7), a regression vs the pre-26/28 `260721` "Exp ≈ Stable" baseline attributed to the global item-26/28 changes. Item-24 gate-enablement pricing is a SEPARATE later A/B against this zero. (Note: item-24 gates were found shipped **ON** in `ai.yaml:180/:309` — flagged to user; the re-baseline forced them off temporarily to exclude item-24 from the zero.)
- **Danger kernels are radial v1** (`DangerFieldLayer.cs:24-26`); terrain-aware flow (a river splitting the front) is a declared v2. The Stage-E line-walk terrain-blindness (above) is the same v2 boundary.
