## Scenario System

Scenarios are scripted map variants that share terrain with a base map but add different units, players, and Lua scripts. They appear in the lobby map chooser under the "Scenario" category.

### How it works

- A scenario is a **separate map folder** that copies `map.bin` (terrain) from a base map
- Has its own `map.yaml` (different actors, players), `rules.yaml` (LuaScript reference), and `.lua` script
- Uses `Categories: Scenario` to appear in the Scenario filter in the map chooser
- No engine C# changes needed — everything runs on OpenRA's existing Lua scripting API
- Supports multiplayer + bots — human players take specific slots, bots fill the rest

### Creating a scenario

1. Create a new map folder: `mods/ww3mod/maps/<base-map>-<scenario-name>/`
2. Copy `map.bin` and `map.png` from the base map. **Not `shadows.bin`** — the LOS cache no longer lives in the map package and is never read from one; a stray copy is dead weight (see §The LOS cache below)
3. Write `map.yaml` with:
   - `Categories: Scenario` and `LockPreview: True`
   - Custom players (human playable + non-playable garrison/AI factions)
   - Pre-placed actors (garrison units, supply routes, objectives)
4. Write `rules.yaml` with `LuaScript: Scripts: scenario.lua, <your-script>.lua`
5. Write your scenario `.lua` script using the `Scenario` helper library

### Scenario Lua library (`mods/ww3mod/scripts/scenario.lua`)

Reusable helpers for scenario scripts:
- **Spawning**: `Scenario.SpawnUnit()`, `Scenario.SpawnGroup()`, `Scenario.ReinforceFromEdge()`
- **Ownership Transfer**: `Scenario.TransferAll(from, to)`, `Scenario.ScheduleTransfer(from, to, delaySec)`
- **Wave Spawning**: `Scenario.ScheduleWave(wave, delaySec)`, `Scenario.ScheduleWaves(waves, base, interval)`
- **Patrol/Defense**: `Scenario.Patrol(actors, waypoints)`, `Scenario.DefendPosition(actors)`
- **Messaging**: `Scenario.Message(text)`, `Scenario.SetBriefing(text)`, `Scenario.PlaySpeech(player, notif)`
- **Objectives**: `Scenario.AddPrimaryObjective(player, desc)`, `Scenario.CompleteObjective(player, id)`
- **Utility**: `Scenario.GetLiving(tag)`, `Scenario.CountLiving(tag)`, `Scenario.OnGroupEliminated(tag, cb)`

### Naming convention

Scenario titles follow the format **`<Scenario>: <Map Name>`** — scenario name first, then the base map. This lets the same scenario type apply across multiple maps (e.g., "Frontline: River Zeta WW3", "Frontline: Siberian Pass WW3"). Feels like a game mode.

## The LOS cache (shadow/density layers)

**The cache lives outside the map package and is keyed on content. No map carries a `shadows.bin`, nothing writes one, and nothing reads one.** *(Changed 2026-08-30. This section previously described per-map `shadows.bin` files refreshed by hand; every instruction in it is now wrong. `WORKSPACE/recon-shadows-on-demand.md` records why.)*

Generated layers are stored in `Platform.SupportDir/Cache/shadows/<key>.bin` by `ShadowCache`, where the key is `SHA1(mapUid ‖ densityRulesHash ‖ ShadowCache.AlgoVersion)`. `Map`'s constructor probes it and, on a miss, generates and stores (`Map.LoadOrGenerateShadows`). It is out of the package deliberately: `ComputeUID` hashes the package, so a cache inside it would make the LOS data part of map identity — and a package `shadows.bin` carries no magic, no version and no rules hash, so a stale one could not be detected and would silently hand one player different concealment to everyone else. `ComputeUID` now skips the filename outright so a leftover file cannot fork a map's identity either.

**After changing the shadow compute pipeline, do not regenerate anything by hand — bump `ShadowCache.AlgoVersion`.** It is part of the key, so every existing entry on every machine is rebuilt automatically. `ShadowCacheKeyTermsTest.ShadowCurveMatchesTheRecordedAlgoVersion` fails if you change one of the algorithm's constants without bumping; it cannot see a change to the *shape* of the trace, so a rewrite of the Bresenham walk or the projection maths still needs the bump made by hand.

A map, actor, lua or png edit invalidates via `mapUid`, and a rules-only `Density:` edit via `densityRulesHash` — neither needs any action.

```bash
./utility.sh --regen-shadows <ABSOLUTE path to map>   # optional pre-warm; writes nothing into the package
```

That command is now purely an optimisation — it fills the cache so a later load does not pay generation. Generation costs ~7 s for river-zeta and ~18 s for the largest map, once per map per machine.

**The shadow/density layers are frozen at map load and never rebuilt at runtime.** `Map.DensityLayer` and `Map.ShadowLayer` are populated exactly once, from the cache or a one-time `SetDensityLayer()`+`SetShadowLayer()` after `PostInit` (`Map.LoadOrGenerateShadows`). The dynamic-recompute path (`Map.UpdateDensityForBuilding` / `QueueShadowUpdate` / `FlushPendingShadowUpdates`) was **disabled 260503** (too expensive mid-game — visible lag on building destruction); the `Building` add/remove density hooks that would mutate it are commented out (`Traits/Buildings/Building.cs:372-383` add, `:391-397` remove, with the dated reason inline). **Consequence:** killing a tree removes the actor and its sprite but leaves its density — and therefore its concealment / LOS blocking **and its damage-reduction cover** (`DensityModifiesDamage` samples the frozen `DensityLayer` over a per-cell window, `Infantry/DensityModifiesDamage.cs:72-87`) — baked in; burning or shelling a forest does **not** open sightlines or thin cover. Any "dynamic forest / deforestation opens lanes" idea is blocked until that 260503-disabled pipeline is re-enabled and its mid-game-lag cost solved.


**Shadow generation is byte-identical across machines, so per-machine regeneration cannot desync a match** *(measured 2026-08-30 at `55836dd8`)*. `river-zeta-ww3` regenerated from scratch on a scratch copy on macOS (Darwin x86_64, macOS 26.5.2) and on Windows 11 (x64), both on the pinned `6.0.428` SDK, produced the same sha256 `dbecdd12…f150f2c` at 36,871,948 bytes. This **refutes** the hypothesis that unsynced per-machine shadow computation caused the unsolved 2026-08-16 two-machine desync at tick 3792: those bytes genuinely are absent from the sync hash, but they agree, so they cannot be the divergence — look elsewhere. Consequence for on-demand generation: **each machine persisting what it computed is safe**, because there is no disagreement to freeze. Regenerating river-zeta also reproduced its *committed* `shadows.bin` byte for byte, so the shipped cache is current and a cached player does not disagree with an uncached one. **Scope, honestly: one map, two machines, both x64, both on the pinned SDK.** It does not prove determinism across SDK versions or on ARM — that is precisely what the `global.json` pin exists to guarantee, which is a reason to expect it to hold rather than evidence that it does.

## Asset pipeline: loose files & sprite loading

**Loose-file-over-mix precedence — the drop-in replacement rule.** `FileSystem` resolves a filename to the **last-mounted** package that contains it: `GetFromCache` uses `fileIndex[filename].LastOrDefault(...)` (`engine/OpenRA.Game/FileSystem/FileSystem.cs:195`), and the per-package fallback likewise uses `mountedPackages.Keys.LastOrDefault` (`:246`). In `mods/ww3mod/mod.yaml` the RA `.mix` archives mount first (`:21-37`) and the loose `ww3mod|bits*` dirs mount later (`:49-59`), so **a loose file shadows the mix copy of the same name** — dropping a rebuilt sprite in `mods/ww3mod/bits/` overrides the archived one with no manifest edit.
- **CAVEAT — the loose filename must match the sprite's *resolved* name, including tileset extension.** Trees/terrain sequences use `UseTilesetExtension: true` (`DefaultSpriteSequence.InferExtension`, `Graphics/DefaultSpriteSequence.cs:363-380`), so a `t01` tree resolves to `t01.tem` on TEMPERAT, `t01.sno` on SNOW, etc. A loose `t01.shp` will **not** shadow it — name the drop-in `t01.tem` (one file per tileset you care about). Units referenced by a plain `.shp` sequence shadow with a loose `.shp`.

**PngSheet — rendering loose PNGs.** Loose PNGs (both 8-bit indexed and 32-bit RGBA) render once `PngSheet` is in `SpriteFormats` (`mod.yaml:327`). The loader sniffs **content, not extension** (`Png.Verify` magic bytes, `SpriteLoaders/PngSheetLoader.cs:49`), so existing SHP/TMP sprites still load via their own loaders and a PNG-format file named e.g. `3tnk.shp` still renders as a PNG.
- **Indexed PNGs carry their OWN palette — no player-colour remap.** `PngSheetLoader` attaches an `EmbeddedSpritePalette` from the PNG's PLTE (`:87-88`), so an indexed PNG renders in its baked colours and ignores the actor's assigned palette / team-colour remap (indices 80–95). RGBA PNGs are pure truecolour (also no remap). For a team-coloured **unit**, use the SHP round-trip (pure indices, coloured by the runtime palette); loose PNGs suit decoration art.
- **Auto-sliced frames anchor CENTERED — the source SHP offset is lost.** With no embedded metadata, `RegionsFromSlices` treats the whole image as one frame with `Offset = float2.Zero` = sprite centre on actor centre (`:112-160`, offset default at `:136-142`); embedded `FrameSize`/`FrameAmount` chunks control slicing. So a SHP→PNG→PngSheet conversion **loses** the original trunk/turret anchor (a symmetric sprite looks right centred; an asymmetric one sits wrong). Fix anchoring via the sequence `Offset:` field or embedded `Offset`/`FrameSize`/`FrameAmount` chunks; the SHP round-trip preserves offset.

**Cameos are the exception to the remap caveat — an RGBA PNG is a fully correct cameo.** The warning above ("loose PNGs lose team-colour remap, so they suit decoration art, not units") does not apply to cameos, because **a cameo is never drawn through a player palette**: `BuildableInfo.IconPalette` defaults to `"chrome"` with `IconPaletteIsPlayerPalette = false` (`Traits/Buildable.cs:42-47`), `ProductionPaletteWidget` appends the owner name only when that bool is set (`:614`), and `IconPaletteIsPlayerPalette` appears **nowhere** in `mods/ww3mod/`. So indices 80–95 in a cameo render as fixed palette colours for every player, and the one property the caveat is about is never exercised. On top of that, RGBA sprites discard the palette reference outright — `SpriteRenderer.ResolveTextureIndex` returns 0 (no palette) for an RGBA sprite **provided the palette has no colour shift** (`Graphics/SpriteRenderer.cs:118-129`; the same guard is mirrored in `SpriteRenderable`, `UISpriteRenderable`, `TerrainSpriteLayer`), and ww3mod's `chrome` palette has none. A 32-bit PNG cameo is therefore pure truecolour and needs **no indexing, no `temperat.pal` conformance and no `tools/sprite` round-trip** — drop it in named `*.shp` and `PngSheetLoader` sniffs the magic bytes (`PngSheetLoader.cs:45-50`), no YAML edit. *The general detector: before inheriting a caveat, check whether the consumer actually exercises the mechanism the caveat is about.*
- **ww3mod's `chrome` palette IS `temperat.pal`** (`rules/palettes.yaml:58-62`) — the same file as the base actor palette (`:50-53`). So `tools/sprite/validate.py`'s temperat.pal drift check is already the right check for cameos if the SHP path is taken; there is no separate cameo palette. (`chrometd` = `temperattd.pal`, `:25-28`, used by three entries only.)
- **Cameo canvas size is a convention, not an engine constraint.** `IconSize: 62, 46` (`chrome/ingame-player.yaml:21`, `:1297`) sizes the *slot*; the sprite is drawn by `WidgetUtils.DrawSpriteCentered` (`WidgetUtils.cs:86-89`) at `pos - 0.5 * s.Size`, **never scaled and never clipped**. Shipped cameos are a mix of 64×48 (176 files) and 60×48 (40 files) and both overhang the 46 px slot by a row.
- **Single-frame full-canvas assets survive SHP→PNG→PngSheet**, so the "auto-sliced PNG loses the anchor" trap above does not reach a cameo: `--png` exports at `frame.FrameSize` and re-applies `frame.Offset` into the padded image, and the result reloads as one frame at `Offset = 0`, centred — the same place.

**The load screen is a compositor, not a full-screen image.** `LoadScreen: LogoStripeLoadScreen` with `CustomBar: true` (`mod.yaml:260-265`) draws exactly three things (`LoadScreens/LogoStripeLoadScreen.cs`): a logo sprite cut from rect `(0,0,256,256)` of the sheet (`:51`), a stripe cut from `(258,0,253,256)` (`:52`), and text. **There is no code path in this class that renders a full-screen background** — the rest is black, so handing it a 1920×1080 painting cannot work without a new `SheetLoadScreen` subclass. `CustomBar: true` additionally replaces the stripe with a solid drawn bar (`:62-79`), leaving the right-hand 253×256 region of the PNG loaded and never drawn. **The extra pixels in the 2x/3x files buy sharpness only, never size:** `SheetLoadScreen` picks Image/Image2x/Image3x purely from `Game.Renderer.WindowScale` (`:47-77`) and `CreateSprite` multiplies the rect by `density` **and** scales the sprite by `1f/density` (`:85-89`) — the logo is always 256×256 *logical* px, centred, at every window size, and the 2x/3x files must place their regions at `density × rect` (stripe starts at x=516 for 2x, x=774 for 3x, not 2×256). Related: **there is no runtime window icon to author** — `SDL_SetWindowIcon` is called nowhere in `engine/`, and `<ApplicationIcon>$(LauncherIcon)</ApplicationIcon>` (`OpenRA.WindowsLauncher.csproj:4`) resolves empty because `LauncherIcon` is defined nowhere in the repo, so the exe icon comes solely from rcedit at packaging time.

## Audio pipeline: sound formats & adding a music track

**`SoundFormats` is a list of C# class-name prefixes, not file extensions.** `mod.yaml:325` reads `SoundFormats: Aud, Wav, Ogg`; `ModData.cs:80` hands that list to `ObjectCreator.GetLoaders<ISoundLoader>`, which resolves each entry as `FindType(format + "Loader")` (`ObjectCreator.cs:170`) and throws at load if the type is missing or does not implement `ISoundLoader`. `Ogg` therefore binds `OpenRA.Mods.Common.AudioLoaders.OggLoader`, backed by the `NVorbis` NuGet reference (`OpenRA.Mods.Common.csproj:11`). **Ogg Vorbis is WW3MOD's target format for new music** — no upstream OpenRA mod enables it, so this path is ours alone.

**Export settings.** Ogg Vorbis, 44.1 kHz, q5–6 (~160–192 kbps VBR). **Mono or stereo only** — `OpenAlSoundEngine.MakeALFormat` branches on `channels == 1` and sends *everything else* as stereo (`OpenRA.Platforms.Default/OpenAlSoundEngine.cs:109-115`), so a 5.1 file is silently mis-interpreted rather than rejected. Sample rate is unconstrained; bit depth is forced to 16 by `OggFormat.SampleBits` (`AudioLoaders/OggLoader.cs:40`).

### Adding a music track

1. **Drop the file loose** in `mods/ww3mod/bits/sounds/music/<name>.ogg`. That folder is already mounted (`mod.yaml:83`) — **no `Packages:` edit, no `.mix` or zip**. `Folder` mounts are `TopDirectoryOnly` (`FileSystem/Folder.cs:35`), so this only works for files placed directly in a mounted dir; a new subfolder would need its own mount line.
2. **Register it** in `mods/ww3mod/rules/sound/music.yaml` (note: `rules/sound/`, *not* `audio/`).

```
	# blank line above — top-level entries must be separated (see conventions.md)
	deadhand: Dead Hand
		Extension: ogg
		VolumeModifier: 0.8
```

(Indentation is a **tab**. `deadhand` is the key *and* the default filename stem; `Dead Hand` is the jukebox title.)

**`MusicInfo` reads exactly four keys** — `Hidden`, `VolumeModifier`, `Extension`, `Filename` (`GameRules/MusicInfo.cs:26-39`). **There is no `Length:` and no `Hash:`.** `Length` is decoded from the file at load (`:41-63`) and used only for the `M:SS` display label; playlist advance is driven by the audio backend's completion callback, so it cannot stall a playlist. `Extension: ogg` is **required** — the default when omitted is `aud` (`:37`), and `Filename` is built as `<key or Filename>.<ext>`.

**The #1 debugging trap: a track whose file cannot be opened is dropped from the jukebox with no log message at all.** `MusicInfo.Load` returns early and leaves `Exists` false if `TryOpen` fails (`:43-44`), and `Ruleset.InstalledMusic` filters on `Exists` (`GameRules/Ruleset.cs:95`). So `music.yaml` is a *superset declaration*, not a manifest of what ships — a typo in the filename or a missing `Extension: ogg` makes the entry simply vanish. Distinguish the two failure shapes: **absent from the list** = file not found; **present but showing `0:00` and silent** = file found but no registered loader could parse it (`Exists` is set before the parse loop, `:48-57`) — check `SoundFormats`.

**Loose files override `scores.mix`.** `FileSystem.TryOpen` resolves to the *last* mounted package containing the name (`FileSystem.cs:195, 246`), and `~scores.mix` mounts at `mod.yaml:33` while `bits/sounds/music` mounts at `:83`. Dropping `journey.ogg` beside a `journey` entry does not automatically replace the `.aud`, though — `Extension` decides the filename, so the migration path off the Westwood tracks is: add the `.ogg` file, then point the existing entry at it (or add a new key and delete the old entry).

| CohesionMoveModifier.cs | World trait (IModifyGroupOrder): intent-aware cover-placement system for grouped Move/AttackMove orders. Classifies the target cell against `Map.DensityLayer` and dispatches to one of four slot strategies: **Open** (box layout — fires on open terrain, the typical AI case), **SpreadInside** (bid for top-CoverScore cells inside a cover patch), **EdgeLine** (line perpendicular to the density gradient, anchored at the cover edge), **Approach** (boundary-anchored line when the squad is far from a cover click). CohesionMode (Tight/Loose/Spread) controls only the **slot spacing** (col/row WDist), not which strategy fires. See `CohesionMoveModifier.cs:19-26` (class desc), `:126-143` (spacing), `:178-214` (intent classification). Fires for bot-issued grouped orders (confirmed: `UnitOrders.cs:397-413`). AI default is `Loose` (`AutoTarget.cs:120 InitialCohesionAI`). The **Open** box footprint is **bounded per mode**: once `(cols-1)*colSpacing` would exceed `{Tight,Loose,Spread}MaxWidth` (`:54-73`) the effective spacing shrinks to hold the span at the cap (same for depth), floored at `MinSlotSpacing` (1024) — so the box no longer grows without limit as unit count rises. Mode ordering Tight<Loose<Spread is preserved for every count. Regroup-on-arrival is not new code — the bound repurposes the existing `CohesionSlotMemory` sticky-slot leash. ## Aircraft movement system

The air branch introduced a **dual movement system** that is important to understand:

### Helicopters (CanSlide = true)

Use velocity-based movement with acceleration/deceleration:
- `Aircraft.CurrentVelocity` — current movement vector
- `Aircraft.RequestedAcceleration` — set by Fly activity each tick
- `Aircraft.CalculateAccelerationToWaypoint()` — computes acceleration toward target, includes maintenance accel to prevent speed oscillation
- `Aircraft.CalculateStopPosition()` — predicts stop position using discrete semi-implicit Euler formula
- Movement applied in `Aircraft.Tick()` via `CurrentVelocity` (decel THEN move)
- `Fly.Tick()` has a **fully separate CanSlide code path** — only sets RequestedAcceleration, never calls FlyTick
- Always brakes toward target (stopAtWaypoint=true), even when activities queued after
- Altitude adjustment during flight: gradually climbs/descends toward CruiseAltitude while flying
- On arrival: snaps to exact target position, zeros CurrentVelocity. Skips climb if next is Land
- Landing: smooth speed-proportional descent (fast=high, slow=low), gentle touchdown near ground
- Takeoff: rise to halfway CruiseAltitude, then start moving forward while climbing rest
- Pitch applied during horizontal movement in Aircraft.Tick (FlyTick isn't called for CanSlide)
- **CRITICAL**: Never use FlyTick for CanSlide without zeroing CurrentVelocity first (double movement)

### Fixed-wing (CanSlide = false)

Use traditional step-based movement:
- `Aircraft.FlyStep()` — returns movement vector for current speed/facing
- `Fly.FlyTick()` — applies movement, handles altitude, roll, pitch
- Turns computed via `Fly.CalculateTurnRadius()`

    RotationAcceleration: 2     # Turn acceleration (for CanSlide)

### Attack standoff (per-target, engine-provided)

The engine already stands a hovering/sliding attack aircraft off at weapon range — helicopter *overflight* past nearer enemies is a bot-order artifact, not an attack-code bug:

- A **Hover** attack aircraft (`AttackType: Hover` + `CanHover`) neither strafes nor takes a fixed-wing attack run in `FlyAttack.Tick`; it falls through to the facing branches (`FlyAttack.cs:183-198`), so it hovers and fires from `MoveWithinRange` distance instead of running past the target.
- A `CanSlide` aircraft's `Fly` activity zeroes `CurrentVelocity` and stops the moment it is inside the weapon annulus (`Fly.cs:187-190`). So a `MoveWithinRange`/`Attack` on a single actor already yields a per-target standoff at that armament's max range.
- **Overflight is a targeting choice, not an engine defect.** A bare `Order("Attack", unit, oneEnemy)` flies to *that* actor's standoff, overflying nearer front-line enemies en route (they are in range but are not the locked target). `Order("AttackMove", …)` instead lets `AutoTarget` engage the nearest in-range threat and only advance when clear — the standard way to get "stop and shoot what's in front of me" behaviour from a squad or unit.

### The break-off guard cancels the ATTACK, not the ENGAGEMENT — and only one airframe class changes its flight path

*(Measured 2026-08-27 in `tools/autotest/scenarios/test-aircraft-breakoff-midrun`, RED arm with the guard commented out of `AttackFollow.Tick`, three greens across three seeds.)* When `AttackFollow.Tick`'s break-off guard clears a critically damaged requested target, **the guns stop in both classes but neither aircraft leaves.**

- **Hover (`AttackType: Hover` + `CanHover`, e.g. Mi-28) — stops firing on the same tick, then holds station forever.** Distance trace over 250 ticks: `[14,14,14,…]` — not one cell of movement in any direction. Guns cold, parked at weapon range over a target it has declined to shoot.
- **Fixed-wing (`AttackType: Default`, `!CanHover`, e.g. A10) — stops firing after 2 ticks, then ORBITS the doomed target indefinitely.** Distance trace `[8,5,13,11,4,11,12,8,7,13]` with `minDistAfter` **0** (it passes directly overhead), never re-firing and never returning to base.

**The mechanism for the asymmetry is `Activity.TickOuter`, not anything in `AttackFollow`.** With `ChildHasPriority` (FlyAttack's default) the parent tick is short-circuited by `lastRun = TickChild(self) && (finishing || Tick(self));` (`engine/OpenRA.Game/Activities/Activity.cs:124-126`), so `FlyAttack.Tick` does not run while a child activity is alive — and FlyAttack's own abort check for exactly this case (*"Check that AttackFollow hasn't cancelled the target"*, `FlyAttack.cs:99-102`) lives in that tick. A `Default`/`!CanHover` aircraft is inside `MoveWithinRange` and then `FlyAttackRun`, so the check cannot be consulted until the run ends; `FlyAttackRun.Tick` self-cancels only when the target becomes *invalid* or has no valid weapons (`FlyAttack.cs:270-275`), and a critically damaged target is neither. A `Hover` aircraft queues no run child, so the check is live every tick. The **trait-level** guard runs regardless, which is why the guns stop in both classes even though the flight path only responds in one. **Do not read "break off" as "disengage"** — in both classes the airframe stays in hostile airspace over an enemy it has decided not to kill.

- **Strafe aircraft look structurally EXEMPT — read off the code, NOT observed.** `A10.Airstrike` and `FROG.Airstrike` are `AttackType: Strafe`, a third shape neither lane covered. `StrafeAttackRun.Tick` calls `attackAircraft.SetRequestedTarget(Target.FromTargetPositions(target), true)` **every tick** (`FlyAttack.cs:325`). The guard's predicate needs `RequestedTarget.Type == TargetType.Actor` *and* `BreakOffApplies(source, forceAttack)` = `!forceAttack && source != Default`; a strafe run fails **both** clauses independently — the re-set target is a position, and the re-set is a force-attack from the default source. Measure this before relying on it.
- **`IsIdle` is useless as an observable for aircraft.** `ticksToIdle` was `-1` and `idleSpans` `0` in **every** arm including RED: an idle airframe is running `FlyIdle`/`Hover`, which is an activity, so `IsIdle` never goes true. Use a **position trace**, and sample it — a min/max pair cannot separate "flew over once and left" from "flew over, came back, flew over again", which is exactly the fixed-wing behaviour.
- **Every vehicle bleeds out below 50% HP, and it silently confounds any "hold a unit at critical damage" scenario.** `ChangesHealth@CriticalDamage` on `^Vehicle` (`vehicles.yaml:153-156`: `PercentageStep: -1`, `Delay: 5`, `StartIfBelow: 50`) is irreversible, so a target parked at 15% **dies on a fixed ~75-tick clock with nothing shooting it**. Two runs of the scenario above ended with a dead target on *both* lanes — including the lane that fired zero shots — so two thirds of each observation window measured an aircraft against a corpse. The tell was the zero-shots lane also reporting a dead target; nothing in the verdict flagged it. Add `-ChangesHealth@CriticalDamage` to any such scenario. This is also what makes "already doomed" literally true in WW3MOD and is the premise the whole break-off feature rests on.

## Suppression system

**Infantry suppression (10-tier, cap 100, decay 1/5 ticks):**
- `GrantExternalCondition` warheads with Amount/Range for graduated suppression
- Speed/vision/burst/inaccuracy multipliers (90%→0% across tiers)
- InfantryStates triggers prone at suppression > 30 — **and, more importantly, whenever the unit is standing still: `ProneCondition` is `deployed || suppressed > 30 || !moving || critical-damage` (`infantry.yaml:294`), so prone is automatic and there is no stance or command that sets it.** **Prone DOES grant concealment: +1 detection tier** via `DetectableAddativeModifier@Prone` (`RequiresCondition: prone`, `VisionModifier: 1`, `mods/ww3mod/rules/ingame/infantry.yaml:716-718` — line ref refreshed 2026-08-19, it had drifted to `:684-686`, which is now an unrelated `WithDecoration@DamageInfantryPips` block), applied inside `Detectable.IsVisibleInner` (`Detectable.cs:93-116`) — same mechanism as the `@Dugin` bonus. Beyond stealth, prone gives per-damage-type reduction, −40% speed, a smaller hitshape (r20 vs r30), and the crawl animation. (Corrected 2026-07-28; the doc previously claimed prone had no stealth effect.)
- 10-tier pip display (pip-suppression-1 through pip-suppression-10). **It is ten colours of ONE glyph, not a bar that fills — do not design a readout around the ten tiers being individually legible.** The art is a single 6×3-pixel sprite in 10 frames (`bits/units/pips/pip-suppression.shp`, ShpTS header `w=6 h=3 frames=10`), each frame the same downward chevron on a different palette index; the ten `pip-suppression-N` sequences are `Length: 1` each (`sequences/sequences-misc.yaml:334-363`) and the ten `WithDecoration@Suppression_N` blocks select between them on mutually-exclusive `suppressed > X && <= Y` bands (`infantry.yaml:549-627`), so exactly one glyph is ever shown and it never accumulates. A 2026-08-17 SHP decode measured the ramp as pale yellow `#FFD77D` (tier 1) → dark red `#9A2800` (tier 10) in ~10-per-channel steps; at 6×3 px adjacent tiers are not separable on screen, still less on an unselected building's garrison pips, drawn at 0.7 scale / 0.35 alpha (`Render/WithGarrisonDecoration.cs:263-264`). In particular the pip **cannot** warn of an imminent garrison recall: recall fires at 60, which is the boundary between two adjacent oranges. An exact level has to be said in text (the garrison panel does) or drawn with new art.
- **Suppression is not a blanket fire-halt** — suppressed infantry keep firing, just degraded by the multipliers above. The exceptions are two armaments that hard-pause via `PauseOnCondition: suppressed >= 10`: the AT Specialist ATGM (`infantry.yaml:1702`, as `!ammo-primary || suppressed >= 10`) and the engineer repair arm (`:1915`). So a "let it pass, then shoot the rear" AT ambush that lets the escort return fire risks suppressing its own AT gunner into silence before it exploits the rear arc. **Note the threshold: `>= 10` is the LOWEST of the ten tiers, below even the `> 30` at which the man goes prone** — so these arms are off under any incoming fire at all, not under heavy fire. The medic's heal arm used to be a third (corrected 2026-08-11): it was removed because casualties only occur under fire, so the gate silently switched the medic off exactly when he was needed and patients bled out beside him. Suppression now degrades his treatment cadence through the ordinary ladders instead.

- **A zeroed burst multiplier is NOT a second hard gate — do not read it as one.** `BurstMultiplier@Suppression_10` is `Modifier: 0` at the top tier (`infantry.yaml`, `suppressed > 90 && <= 100`) and `Weapon.Burst` defaults to 1, so integer maths sends the effective burst to 0 for *any* 1-burst weapon under *any* suppression. That does not stop it firing: `Armament.UpdateBurst` runs **after** the shot (`Armament.cs:624-648`), decrements below 1, applies `BurstWait` and resets. The observable effect is one shot per burst-wait cycle, not silence.
- **Garrison fire is ALREADY suppression-degraded — a rate-of-fire hook on the building would double-apply.** `AttackGarrisoned.DoGarrisonedAttack` iterates `ps.DeployedSoldier.TraitsImplementing<Armament>()` and calls `a.CheckFire(a.Actor, …)` (`Traits/Attack/AttackGarrisoned.cs:292-305`): the armament belongs to the **soldier**, not the building, and `Armament.Created` captures its burst / burst-wait / inaccuracy modifier sets from its own actor (`Armament.cs:253-258`) — which is exactly where `^SuppressionEffects` installs them (`infantry.yaml:381-392`). So a garrisoned soldier is degraded across all ten tiers starting at suppression 1; the building contributes target selection and nothing else. What the building *does* own is `garrisoned-at-port`, which pauses the soldier's own `AttackFrontal` and `AutoTarget` (`infantry.yaml:186-188`) — that is what makes it look like the building is doing the shooting. A vestigial second implementation (`PortState.IsDucking` / `SuppressionDuckThreshold`) has been deleted; a PITFALL sits at the firing loop (`:288-290`) and at the former declaration (`GarrisonManager.cs:95-98`).
- **Staging suppression in a test: do not over-grant.** `ExternalCondition.CanGrantCondition` returns false once permanent tokens reach `TotalCap` (`ExternalCondition.cs:103-105`), and the Lua binding then **throws a `LuaException`** rather than ignoring the surplus (`Scripting/Properties/ConditionProperties.cs:36-39`) — an over-grant aborts the run with a stack trace instead of saturating. Infantry suppression decays `ReduceAmount: 1` per `ReduceTicks: 5` (`infantry.yaml:391-392`; vehicles are 1 per 3, `vehicles.yaml:324-325`), so topping up strictly *less* than the decay rate holds a unit near the cap indefinitely without ever hitting it.

**Vehicle suppression (5-tier, cap 50, decay 1/3 ticks):**
- Only medium caliber (12.7mm+) and explosions suppress vehicles
- Turret turn speed reduced (85%→25%), inaccuracy increased (115%→200%)
- Burst wait increased (105%→150%), NO speed reduction
- Defined in `^VehicleSuppressionEffects` template in vehicles.yaml

**Fire discipline (3 stances — controls WHEN to fire):**
- HoldFire, Ambush, FireAtWill (default)
- Ambush: pre-aim at targets, hold fire until spotted or damaged, coordinate with nearby allies. Widened into a stationary hide-and-spring state machine + an `@experimental` bot lane consumer behind the default-off `enable-ambush-tactics` gate — see §Widened ambush (Stages 1–4) below.
- FireAtWill: fire at any valid target in range
- Conditions: `stance-fireatwill`, `stance-ambush`, `stance-holdfire`

## Directional / rear armor

`DamageWarhead.ArmorDirectionPercent` (`DamageWarhead.cs:121-198`) scales effective armor by the shot-vs-facing angle, reading a 5-element `Armor.Distribution` `[front, side, rear, top, bottom]` (only applied when `Distribution.Length == 5`). A heavy tank's `100,50,25,10,10` means a rear shot lands ~4× the front damage. This runs inside the normal damage pipeline, so rear/flank bonuses are **automatic** from geometry — no special warhead flag or code path is needed; putting the shooter behind the target is the whole trigger.

**Engagement stances (3 stances — controls WHERE to position):**
- HoldPosition, Defensive (default), Hunt
- Separate from fire stances — two independent UI bars (3 buttons each)
- Hunt: chase targets aggressively, even out of range
- Defensive: fire from current position, reposition only if LOS blocked (Phase 2: cover-seeking via ShadowLayer — see `DOCS/reference/shadow-los-plan.md`)
- HoldPosition: never auto-reposition, only fire from current cell
- Hotkeys: Alt+A/G/F (fire), Ctrl+Alt+A/D/F (engagement)
- Engagement stance drives `allowMove` in AutoTarget scanning and movement decisions in Attack activity

**Cohesion stances (3 stances — controls HOW close together, Phase 1 UI only):**
- Tight, Loose (default), Spread
- Hotkeys: Ctrl+Alt+1/2/3
- Phase 3 will modify waypoint distribution on group moves (not repulsion — too laggy for ground units)

**Resupply behavior (3 stances — controls WHAT to do when out of ammo):**
- Hold (stay put, flag NeedsResupply for supply truck pickup), Auto (seek nearest supply point, default), Evacuate (leave via Supply Route)
- Only shown for units with AmmoPool trait
- Hotkeys: Ctrl+Alt+4/5/6
- AutoRearmIfAllEmpty checks stance: Auto=seek, Hold=flag+wait, Evacuate=RotateToEdge

**Click-modifier meta-system (all 4 stance bars):**
- Click: Set stance for current selection (immediate)
- Ctrl+Click: Set per-unit default (unit remembers even after resets)

## AI configuration

AI is configured entirely via YAML in `mods/ww3mod/rules/ai/`:

- `ai-america.yaml` — America-specific build priorities, unit limits, squad composition

**What the bot actually buys is re-derivable statically:** `OpenRA.Utility ww3mod --composition-plan [--faction america|russia] [--cycles N] [--attrition N] [--verbose]` (`UtilityCommands/DumpCompositionPlanCommand.cs`) replays the production `ForceCompositionMath` argmax — real resolved `ValuedInfo.Cost`, real `UnitTargetShares`/`UnitLimits`/`UnitFloors`/`UnitDelays` off the live trait info — against the starting-units package, with **no game session**. Same shape as `--danger-reference`. It prints a per-type reachability table whose `V_fit` column (`1000 × cost / target`) is the one number that explains most "why does the bot never buy X" questions: **below that army value a single unit of X is already over its target share, so the ceiling strikes the slot.** `--attrition N` adds deterministic proportional-hazard losses (every standing unit accrues one point per cycle, dies at N), which is what separates "bought in a quiet sim" from "bought in a real match" — medics measured 4 buys at zero losses and **0** at 1-in-40. **Limits, stated because the tool is persuasive:** budget is unlimited, the believed-enemy vector is zero, and it models only this module's lane — the `IBotRequestUnitProduction` lanes (e.g. `CaptureCoordinatorBotModule.MaintainTecnFloor`) are invisible to it, so its `tecn` numbers are an artefact, not a finding. **It also does not model the ammo gate at all, and that skews trucks in BOTH directions:** `GateResupplyOnAmmoNeed` is absent, so on the deficit path `truk` is unconditionally eligible and the replay *overstates* it, while the supply pre-empt is pinned at zero starving customers so it only ever reflects `SupplyTruckFloor` and *understates* demand-driven buys. **The tool cannot answer "how many trucks will the bot field"** — read the unconditional `[composition] census` line from a real match, which carries `starving` / `trucks-desired` / `ammo-need` for that purpose.

Key AI modules: `UnitBuilderBotModule` (what to build), `PoiOffensiveBotModule` (how the GROUND army attacks — see below), `SquadManagerBotModule` (**air squads only** in WW3MOD), `HelicopterSquadBotModule` (helicopter attack/scout/transport squads), `CaptureCoordinatorBotModule` (what to capture), `BuildingRepairBotModule` (auto-repair). Note `CaptureManagerBotModule` is the *legacy* capture module and is **not attached in ww3mod** — it was deliberately superseded by `CaptureCoordinatorBotModule` because the two competed for the same TECN pool (`ai.yaml:118-120`; that comment now describes a module `mods/` never instantiates at all — see §The bot's capture vocabulary below).

**The skirmish bot roster is exactly two profiles — `experimental` and `stable`** (`ModularBot@experimental` / `@stable`); the old Normal/Rush/Turtle bots were removed 2026-07-30. Two traps for anyone editing the config after the prune: (1) **`enable-ai-player` is the SHARED baseline tier**, granted to *both* surviving bots — so the `@normal`-named baseline blocks it gates (e.g. `BaseBuilderBotModule@normal`, `ai.yaml:1017`) are live production for both bots, not dead legacy; the `@normal` suffix is now a misnomer, keep the blocks. (2) **`SkirmishLogic.cs` seeds the default AI opponent by string-matching the bot *type***: `availableBots.FirstOrDefault(t => t == "stable")` (`ServerTraits/SkirmishLogic.cs:182`), repointed from the removed `"normal"` — a fresh skirmish silently falls through to whatever bot is first if that string stops matching. The condition `enable-ai-legacy-only` is now granted to nobody and survives only in comments.

**Profile scoping is a CONDITION, not a trait-name suffix — `@stable` / `@experimental` in a trait name mean nothing.** MiniYaml `@suffix` is only an instance key: it makes two entries of the same trait distinct and carries no scoping semantics whatsoever, so `@poi`, `@supply`, `@america` and `@aiplayer` are the same kind of token as `@stable`. What actually scopes a module to a personality is `GrantConditionOnBotOwner` keyed on the bot's `Type` (`ai.yaml:58-71`) plus each module's `RequiresCondition`: `enable-ai-player` and `enable-ai-any` go to `Bots: experimental, stable` (`:58-60`, `:69-71`), `enable-ai-experimental` to experimental only (`:61-63`), `enable-ai-stable` to stable only (`:64-66`). `ScoutBotModule@america` is shared not by default but because it declares `RequiresCondition: enable-ai-any && player.nato` (`:863-864`). **Read the `RequiresCondition`, never the suffix** — this is why `MountedTransportBotModule@poi` is the `@stable` twin, and why `BaseBuilderBotModule@normal` is live on both. Two corollaries. **(1) There is a THIRD ModularBot personality**: `ModularBot@CampaignAI` with `Type: campaign` (`rules/campaign/campaign-rules.yaml:13-15`). ### AI production: `UnitsToBuild` weights are share *ceilings*, not priorities

`UnitBuilderBotModule` (the shared "what to build" module) has **no YAML field for a production floor or priority** — all three of its Info dictionaries are caps or gates, never guarantees:

- **`UnitsToBuild`** — the weight is a per-type *share ceiling as a percent*, not a priority. `ChooseUnitToBuild` (`UnitBuilderBotModule.cs:177-195`) **shuffles** the dict and returns the first entry passing `count*100 < weight*total` (`:190`), i.e. `count/total < weight/100`. Any weight ≥ 100 can never bind, so that unit is merely "always eligible" and is then picked **uniformly** by the shuffle — weight `500` and weight `120` give identical early-game odds. Below the roster-average weight a type is *throttled*; above it there is no boost.
- **`UnitLimits`** is a ceiling; **`UnitDelays`** is a start delay.
- While `idleBaseUnits < IdleBaseUnitsMaximum` (12, `:25`) the module ignores weights entirely and builds a **uniform-random** buildable (`ChooseRandomUnitToBuild :167-175`), discarding picks not in `UnitsToBuild` (`:125-126`).

A guaranteed "keep N of type X ready" therefore requires **code**, via the `IBotRequestUnitProduction` demand queue (the same queue `AdaptiveProductionBotModule` uses, `:64,159`):

- Call `up.RequestUnitProduction(bot, name)` on each `player.PlayerActor.TraitsImplementing<IBotRequestUnitProduction>()` (in WW3MOD only `UnitBuilderBotModule` implements the sink). `BotTick` pops **one** queued request per `FeedbackTime` (30-tick) cycle **before** the share lottery (`:87-92`) and routes it through the single-name `BuildUnit` overload (`:142-165`), which skips `UnitsToBuild`, `UnitLimits`, and `UnitDelays`.
- **Drop-on-failure is real** (`:90-91` removes the entry whether or not a queue was free), so a floor must **re-request every scan** and subtract already-queued via `RequestedProductionCount` (`:104-107`) — gate on `alive + pending < floor`, checked every scan.
- For a faction-correct build type with no hardcoding, intersect the desired types with the player's queue `BuildableItems()` names, and resolve lazily without caching a null (queues/prereqs may be cold on the first scan).

`CaptureCoordinatorBotModule.MaintainTecnFloor` (`:389-402`, default-off `TecnFloor`) is the reference implementation.

**A player carries several disabled-but-constructed producer twins, and `TraitsImplementing<>` returns them — so routing a request to index `[0]` can silently drop it.** Each player has multiple `UnitBuilderBotModule` instances (per-profile `normal`/`experimental` plus per-aircraft `fixedwing`/`heli`), all but one condition-disabled per game via `RequiresCondition`. `PlayerActor.TraitsImplementing<IBotRequestUnitProduction>()` (and the `IBotRequestPriorityUnitProduction` variant) returns **all** of them — the disabled ones included — in trait construct order, which preserves the YAML/mod-load merge order among same-type traits. But `ModularBot` only *ticks* enabled modules (`ModularBot.cs:96`, `if (t.IsTraitEnabled()) t.BotTick(...)`) while the interface methods are invoked directly regardless of enabled state. So a requester that blindly uses `producers[0]` can land every request on a disabled twin whose `BotTick` never drains it: the unit is never built, yet `RequestedProductionCount` keeps counting the queued request, so the caller's `pending` climbs forever while `alive` stays 0 (a measured `pending=82 / alive=0` deadlock). Two in-tree fixes:

- **Route to the first *enabled* producer** via `Exts.FirstEnabledTraitOrDefault()` — the seam `McvManagerBotModule.cs:117` and `HarvesterBotModule.cs:158` already use. `AdaptiveProductionBotModule` gates this behind default-off `RouteToEnabledProducer` (`:93`; `SelectUnitProducer` `:269` delegates to the pure `AdaptiveRoutingMath.SelectProducerIndex`), set only on the two `@experimental` twins so `@stable` keeps the frozen `producers[0]` routing byte-identical (index 0 verbatim even when `[0]` is disabled).
- **An accept/reject handshake:** `IBotRequestPriorityUnitProduction.RequestPriorityUnitProduction` returns `false` when `IsTraitDisabled` (`UnitBuilderBotModule.cs:154-164`), and `CaptureCoordinatorBotModule` routes to the first twin that returns true (`:694`) — the request lands on the enabled UnitBuilder. That module's priority drain is peek-don't-pop (a busy queue keeps the request at the head for the next free slot) so delivery is non-lossy.

**Reactive counters come from `AdaptiveProductionBotModule`, not the static composition.** It scans the *fog-legal* enemy composition each cycle (`ScanEnemyComposition`, only actors passing `CanBeViewedByPlayer`, `AdaptiveProductionBotModule.cs:200,213`) and pushes threat-scaled requests through the same `IBotRequestUnitProduction` demand queue. AA is illustrative: it requests anti-air **only when `enemyAir > 0`** and caps at `aaCount < enemyAir*2` (`:145,149`). So the "several SHORAD/Tunguska sitting at the start" a player sees is **not** AdaptiveProduction over-reacting — with no enemy air sighted it requests zero AA. That early AA is the *static* `UnitsToBuild` share composition building toward its fixed weight regardless of threat. The two AA sources are independent: composition is the always-on baseline, AdaptiveProduction is the sighted-threat reactive top-up. The `@experimental` twin adds a separate **SR-defense** path (default-off `SupplyRouteDefenseEnabled`) that reads the *believed* belief store to classify an incoming rush by attacker **identity** and pre-buy the matched counter, bypassing `MinEnemySightings` — see [influence-stack.md](influence-stack.md#experimental-consumers-beyond-def).

### Call-in bookkeeping: what bounds a repeat purchase (and what does not)

Under the reinforcement model a purchase spawns at the map edge and *walks in*, so delivery latency vastly exceeds the 30-tick purchase cycle. That breaks the intuitive reading of `UnitBuilderBotModule`'s three dictionaries:

- **`UnitLimits` counts WORLD ACTORS only** — `world.Actors.Count(a => a.Owner == player && a.Info.Name == name) >= limit` (`:465-468`) — so a call-in still in the queue or still walking in is invisible to it. A lane that picks the same type on consecutive cycles sees the same count every time and can overshoot the cap by however many cycles fit inside the delivery time. Read `UnitLimits` as a lagging ceiling, never as a guarantee.
- **`UnitDelays` is an absolute world-tick opening threshold, not a repeat cooldown**: `Info.UnitDelays[name] > world.WorldTick` (`:460-463`) opens once and never closes again.
- **What actually serializes a repeat call-in is `BuildUnit`'s empty-queue precondition** — `FirstOrDefault(q => !q.AllQueued().Any())` (`:440`, mirrored in the single-name overload at `:664`) only ever picks a queue with nothing already queued. Because WW3MOD calls units in through the Supply Route's single queue, that admits no second simultaneous call-in; `UnitLimits` bounds the rest once the unit spawns. The residual is **multi-SR** (a captured second SR = a second queue), itself bounded at spawn. Two consequences: "already in flight" is a QUEUE property in this module, not a limits property; and any pending-production credit **cannot be scoped to "this queue"**, because the selected queue is provably empty — it must span the module's other queues plus its own `priorityBuildRequests`/`queuedBuildRequests` lists (`RequestedProductionCount`, `:429`).
- **The `BuildUnit(bot, name)` FIFO lane applies none of the above** (`:651-677`): it issues `Order.StartProduction` with no `UnitsToBuild`, `UnitDelays`, `UnitLimits` or resupply/AA gates. That is deliberate for the capturer floor; `AdaptiveProductionBotModule`'s counter-buys ride the same lane, and are now bounded only by a composition ceiling applied at the call site (`RequestIsOverCompositionCeiling`, `:400`). A ceiling-refused FIFO request is consumed either way (`queuedBuildRequests.Remove`, `:367`) — contrast the priority lane's peek-don't-pop — so a refusal is a *deferral owned by the requester*, which re-issues on its own cycle, and the census correctly stops crediting it.

**An affordability-filtered argmax degenerates into a cheapest-type pump.** `ForceCompositionMath.SelectDeficit` has no positive-deficit requirement — when every eligible type is at or above target it returns the least-over one, so a buy always happens. Eligibility, however, is affordability-filtered (`IsCompositionCandidateEligible`, `:983`, tests `CompositionNeedMath.Affordable` at `:1010`), and a bot spends to zero routinely — so in the low-cash band the only eligible member of a queue is its **cheapest** type and the argmax buys that type every cycle, unboundedly far over target. (America's Vehicle queue: humvee 450 against a 40‰ target, with everything else 700+.) The fix is `ForceCompositionMath.ApplyCeilingEligibility` (`:253`), which strikes slots **strictly** over target from the eligible set under `CompositionEnforceTargetCeiling` (`UnitBuilderBotModule.cs:744-745`) so the cycle DECLINES and banks the cash (`ShouldDeclineCycle`, `:757`) rather than falling through to the uniform `ChooseRandomUnitToBuild` lottery. *Strictly*-over matters: census and targets are both apportioned to 1000, so an over-target slot implies an under-target one survives the filter — but at-or-over would strike everything if every slot sat exactly on target and freeze purchasing outright. The general shape: a "no-opinion ⇒ fall back to the legacy picker" branch fires on *being broke*, not only on *having nothing composed to buy* — check which of those two your fallback is really answering.

### `UpdatesPlayerStatistics.AddToArmyValue` is a win-rule input, not telemetry

The flag **defaults to false** (`Traits/Player/PlayerStatistics.cs:258`), and the per-type alive tally is incremented only inside `if (includedInArmyValue)` (`:342-347`, mirrored on every decrement) — so a type without it reads **count 0 in the observer army bar no matter how many are alive** (`ObserverArmyIconsWidget.cs:95` renders `Units.Values`). A "the bot builds zero riflemen" report is therefore ambiguous between an empty army and an unflagged template. The flag is not cosmetic: it feeds `PlayerStatistics.ArmyValue` → `WeightedComponentScoring.Compute` (`Tournament/Scorers/WeightedComponentMatchScorer.cs:84-91`) → `snapshot.Total`, which `TimeOrSrCaptureWinRule` sorts on to pick the **time-expiry winner** (`:88`) and the SR-capture runner-up (`:59`), and it also drives `assets_value` / `unit_type_stats` in the match record and the observer ASSETS label. Nothing in the *simulation* branches on it (both victory-condition traits sort on `Experience` — `ConquestVictoryConditions.cs:93`, `StrategicVictoryConditions.cs:136`), so it is not a determinism or byte-identity concern — but **flagging a template invalidates any in-flight ladder baseline**, and pre/post match scores and telemetry columns must not be compared across such a change. All line-infantry templates plus `^TECN` now carry it (`infantry.yaml:1179/1298/1364/1436/2207`); the shared `^Soldier` base deliberately does not (`:175`), nor do the rank/husk `OverrideActor` variants.

### Adding a behavioural field to a trait shared by both bot profiles

`ModularBot@experimental` and `ModularBot@stable` (`ai.yaml:41-46`) share the same trait classes; `@stable` is the **benchmark control** — a fixed, known, *versioned* configuration. **It is not "frozen".** `b8d2e601` (2026-08-02) promoted `@stable` to full `@experimental` parity under user authorisation, and the profile display name is versioned to match (`Name: Stable AI 0802`, `ai.yaml:50`, previously `0730`) precisely so a benchmark artefact identifies which control it ran against. **Never write "`@stable` is frozen / byte-identical"** — a byte-identity claim is a statement about *YAML*, not about the C# it sits next to, which is why such claims survive next to correct-looking code citations. Write "as of `<sha>`, `@stable` sets X", or better, phrase flag-relative ("when this flag is off, the path is the pre-feature one"), which stays true across promotions and needs no maintenance. A new Info field with a non-baseline **code default** (e.g. `PoiOffensiveBotModule.ApproachCohesion = Spread`, `:96`) therefore leaks into `@stable` even when its YAML is untouched — silently mutating the control. Rule: **any behavioural Info field added to a shared trait must default to the frozen/baseline behaviour and be opted in per-profile via YAML.** The dispersion work does this with `CohesionSwitchEnabled` (default `false`, `:87`; the dispersion path is gated on it at `:424`), flipped `true` only on `@experimental`.

### A per-VALUE budget share cannot size a fleet whose workload scales with customer count

`ChooseByDeficit` takes a census of what the bot owns, compares it against designer-authored target shares, and buys whatever is furthest below target. **Those shares are per-mille of army VALUE, not of head count**, and `ForceCompositionMath`'s own header says why: *"Ten riflemen are not 'ten times the army' of one tank, so both census and targets are per-mille of army VALUE."* That is the right call for combat types — composition is a budget statement.

**It is the wrong call for a support unit whose demand scales with the number of units it serves.** A supply truck's workload grows with the size of the army; its permitted count under a value share grows with the army's *value divided by the truck's own cost*. Those are different functions, and at a small share and a high unit cost the quotient can pin the fleet at one vehicle for an entire match — which is exactly what a player reported, with much of the infantry out of ammo. **There was no "max 1" anywhere in the codebase and never had been; the fleet size was the quotient of two innocent-looking numbers in different files.**

Read this before chasing the next "the bot never builds enough X": check whether X's demand is driven by army value (composition — a share is right) or by customer count / area / throughput (logistics — a share is structurally wrong, and no amount of re-tuning the share fixes the shape). The specific share values are live tuning and move; the shape does not.

### A ratio floor has a cliff, and its failure mode is that the floor silently never exists

The companion knob to the share above is `UnitFloorPer` — "keep one of X per N of the supported force" — resolved by `SupportFloorMath.EffectiveFloor` (`Traits/BotModules/SupportFloorMath.cs:67-80`). The body is `var scaled = supportedCount / perSupported; return scaled < flatFloor ? scaled : flatFloor;` — **integer division, so the effective floor is exactly ZERO on every cycle where `supported < per`.** That is arithmetic, not tuning: any ratio whose denominator collapses under attrition has a loss regime above which the floor stops firing *entirely* and behaviour reverts to the pre-feature state — and it reverts hardest in the heavy-loss regime, i.e. exactly where the support type matters most.

**The failure is invisible to every outcome column.** A floor that never engaged and a floor that is fully satisfied both show zero pre-empts, and `standing` / `bought` / final `census‰` are end-of-cycle snapshots of a continuously-replaced type. The discriminator has to be the floor's own value, which is why `--composition-plan` reports `engaged` (cycles where the effective floor was ≥ 1 at all) beside `short`, and prints an explicit `INERT` marker on `engaged 0/N` (`UtilityCommands/DumpCompositionPlanCommand.cs`, `--floor-per N` sweeps the ratio without editing YAML). The medic shipped past its own cliff on both factions: measured on `--composition-plan` (2026-08-17), at `medi.* 20` the bot's standing non-medic infantry peaked at 18–19 under heavy attrition, so the floor reported `engaged 0/200` — it never once existed — and zero medics were bought. The ratio is now 10 (`ai-america.yaml:209-210`) with the measured denominator trajectory recorded beside it as a comment (`:177-182`) — and with its own caveat, worth repeating because it bounds the fix as well as the bug: that denominator is the **offline replay's**, which buys one unit per cycle on an unlimited budget and never buys four of the ten supported types, so a live infantry count could run higher and no live match has been read for it (`:205-208`).

**Generalisable rule: a ratio is only meaningful against a MEASURED denominator.** A denominator taken from a human's mental model of the game ("about one medic per 20-man squad") is a hypothesis. When adding any `UnitFloorPer`-shaped knob, print the denominator's own trajectory and confirm the ratio sits below its minimum, with margin, in the *worst* regime — and sweep it, because two values cannot find a cliff. (The off-switch contract is separate and intact: `perSupported <= 0` returns the flat floor verbatim, `:73-74`, so a profile that does not opt in is unaffected.)

Widening `IncomeWeights` is not free: it is a *value* in a shared score, and `world.yaml:312-313` carries a PITFALL that a $0 building listed there outbids real income POIs. ### `AIUtils.BotDebug` is default-off AND chat-only, so a lane instrumented only with it is structurally unmeasurable

`AIUtils.BotDebug` (`AIUtils.cs:92-96`) gates on `Game.Settings.Debug.BotDebug` (**default `false`**, `Settings.cs:171`) and routes to `TextNotificationsManager.Debug` → `AddSystemLine` (`TextNotificationsManager.cs:79-82`) — the in-game **chat pool**. It never reaches `debug.log`. A lane whose only instrumentation is `BotDebug` therefore has no post-hoc observability at all: *"the bot never bought a medic"* and *"nobody was recording"* are the same silence, and they are not distinguishable after the match. This is not hypothetical — `UnitBuilderBotModule.LogCompositionChoice` (`:1978-1988`) advertises itself as an "observability channel … so autotest log-mining can chart the standing composition against its targets", and there was nothing to mine, which is why a procurement hypothesis could only ever be recorded as *"leading, unmeasured"*.

The fix pattern is the one the supply and danger subsystems already use: unconditional `Log.Write("debug", …)`, or a designer-gated interval like `LogPick`'s `CensusLogInterval` (`:2001-2004`). **Before spending a benchmark run on a bot question, grep the lane for `BotDebug` and check whether the number you intend to read exists in a log at all.** Still dark for this reason: the composition-directed buy and DECLINE lines, the composition ceiling refusal, and the supply-fleet shortfall line — the unconditional `[composition] census` covers their *outcome*, not their *reasons*.

### A bot ordered onto un-standable ground is not rejected — the engine silently relocates it up to 10 cells

Both order paths a bot module uses run the destination through `Mobile.NearestMoveableCell`, which scans a radius-1..10 annulus for a cell the mover can enter *and stay in* (`Traits/Mobile.cs:834-856`; budget defaulted at `:808-812`): `Order("Move")` via `Move.OnFirstRun` (`Activities/Move/Move.cs:139-143`) and `Order("AttackMove")` via `AttackMove.ResolveOrder` (`Traits/AttackMove.cs:116`). So a ground unit ordered a short way into the sea walks to the beach and looks fine; it fails to move only when nothing standable is within 10.

**The consequence that matters is bookkeeping, not movement, and it is the reason "does a unit get stranded?" is the wrong triage question** — asking it produces false CLEARs. The bot is never told it was relocated, so any module that **stores** the requested cell, **compares** against it, or **keys** anything on it (a ledger claim, a re-issue deadband, an arrival radius) is now measuring against a cell its unit will never occupy. The worked case: `MountedTransportBotModule` tests delivery arrival within `DropOffArrivalRadius: 3` (`:874,883`, `ai.yaml:1516/:1574`) — **tighter than the engine's 10** — so a drop cell 4–10 cells offshore parked the carrier where the arrival test could never pass, the idle re-issue guard queued the identical Move (which completed instantly, being already there), and a loaded carrier never unloaded for the rest of the match. *The engine's own repair is what makes the stall permanent*; a rejection would have been recoverable.

The in-tree answer is `BotTerrain` (`Traits/BotModules/BotTerrain.cs`), one shared mover-bound predicate rather than the three inline copies it replaced: `PassableFor(mover)` binds terrain passability to that unit's locomotor (`:49-56`) and `TryNearestStandable` clamps the picked cell to the same radius the engine uses, `EngineRelocationCells = 10` (`:41,77-89`), returning false — the caller's signal to issue *no* order — when nothing standable is in reach. Clamp to the same reach deliberately: shorter gives up deliveries the engine would have completed, longer picks a cell the engine would not have chosen. **Matching the radius does not make the two agree outright**, and the residual hole is worth knowing: `PassableFor` tests TERRAIN only, while `NearestMoveableCell` also requires `CanEnterCell(..., BlockedByActor.Immovable)` and `CanStayInCell` (`Mobile.cs:847-852`) — so a terrain-passable cell occupied by a building is still relocated, and a module measuring against it is back in the trap.

### Six independent places decide a unit is available for tasking, and they share no code

Six-plus bot modules each build a pool of units they may order around, and **each re-implements the same predicate from scratch, inline, in its own private method** — owned, alive, in-world, has `IPositionable`, has `AttackBase`, not `Aircraft`, not claimed by me, not committed in the shared ledger. There is no base class and no shared helper; `BuildFreePool` alone appears in **seven** modules (`PoiOffensive`, `PoiGarrison`, `CaptureCoordinator`, `HelicopterSquad`, `MountedTransport`, `LayeredDefence`, `LaneAmbush`), and `IsEligibleCombatUnit` in four.

Two consequences for anyone making a cross-cutting change to "which units the bot may use":

- **A change to one predicate reaches only its own module.** There is no single seam; "the bot's free pool" is not a thing that exists.
- **There is an enumerated census of those sites, and it is a grep.** `StarvingRecruitGate` (`Traits/BotModules/StarvingRecruitGate.cs`) is the one cross-cutting availability rule that was actually walked to every site: one instance per module, tagged, in `PoiOffensive` (`:1102`), `PoiGarrison` (`:194`), `CaptureCoordinator` (`:539`), `LayeredDefence` (`:197`), `LaneAmbush` (`:164`) and `EngineerRouteOpen` (`:171`). The class is ammo-specific and should not be bent into a general filter, but **`grep -rn "StarvingRecruitGate\|ammoGate" engine/` is the checklist** for the next "don't task unit X for Y" rule. That it needed walking is the point: `SkipOutOfAmmoUnits` shipped on three of these modules and not the others, with no comment explaining the split — because there was no split, just sites nobody visited. **A rule added at one site does not merely fail to apply elsewhere; it looks complete, because the site you are reading has it.**
- **Recruit gates and RETENTION are separate code.** `PoiOffensiveBotModule.PruneAxes` is the retention half — a unit already recruited onto an axis is kept there by different code than the gate that admitted it, so **a change to the recruit gate alone never reaches units already committed.** Expect to edit both, and expect the fleet to take a full commitment cycle to reflect either.

### All bot orders funnel through `ModularBot.QueueOrder`

Every `bot.QueueOrder(...)` call across the ~25 BotModules lands in the single interface-explicit `IBot.QueueOrder` on `ModularBot` (`Traits/Player/ModularBot.cs:123-127`); `ITick.Tick` dequeues (`:257`) and `world.IssueOrder`s each (`:263`). So any per-order instrumentation or attribution is a **single-file change, not 25**. The issuing module is not on the order, but it is known at the tick loop and now recorded: `Tick` runs each `IBotTick` module via `if (t.IsTraitEnabled()) t.BotTick(this)` after setting `currentModuleTag = t.GetType().Name` (`:224-229`, cleared in a `finally` so an order queued outside a module tick attributes as `""`, `:236`; note **only enabled modules tick** — see §AI production's disabled-twin routing), and the attack-response path mirrors it (`:316-322`).

**`QueueOrder` is no longer a pass-through: it returns `bool` and an order can be DROPPED.** It takes a `BotOrderDamping` (`IBot.QueueOrder(Order)` defaults to `Protected`, `:123`) and runs the order through `BotOrderQueue.Admit` (`Traits/BotModules/OrderArbitrationMath.cs`) before enqueueing (`ModularBot.cs:137-145`); a non-`Admitted` verdict returns false and nothing is queued. **Suppression is opt-in — only a `Recurring` order can be dropped** (`OrderArbitrationMath.cs:527`) — but *recording* is not: a `Protected` order still establishes the standing record that protects its unit from the next `Recurring` challenger, so the suppressible set is narrow without narrowing what can be defended. Two rules follow.

- **The damping class must follow the CALL SITE's retry behaviour, not the order string.** Ask "if this is dropped, does anything re-issue it?" — if not, `Recurring` is silent data loss whose only symptom is a counter in `debug.log`. The measured case: the capture ferry's spare-seat fill copied `Recurring` from the frontline pool's boarding order and logged `candidates=3 boarded=0` — the dwell rule (`Admit`'s single-target branch, `:561-572`) drops an order to an actor holding a standing record inside the dwell window for a different destination, and fresh infantry near the SR has always just received something from another module. The frontline pool re-offers every scan and can afford the drop; `TryReserveCaptureFerry` is called once per capture dispatch and never re-offers, so a drop was a seat lost for the run. It is now unmarked/`Protected`, matching the capturer's own `EnterTransport`, with the rationale recorded at the call site (`MountedTransportBotModule.cs:642-649`).
- **Suppression perturbs the drain schedule for every module, including ones the gate never inspects** — `ordersToIssueThisTick` is a quotient of `orders.Count` (`ModularBot.cs:253`), so fewer queued orders means a smaller per-tick quotient and a few ticks of extra latency in the tail of an unrelated burst. FIFO order among survivors is exact and nothing is lost, so the effect is bounded latency, not reordering — but it is a deliberate, visible `@stable` change and the ai-bench baseline must be re-taken knowingly.
- **A green run is not evidence the fill happened.** The ferry test asserted a peak passenger count on the named carrier, reasoning only the ferry could load it — true *while the ferry owns it*, but once the task is torn down the carrier returns to the general pool and the ordinary frontline path loads it minutes later. The predicate had to be frozen at dismount. **A per-actor observable is not automatically an attributable one; the ownership window has to be part of the predicate.**

**THE INVARIANT, and it is a multiplayer-desync boundary, not a style rule.** The engine states it two lines above the bot activation: *"Bot logic is not allowed to affect world state, and can only act by issuing orders"* (`Traits/Player/ModularBot.cs:105`). The reason is `Player.cs:224-232` — `if (IsBot && Game.IsHost)` — **bot logic runs on the HOST ONLY.** So a bot module that mutates synced actor state directly, rather than issuing an order, applies that mutation on the host and on no other client: the game diverges the instant the module acts. The order system exists precisely because orders are the thing that replicates. A direct `actor.QueueActivity(...)` from inside a `BotTick` is therefore never merely untidy — it is a desync, and it needs a bot player present to fire, which is what makes it easy to miss.

- **Detector:** `Debug.SyncCheckBotModuleCode` (`Settings.cs:189`, **default `false`**) wraps bot module ticks in `Sync.RunUnsynced`, which throws `InvalidOperationException: RunUnsynced: sync-changing code may not run here` on the first synced mutation. Turn it on when auditing bot code. Two caveats: the throw happens in the guard's `finally`, *after* `ModularBot` clears `currentModuleTag` (`:236`), so the stack names only the wrapping loop and not the offending module — wrap each `t.BotTick(this)` individually if you need attribution. And because the instrument's success mode *is* an exception, a positive result looks like a harness failure (non-zero exit, no verdict file); pre-register that shape or you will re-run into the same crash reading it as noise.
- **Saved-game restore is the cheapest way to observe a violation, not the scope of the problem.** `ModularBot.Tick` early-returns while `IsLoadingGameSave` (`:206`), so on the replay the mutation never happens at all — whereas an order would have been recorded in the save's stream and replayed faithfully. That asymmetry turns any such write into a guaranteed restore divergence, which is how this class was first caught. **A fix here is a multiplayer fix that a saved-game test happens to be able to see.**
- **Standing hazard of the same shape:** any `IBotTick` module that draws `world.SharedRandom` breaks saved-game restore silently, because `SharedRandom.Last` feeds `World.SyncHash()` — a draw that happened live but not on the suppressed replay shifts the stream. As of 2026-08-12 no live bot-module draw site exists (the two under `Traits/BotModules/` are either not bot-gated or on a dead branch), but nothing enforces it.
- **Bisection finds only the FIRST divergence.** Several sites can produce the same failure, and a later leak is completely masked by an earlier one. After fixing one, **re-run** — do not assume clean.
- **`World.SyncHash()` does NOT cover the activity queue, so a sweep built on it cannot see the very class of write it is most often used to rule out.** The hash folds `[Sync]`-marked trait fields (`actor.SyncHashes`), `SyncedEffects`, `SharedRandom.Last` and `RenderPlayer` status (`World.cs:549-578`) — and `Actor.CurrentActivity` (`Actor.cs:62`) carries no `[Sync]`. It is narrower still than that list reads: a `[Sync]` field only reaches `actor.SyncHashes` when its declaring trait implements `ISync`, and an effect only reaches `SyncedEffects` when it implements `ISync` — see §"`[Sync]` is inert without `ISync`" below. A "whole-match sweep comparing `World.SyncHash()` around every bot tick came back clean" is therefore evidence about synced *trait state*, not about `QueueActivity`/`CancelActivity` calls. **Do not read such a sweep as closing the direct-write class**; the divergence only becomes visible downstream, once the changed activity moves something that *is* synced (a `Mobile.ToCell`, a facing). Corrected on 2026-08-12 by the author of the original closure claim, whose evidence was narrower than the claim.

### The bot free pool self-heals — only free-pool-EXCLUDED units can leak

`PoiOffensiveBotModule.BuildFreePool` (`:1855-1865`) scans **all** `world.Actors` (`:1860`) filtered by `IsEligibleCombatUnit` (`:2229`, requires `AttackBaseInfo` `:2233`, excludes aircraft), minus axis-claimed and ledger-committed units. Garrison/LaneAmbush/LayeredDefence use the same global scan. `SquadManagerBotModule` also scans globally but is **not** a consumer of this pool — it discards every ground unit at `:329-336` without claiming it (see §AI configuration), so it neither competes for nor replenishes the ground free pool. **Consequence:** an idle armed combat unit left anywhere on the map — even deep in contested territory after a drop — is re-collected regardless of location, so it is *self-healing*, not a leak. Only classes **excluded** from that pool can strand orderless at a hostile spot: when `UseUnitRoles` is on, `IsEligibleCombatUnit` (`:2271-2272`) admits only `MainBattle`/`IndirectFire` AND `!IsTroopCarrier`, so it excludes `ShortRangeAD`, `Recon`, `TransportLift`, `CaptureSpecialist`, `Logistics`, `AttackAir` (`UnitRole` enum, `Traits/World/UnitRoleResolver.cs:37`; `IsTroopCarrier` = has `Cargo` with `MaxWeight > 0`, `:239`). "Orderless-at-a-hostile-location" is therefore a bug **class** confined to dedicated non-combat units (a transport heli idling at its drop, a post-capture technician) — each needs an explicit return order; combat units do not.

**A class can be excluded "because another module owns it" when no module's config actually lists it.** Mobile SHORAD is the live case: `AdaptiveProductionBotModule.AntiAirRoles` is exactly `{ShortRangeAD}` so the bot **buys** it, but every ground movement module (`PoiOffensiveBotModule`, `PoiGarrisonBotModule`, `LayeredDefenceBotModule.IsLineEligibleByRole`) filters the pool to `MainBattle`/`IndirectFire`; `strykershorad` additionally trips the `!IsTroopCarrier` term (`Cargo: MaxWeight: 9`); and it is **not** in `MountedTransportBotModule`'s `CarrierTypes`. Bought, never moved, parked at the Supply Route for the match. There is a default-off `FoldShortRangeAdIntoLine` lever (`PoiOffensiveBotModule.cs:2269`, off even in `@experimental` — it trades air cover over the rear for air cover over the push, a doctrine A/B rather than a bug fix). Whenever a filter comment says another module owns an excluded class, check that module's YAML actually names it.

**Role classification margins are ONE cell on the two infantry types the line pool depends on.** `UnitRoleResolver.ExtractFacts` takes the MAX `MinRange` over every armament (`:288-289`) and classes the owner `IndirectFire` when that reaches `IndirectMinRange` = 4c0 **or** `MaxWeaponRange` reaches `IndirectRangeFloor` = 35c0 (a disjunction, `:364`). `^E3` — the bulk rifleman — carries an RPG secondary at `MinRange: 2c0` (`weapons-ballistics.yaml:305`) and `^AT` carries `ATGM` at `MinRange: 3c0` (`weapons-missiles.yaml:8`): margins of two cells and **one**. A weapon-balance pass nudging either to 4c0 reclassifies that infantry `IndirectFire`, dropping it out of `LayeredDefenceBotModule.IsLineEligibleByRole` (`:673-677`, `MainBattle` only) *and* out of the helicopter lift's passenger pool (`HelicopterSquadBotModule.IsLiftCandidate`, `:1596-1599`) — two consumers on one weapon number, with a purely behavioural symptom ("the bot stopped manning the line") that presents far from its cause. It is **not** silent, though: `Lint/CheckUnitRoleTable.cs` pins `("e3", MainBattle)` (`:83`) and `("at", MainBattle)` (`:85`) against the real ruleset and emits an error, so the change fails `make test` rather than the game — the NUnit `UnitRoleResolverTest` works on hand-encoded facts and does not cover these two. Adjacent margin, safe today: `^E3` stays out of the `Recon` branch on SPEED alone (`Mobile: Speed: 25`, `infantry.yaml:46`, against `ReconSpeedFloor = 110`, `:163`) because its 14c0 rifle does satisfy the `ReconMaxWeaponRange` 16c0 clause; `^AT` fails the range clause too (ATGM Range 20c0), so "speed is the sole discriminator" is true of the rifleman, not of infantry generally.

**The `RetreatCapturerWhenDone` `[Desc]` states the right conclusion for the wrong reason, and the wrong reason makes the exclusion look accidental.** `CaptureCoordinatorBotModule.cs:309-310` reads "A CaptureSpecialist has no `AttackBase`, so it is EXCLUDED from every combat free pool". It does have one: `^TECN` inherits `^ArmedCivilian`, which carries `AttackFrontal` and an `Armament: Weapon: Pistol` (`ingame/infantry.yaml:370-378`, `:2177`). So a technician **passes** `IsEligibleCombatUnit`'s trait test and is excluded one line later, by ROLE, under `UseUnitRoles`. Right verdict, wrong mechanism — and it matters, because a trait-absence exclusion reads as incidental and reversible while a role-filter exclusion is neither. *(Flagged 2026-08-19, code comment not edited — this doc is the correction of record.)*

**For an availability conjunct, prefer a predicate that is true from tick 0 over one that becomes true when the data arrives.** `DangerFieldLayer` creates a player's `PlayerField` lazily inside `RecomputePlayer` (`DangerFieldLayer.cs:473-474`), first reached after the deterministic stagger and then only on that player's round-robin slot — while bot modules scan from tick 1 (`scanCountdown` is a default `int` = 0). A gate written as "has the field been built yet?" therefore **fails OPEN for the entire opening window**, which is exactly when opening-play bugs live. Gate on `InfluenceStack.Participates(player)` — knowable at tick 0 — and let the *reading* return 0, which for a participant with no field yet is the honest answer ("nothing believed here"). This is the general shape: a conjunct whose truth tracks data arrival silently disables itself over the warm-up.

### The PoiGoalGuard commitment ledger — commit-on-order + three-tier timers

`PoiGoalGuard` is a shared single-instance world module (fetched by consumers, gated `enable-ai-experimental || enable-ai-stable`) holding a per-unit commitment ledger that makes a claimed unit invisible to other axes/modules. Two invariants govern it:

- **Commit-on-order is a PAIR, not a single act** (`CommitOnOrderMath`, `PoiGoalGuard.cs:285-300`). Every executor must (a) commit every unit it orders AND (b) recruit only from the ledger-checked free pool — *both halves*. Commit-alone still lets a writer poach a unit another already committed (its own `Commit()` overwrites the prior objective); recruit-check-alone leaves the reverse steal channel open. The gate seams are `ShouldCommit(flag, ledgerAvailable)` (per-profile twin) and `ShouldCommitShared(flag, ledger, isExperimentalBot)` (adds a runtime `BotType == experimental` term for a module that is a single `enable-ai-any` instance, e.g. Garrison, which a per-profile YAML flag can't confine). Objective keys are **disjoint prefixes** so claims stay attributable and never collide: `offense:` / `capture:` / `capture-escort:` / `capture-defend:` / `transport:` / `garrison:` / `defend-line:<x>,<y>` (cell-based) / `ambush:`.
- **The ledger only arbitrates between modules that BOTH WRITE it — "I read the ledger" is not a claim.** A flag that gates ledger *resolution* silently gates participation: `MountedTransportBotModule` resolves `goalGuard` only under `CommitPassengers` (`:313`), which the `@poi`/stable twin does not set (`ai.yaml:949`), so on `@stable` that module neither reads nor writes and the ledger cannot mediate between it and the heli lift — both draw passengers from the same reserve bubble and each would yank the other's boarder. Read-only participation is asymmetric and secures nothing. ### `BotOrderGate` can only damp orders it CLASSIFIES — everything else is structurally ungateable

Every bot order passes through `ModularBot.QueueOrder` (`ModularBot.cs:127`), which consults `BotOrderGate.Admit`, and both profiles arm the gate (`RespectCommitmentsOnIssue: true`, `ReorderDwellTicks: 120`, `ai.yaml:48-57`). So `"ForceAttack"` can never be damped while a `Move` to the same unit can be — **a module that walks a unit and then fires can have the walk dropped and the shot kept.** When reasoning about whether the gate protects something, look up the order string in `Classify` first; the gate's config fields say nothing about which orders it can see.

Two adjacent facts that matter when a bot module fires a weapon:

- **The spawn/attack notification happens `FireDelay` ticks AFTER the order, not at order time.** `na.Attacking(…)` is invoked inside the `ScheduleDelayedAction(Info.FireDelay, Burst, …)` callback (`Armament.cs:691-692`, callback opened at `:531`). At `FireDelay: 50` and the mod's real 16.67 tps that is **3.0 s**, and a `CarrierMaster` whose `Attacking` early-returns on `IsTraitPaused` (paused by `moving`) must stay unpaused for that whole gap — an operator that starts moving during it fires the weapon and spawns nothing.
- **Turning does not grant `moving`.** `GrantConditionOnMovementInfo.ValidMovementTypes` defaults to `{ Horizontal, Vertical }` and **excludes `Turn`** (`Traits/Conditions/GrantConditionOnMovement.cs:25`), so rotating onto a target is safe.

### `StancePositioningExecutor` can only ever move an IDLE unit — its gate says when it is ENABLED, not when it ACTS

The trait has **exactly one mover**: `self.QueueActivity(new Move(…))` at `StancePositioningExecutor.cs:426` (an exhaustive grep of the file for `QueueActivity` and `new Move` returns that one hit). It sits inside `INotifyIdle.TickIdle` (`:289-427`), which the engine invokes only when `CurrentActivity == null`, and it guards itself a second time at `:296` with `if (self.CurrentActivity != null) return;`. **Therefore any unit holding a long-running activity is untouchable by this trait for as long as that activity lasts**, and the plausible-sounding failure "the positioning layer walks a unit off station mid-task" is unreachable.

**What it CAN still do to such a unit is touch the ledger, and that is a separate reach.** `CommitManagement` overwrites the `PoiGoalGuard` entry with `"tacpos:"+ActorID` (`:665`) and `ReleaseManagement` calls `Ledger.Release(self)` unconditionally (`:676`), never consulting `IsCommitted` — and `PoiGoalGuard.Release` is keyed on the **unit**, not the objective (`PoiGoalGuard.cs:100`, `commitments.Remove(unit)`), so it deletes whatever claim the actor holds regardless of who wrote it. That is a general hazard for any module claiming a unit this executor also manages.

**The general trap, which is why this is here rather than in a bot-module note:** *a trait's `RequiresCondition` tells you when it is ENABLED, not when it ACTS.* Two reviewers and a ruling reasoned about this trait's effect on a unit from its gating condition alone and all three got it wrong in the same direction, because the gate says nothing about `INotifyIdle` being the only entry point. **When the question is "can this trait do X to this unit", find the call site of X, not the condition.**

**Instrument note for any condition-gating change:** `make test`'s unconsumed-condition warning is a usable check that a condition still reaches its consumer, but **compare those warning lines as SETS, never by text diff** — the member order of the residual list varies between occurrences within a single log (it recurs once per map) while the set is stable.

### Bot decisions ARE seed-reproducible (since main @ 2d3c8fe0)

`World.cs:222` seeds `SharedRandom` from the lobby `RandomSeed` (deterministic, network-synced); `World.cs:231` now also seeds `LocalRandom` — from that same `RandomSeed` via a fixed decorrelating transform `(int)(RandomSeed*6364136223846793005 + 1442695040888963407)`, guarded on `RandomSeed != 0` so normal gameplay (seed = `DateTime.Now`) still varies per launch. The bot modules make their *decisions* off `world.LocalRandom` (e.g. `UnitBuilderBotModule` picking which unit to call in; squad / layered-defence / support-power scan timing and target choice), so before this fix `LocalRandom` was unseeded (`new MersenneTwister()` → `Environment.TickCount`) and two same-`Test.RandomSeed` runs diverged within ~125 ticks. **Now a fixed seed is a *reproduction*:** verified byte-identical verdicts (and tick-by-tick score logs) across two seed-1017 hidden Mode-B matches, with a different-seed negative control diverging as expected (`WORKSPACE/ai-bench/runs/260720_seeded_determinism_verify.md`). The derived seed is decorrelated from `SharedRandom`'s combat rolls so the two MT streams stay independent. The verdict JSON records the seed (`verdict_version` 5). Note: OpenRA's off-thread (async) pathfinding did **not** need any extra work for this — it applies its results deterministically on the sim thread even with WW3MOD's modified movement, so seeding the single unseeded `LocalRandom` was sufficient for full byte-identical replay. Aggregate-over-N benchmarking is still the right way to *evaluate a code change* (one seed is one battlefield); what seeding buys is a *stable* mean over a fixed seed-set. Moving bot draws into `SharedRandom` would instead shift every subsequent combat roll and break the frozen `@stable` A/B baseline's RNG-stream byte-identity (the baseline was recorded *on* the seeded-`LocalRandom` build `2d3c8fe0`, so the decorrelated-seed fix is already baked in). Re-investigated and closed HOLD 2026-08-03: the safe fix is already in `main`, so re-implementing is a no-op.

## Determinism & sync

*(Re-parented 2026-08-19. These subsections lived under §AI configuration only because §RenderPlayer happened to be there; none of them is about bot configuration. Markdown anchors derive from the heading text alone, so every existing `§`-by-name reference to them still resolves.)*

### A trait's `[Sync]` members are XORed with NO position weighting — so two bools that change together are invisible

`Sync.GenerateHashFunc` emits `Ldfld; <coerce>; Xor` per annotated member into a single accumulator (`Sync.cs:77-106`), and `EmitSyncOpcodes` coerces a `bool` to raw **0 or 1** (`:62-70`). Measured by reflection, pinned in `OpenRA.Test/OpenRA.Mods.Common/SyncFoldingTest.cs`:

| two `[Sync] bool` fields | trait hash |
|---|---|
| `false,false` | 0 |
| `true,false` / `false,true` | 1 |
| `true,true` | **0 — identical to both-false** |

**Any even number of bools flipping at once cancels**, and two bools can never be distinguished from each other; `int` fields differing only in bit 0 collide identically. This bites hardest at exactly the wrong moment — a trait that sets two flags in the same statement block cancels them on the *critical transition*, i.e. the tick it starts mattering, so the per-field annotations leave the trait effectively unhashed precisely when it matters.

**PITFALL — this looks like a dead-constant bug and "fixing" it is worse than leaving it.** `EmitSyncOpcodes` pushes `0xaaa` then `Brtrue`s on *that constant*, so the branch is always taken and the `Pop; Ldc_I4 0x555` arm is unreachable. It is tempting to restore the intended `0x555`/`0xaaa` encoding. **Don't:** both bools would still use the same encoding, so `0x555^0x555 == 0xaaa^0xaaa == 0` and the cancellation is completely unchanged. Only distinct bit *positions* fix it. Meanwhile restoring the constants changes every sync hash in the game, breaking existing replays and saves, and buys zero additional detection. **The real remedy is to not rely on two bools carrying independent information through one trait's hash.**

### Cross-runtime float drift is a WEAK desync hypothesis here — structurally, then empirically

Worth settling early, because "different .NET versions" is the first thing reached for when a desync has no other explanation, and chasing it costs days.

- **Floats and strings cannot enter the sync hash at all.** `Sync.EmitSyncOpcodes` accepts the registered custom types, `bool` and `int`, and otherwise throws `NotImplementedException: SyncAttribute on member of unhashable type` **at IL-generation time** (`Sync.cs:58-72`). A float-valued `[Sync]` field is a startup crash, not a silent drift.
- **No transcendental function sits on a synced path.** Simulation trigonometry is an integer lookup — `WAngle.Cos()` indexes `CosineTable` (`WAngle.cs:74-76`). The `Math.Sin`/`Cos`/`Atan2` calls that do exist are rendering and UI (`Graphics/Util.cs`, `SpriteFont.cs`, `ScreenShaker.cs`, `MarkerLayerOverlay.cs`), plus client-side order *generation*, whose result travels as a networked order rather than as local state.
- **Measured, and it is a measurement rather than a proof.** .NET 6.0.36 / 8.0.30 / 10.0.11 produced identical per-frame sync traces across all 6000 net frames of a full 12-minute match (2026-08-17, seed 20260817), with determinism, sensitivity and hook-inertness controls. **One machine, one match, one seed — same CPU and same libm.** A cross-*machine* difference is untested and this result does not speak to it.
- **The TFM does not choose the runtime; `RollForward: Major` does** (`engine/Directory.Build.props:26`). So cross-runtime exposure is already live under today's `net6.0` target — a TFM bump raises the floor rather than introducing the risk. (Roll-forward only *rolls* when the requested version is absent, so a player who has 6.0 installed runs 6.0; the exposure is players who lack it.)
- **PITFALL: `Test.ForceSyncReports` cannot be used under a replay.** The gate is `Connection is not ReplayConnection && … && (humanClients > 1 || (TestMode.IsActive && TestMode.ForceSyncReports))` (`OrderManager.cs:161-164`) — the override lifts only the human-client floor, never the replay term. "Replay the desyncing match with `ForceSyncReports` and diff the `syncdiag-*` files" produces **no files at all**.

### `[Sync]` is inert without `ISync` — and the same type test guards synced effects

**Two places decide what reaches the sync hash, and both are a `is ISync` type test rather than an annotation or a convention.** This is the single most useful thing to know before reading a sync report as evidence.

- **Traits.** `Actor.cs:206` is `{ if (trait is ISync t) syncHashesList.Add(new SyncHash(t)); }`. A `[Sync]` attribute on a class that does not implement the marker interface — directly or via an `ISync`-supplying base such as `ConditionalTrait<T>`, `AttackBase`, `Turreted` or `Mobile` — **hashes nothing and warns about nothing.** The annotation reads as coverage and is decorative.
- **Effects.** `World.Add(IEffect)` files an effect into `syncedEffects` **only when `e is ISync`** (`World.cs:421-422`), and `SyncHash()` folds only `SyncedEffects` (`World.cs:566`). This is why the many `RenderPlayer` reads inside sim-ticked `Tick` methods that spawn a cosmetic `FloatingText` (`Sell.cs:48`, `DonateCash.cs:40`, `GainsExperience.cs:128`, `GivesBounty.cs:89`, `Refinery.cs:155`, `RotateToEdge.cs:392`) are safe: `FloatingText` is `IEffect, IEffectAnnotation` and not `ISync`, so it never enters the hash. **The guard is the type test, not caller discipline** — a cosmetic effect that ever gained `ISync` would convert every one of those sites into a desync at once.

**Consequence for reading a sync report: a matching trait clears that trait's HASHED members and nothing else.** Before treating "trait X matched" as evidence that X's behaviour matched, open X and list which members are actually hashed. A field with no annotation, or an annotation on a non-`ISync` type, produces divergence with *no upstream trait named anywhere in the report* — an effect with no visible cause. When something moved and nothing explains why, suspect unhashed state before floating point or runtime versions. (The concrete incident: `AutoTarget (4)` matching in both 2026-08-16 desync reports was used by more than one person to rule out a stance/cohesion divergence, and could not — only `nextScanTime` and `IsTraitDisabled` were in the hash.)

**Guards that now exist.** `engine/OpenRA.Test/OpenRA.Mods.Common/SyncAnnotationTest.cs` fails the build if any type gains inert `[Sync]` annotations, and separately proves every `ISync` type can generate its hash function — worth having because hash functions are IL-emitted at runtime (`Sync.cs:72` throws `NotImplementedException: SyncAttribute on member of unhashable type`), so `[Sync]` on an enum or a double compiles fine and throws only in a live game. For an enum, sync an `int` projection: `int SyncStance => (int)stance;`. The mod-side `CheckSyncAnnotations` lint reports at *warning* severity and `TREAT_WARNINGS_AS_ERRORS` is read at `CheckYaml.cs:57` and set nowhere in the repo, so the lint alone cannot fail anything — the NUnit test is the load-bearing guard.

### `RenderPlayer` is render-side only

`world.RenderPlayer` never touches the sim or the sync hash. `FogObscures`/`ShroudObscures` all short-circuit to `false` when `RenderPlayer == null` (`World.cs:109-115`), no player's `MapLayers` is mutated, and the sync hash reads `p.UnlockedRenderPlayer`, not `world.RenderPlayer` (`World.cs:572-574`). - **A World-actor render overlay must fall back to `LocalPlayer`** — in the autotest harness `world.RenderPlayer` is **null** even though the World-actor's `RenderAnnotations` is still called, so `var viewer = world.RenderPlayer ?? world.LocalPlayer;` is the correct local-client identity (still per-player-legal — reads only the viewer's own layer).
- `ShroudRenderer.UpdateShroud` only clears drawn shroud sprites when a render player is active; flipping `RenderPlayer` to null on a *live* client (world-view / `DevCinematicView`) must still clear each dirty cell's sprites or the map stays black despite uniform visibility.

**Visibility is NOT a network-desync risk, and this was established exhaustively rather than by spot-check** *(all 40 `CanBeViewedByPlayer` call sites read, as of `main @ 61e46e64`; earlier drafts named ~5 and were flagged as the weakest claim in their own audit)*. **38 of the 40 pass a simulation `Player`** — `self.Owner`, `manager.Self.Owner`, a `player`/`Bot.Player`/`firedBy` binding, or `targetOwner` = `target.Actor.Owner ?? target.FrozenActor.Owner` (`AutoTarget.cs:748`, `AttackMoveActivity.cs:203`). `TargetExtensions.cs:62,79` sit inside `Target.Recalculate(this Target t, Player viewer, …)` and so take an open-ended `viewer` — **that one needs checking at every caller, not at one**: `Recalculate` and its wrapper `RecalculateInvalidatingHiddenTargets` are called from `Attack.cs:103`, `AttackFollow.cs:133,357`, `AttackOmni.cs:68`, `LeapAttack.cs:85`, `Enter.cs:76`, `Follow.cs:55`, `MoveAdjacentTo.cs:77`, `Fly.cs:146`, `FlyFollow.cs:58` and `FlyAttack.cs:107,272,323` — a dozen sites, **every one passing `self.Owner`**. *(A 2026-08-19 audit recorded this as "its only caller is `AttackOmni.cs:68`"; that was wrong, and is corrected here. The conclusion survives because all the callers it missed pass a simulation player too — but the enumeration did not, which is the README §Four-shapes trap of a verdict outliving its justification.)* **Exactly two sites receive a client-local player, and both are confined to render/UI — name them explicitly, because an unnamed exception costs the reader the whole claim:**

- **`World.cs:109` — `FogObscures(Actor a)` passes `RenderPlayer` straight into `CanBeViewedByPlayer`.** This is the first thing anyone who greps the method will hit, so it reads as a refutation and is not one: every caller of the `FogObscures(Actor)` overload is render, UI or order-generator code — `WithDecorationBase.cs:88`, `RenderMouseBounds.cs:46`, `CombatDebugOverlay.cs:54`, `Selection.cs:171`, `MiniMapWidget.cs:419`, `ViewportControllerWidget.cs:249`, `SelectionUtils.cs:57,122`, `UnitOrderGenerator.cs:32,160`, `RepairOrderGenerator.cs:37`, `GuardOrderGenerator.cs:90`.
- **`WithSpottedDecoration.cs:105`**, whose `viewer` is `self.World.RenderPlayer ?? self.Owner` (`:86`). Reached only from `WithDecorationBase.cs:117` (`IDecoration.RenderDecoration`); the trait declares no `[Sync]` and no `ISync`.

So a synced code path branching on visibility is safe in network play. **Do not conflate this with saved-game restore**, where shroud must be reconstructed and bot ticks are not replayed — `AttackMoveActivity` ending a march on `CanBeViewedByPlayer` is a real restore hazard and not a network one.

**Adjacent trap, clean today but worth knowing:** `IResourceLayer.IsVisible(CPos)` is implemented as `!world.FogObscures(cell)` (`ResourceLayer.cs:301`) — a `RenderPlayer` read behind an interface name that promises nothing about rendering. Its only consumers are `ResourceRenderer.cs:211` and `TSVeinsRenderer.cs:243`, both renderers, so nothing is wrong now. But `resourceLayer.IsVisible(cell)` is exactly what simulation code would reach for, and the leak would be invisible at the call site.

### A per-machine settings file is a desync source, and the remedy is to issue ORDERS rather than to write the state

**A desync does not need an in-match action — a file on disk is enough.** `UnitDefaultsManager` (`UnitDefaultsManager.cs:47`) is backed by `Platform.SupportDir/ww3mod/unit-defaults.yaml`, a file that differs per machine and is not part of the map, the mod rules or the order stream. Until `8afcbbf8` (2026-08-17) `AutoTarget.Created` read it and wrote the authoritative `stance` / `engagementStance` / `cohesion` / `resupplyBehavior` fields — and because `Created` runs **on every client for every actor**, each client applied *its own* preferences to *everyone's* units. Synced state diverged with no player input at all.

**The shape to recognise:** any trait constructor or `IWorldLoaded` hook that reads client-local configuration and assigns a synced field is a desync by construction, and it presents as a divergence nobody did anything to cause. The house remedy is recorded in-code at the site (`AutoTarget.cs:514-518`): `UnitDefaultsManager` now applies the preference **client-locally by issuing the normal `SetUnitStance` / `SetCohesion` / … orders**, which travel the order stream and every client resolves identically. Orders are the only channel that makes a client-local decision legal.

The companion idiom is `Predicted*` — `AutoTarget` carries `PredictedStance` / `PredictedEngagementStance` alongside the synced fields (`AutoTarget.cs:504-505`, `:546`) so the UI can show the player's click immediately while the authoritative value waits for the order to resolve. **Optimistic UI belongs in a `Predicted*` mirror, never in the synced field.**

### An `IOrderGenerator` runs only on the client holding the mouse

Any simulation mutation an `IOrderGenerator` performs that is **not** carried by a yielded `Order` happens on exactly one machine. Orders are the only thing replicated between clients, so a client-local `QueueActivity`, `CancelActivity` or trait-state write inside a generator is a desync by construction — and one that moves units, which is the fastest possible route to a position divergence.

**The class is currently closed, and it was closed by enumeration.** All 20 concrete implementations were read *(as of `main @ 61e46e64`; the count was 22 at `43d55ace`, before `CargoUnloadOrderGenerator` and `EjectRallyOrderGenerator` were deleted)*. Every one yields `Order`s and mutates nothing else; the only writes are legitimately client-local — `world.CancelInputMode()`, `world.Selection.Clear()`, `world.OrderGenerator = …` (`ChronoshiftPower.cs:175`), `Game.Cursor.Lock()` (`SelectDirectionalTarget.cs:66,85`), notification sound/text, and the generator's own fields. Two sites to know:

- `RepairOrderGenerator.cs:61` calls a trait method directly (`Repairable.FindRepairBuilding`), which is the known-bad *shape* — but the method is a pure LINQ query (`Repairable.cs:156-167`) and writes nothing.
- `UnitOrderGenerator.cs:71` (`ControlAllUnitsManager.MarkPlayerControlled`) genuinely mutates a synced world trait that gates bot order issuance (`ModularBot.cs:260-263`), but is behind `DeveloperMode.IsControlAllUnitsActive` and so should not fire in a release match.

`PatrolOrderGenerator` carries a PITFALL at `:52-56` recording the rule, and yields a grouped `Order` at `:63-68` with the authoritative route in `TargetString` (the `Target` is the first waypoint, carried for target-line feedback only, so a group-order modifier that rewrites `Target` cannot silently move one client's patrol).

**Method note — the implementor count is the part that lies.** A depth-1 grep for classes whose base list names `IOrderGenerator` returns 18 and misses `GuardOrderGenerator`, because generators subclass *concrete* generators (`GuardOrderGenerator`, `AttackMoveOrderGenerator`, `ForceModifiersOrderGenerator` ← `UnitOrderGenerator`; `SelectNukePowerTarget` ← `SelectGenericPowerTarget`). An under-count presents as a clean sweep. **Compute the transitive closure and cross-check against compiled-assembly reflection**; naive counts of 16, 17, 18, 23 and 24 are all easy to reach and all wrong.

## Networking: transport, hosting, and NAT

### The mod version check fails SILENTLY OPEN, so "WW3MOD reads as up to date" is not evidence that anything checked

`WebServices.CheckModVersion` (`WebServices.cs:50-56`) initialises `var status = ModVersionStatus.Latest` and moves it only on three **exact** response literals — `outdated`, `unknown`, `playtest`. Anything else leaves it at `Latest`: an empty body, a redirect, an HTML error page, a body with trailing whitespace. The whole request is additionally wrapped in `catch { }` (`:60`), so a DNS failure, a timeout or a TLS error is indistinguishable from a clean "you are current". **There is no code path that reports "the check did not run."**

Two consequences worth carrying. First, WW3MOD's apparent up-to-date status is a property of what upstream's master happens to return for an unregistered mod, not of anything this repo controls or observes — and the visible failure mode if that ever changed is a player-facing banner ("You are running an unrecognized version of OpenRA…", `chrome.ftl`), because `Debug.CheckVersion` defaults true (`Settings.cs:156`) and `mods/ww3mod/mod.yaml` overrides neither it nor the `WebServices` URLs. Second, and more general: **a status enum initialised to the benign value and advanced only by explicit success literals cannot distinguish "fine" from "never asked".** Before treating any such readout as a signal, check what its default is and whether a failure path can reach it.


**The net stack is stock OpenRA.** `git log` over `engine/OpenRA.Game/Network/`, `engine/OpenRA.Game/Server/`, `MasterServerPinger.cs`, `ServerCreationLogic.cs` and `DirectConnectLogic.cs` shows no WW3MOD change to connection, NAT or advertisement logic — the only mod edit in that whole set is the tournament seed override at `Server.cs:307-310`. Do not go looking for a mod-specific networking divergence; there isn't one. (The NAT *diagnostics* below are ours.)

**Transport is TCP, exclusively, both directions.** The server listens with `new TcpListener(endpoint)` (`Server/Server.cs:250`) and accepts via `listener.AcceptSocket()` (`:280`); the client dials out with `new TcpClient(...) { NoDelay = true }` (`Network/Connection.cs:142`). **There is no UDP path for game traffic at all** — the only UDP in the engine is `BeaconLib` LAN *discovery* broadcast (`MasterServerPinger.cs`), which carries listing metadata and no orders, and the diagnostic socket described below. This rules out UDP hole punching, the technique that makes most other games NAT-free. The reliable-ordered-stream assumption is load-bearing: the sim is deterministic lockstep and the tick gate is `IsReadyForNextFrame => GameStarted && pendingOrders.All(p => p.Value.Count > 0)` (`Network/OrderManager.cs:201`) — every client's frame must arrive before anyone advances, so **a dropped frame is a stall, not a rubber-band.**

**The host is a listen server.** `Game.CreateServer` constructs `new Server.Server(...)` **in-process**, and the same process then connects to it as an ordinary client (`Game.cs:1129-1135`, binding `IPAddress.IPv6Any`/`Any` on `ListenPort`); skirmish uses the same class on `IPAddress.Loopback` with `AdvertiseOnline = false` (`:1143-1153`). A standalone headless dedicated server also exists and is built and shipped (`engine/OpenRA.Server/Program.cs`); `ServerSettings` carries fields that only make sense there (`RequireAuthentication`, `ProfileIDWhitelist`/`Blacklist`, `EnableSingleplayer`).

**The joining side is already fully NAT-free**, and it resolves DNS names. A joiner only ever makes outbound `TcpClient` connections and binds no listening socket, ever. `ConnectionTarget` stores `DnsEndPoint`s and resolves through `Dns.GetHostAddresses` (`Network/ConnectionTarget.cs`), so a hostname works everywhere an IP does — including the Direct Connect box, whose field is passed straight through with no format validation (`Widgets/Logic/DirectConnectLogic.cs`). WW3MOD uses the stock multiplayer chrome unmodified (`mod.yaml:201-203`), so Direct Connect is present and works today.

**The inbound port is only needed during the lobby.** The accept loop exits and calls `listener.Stop()` as soon as `State != ServerState.WaitingPlayers` (`Server.cs:265-271`). Once the match starts, established connections carry it and nothing new is accepted — so a port-forward requirement is a *join-time* requirement, not a whole-match one.

**"Server port is not accessible from the internet" is a remote verdict, not a local check.** The host POSTs its advertisement to `WebServices.ServerAdvertise` and parses the reply with the regex `^\[(?<code>-?\d+)\](?<message>.*)`; **code 1** means the master could not reach the port. The mechanism: the host advertises its address as the literal placeholder `Address = "0.0.0.0:" + ListenPort` (`Network/GameServer.cs:219`), so the master learns the public IP from the source of the HTTPS POST and probes back at it. That probe lives on the master server and is **not in this repo** — only its verdict is, and on its own the verdict carries zero diagnostic detail: one bit covering "no route, wrong LAN target, CGNAT, firewall, or port closed" alike. It also fires **only on the initial ping** (`isInitialPing`), so a mid-lobby change in reachability is never re-reported.

**WW3MOD advertises on OpenRA's official public master server.** `WebServices` defaults to `https://master.openra.net/{games,ping}` (`WebServices.cs:21-22`) and `mods/ww3mod/` contains **no `WebServices` override**, while `mod.yaml:270` does register `MasterServerPinger`. So every advertised WW3MOD lobby is pinging, and being probed by, third-party infrastructure this project does not control. Pointing at our own master is a one-block YAML addition, not a code change.

**UPnP/NAT-PMP ships ENABLED, and code 1 is expanded locally into the step that actually failed.** `ServerSettings.DiscoverNatDevices` defaults to **`true`** (`Settings.cs:60`), and `Nat.Initialize` starts `Mono.Nat` discovery when it is set (`Network/Nat.cs:44-53`). `Nat.TryForwardPort` returns a `NatForwardStatus` (`DiscoveryDisabled` / `NoDeviceFound` / `DeviceRejected` / `Forwarded`), and `MasterServerPinger.DiagnosePortForward` maps that snapshot onto distinct fluent keys instead of one generic string — plus a carrier-grade-NAT branch that outranks the rest, since no router rule can expose a port behind a second layer of ISP NAT. Two subtleties before touching it: `ForwardStatus` is a **snapshot taken when the server started** while discovery is asynchronous, so a device that answers later leaves the snapshot reading `NoDeviceFound` while `Nat.Status` reports `Enabled` (the code detects that skew and falls back to the generic line rather than naming a cause the rest of the UI contradicts); and `DiagnosePortForward` does socket work, so it is deliberately built **outside** the message lock `Tick` takes every frame. The create-server panel surfaces `Nat.Status` as a UPnP notice (`ServerCreationLogic.cs`), and `mods/ww3mod/chrome/` has no `settings-advanced.yaml` because it **inherits** `common|chrome/settings-advanced.yaml`, which carries the `Checkbox@NAT_DISCOVERY` toggle — absence there means inheritance, not absence.

**Finding the LAN address a router rule must point at.** The listeners bind `IPv6Any`/`Any`, so every endpoint the engine logs reads `0.0.0.0` and names no interface — useless for the single most common hosting failure, a port-forward rule aimed at a DHCP address the machine no longer holds. `NetworkDiagnostics.GetLocalAddress()` (`Network/NetworkDiagnostics.cs`) obtains it by `Connect`ing a `Dgram` socket to `192.0.2.1` (RFC 5737 TEST-NET-1, never routed, so it cannot be mistaken for contacting a third party) and reading `LocalEndPoint`: **`Socket.Connect` on a datagram socket transmits nothing** — it only makes the OS bind the socket to whichever interface it *would* route that destination through. It returns null when there is no route off the machine, which is a legitimate answer that must be handled, but it never returns the wildcard.

**There is no relay, proxy, STUN, hole-punching or connect-by-ID path anywhere in the engine.** Servers are addressed only as host:port (`GameServer.Address`/`Port`, `ConnectionTarget`). Any relay would be new work from zero — but because the transport is a plain TCP stream with no address baked into the payload, **a dumb TCP forwarder needs no engine change at all**: a joiner pointed at a forwarder is indistinguishable, to the engine, from a joiner pointed at the host.

**Diagnosing a multiplayer desync — what the handshake can and cannot see.** `Server.ValidateClient` rejects on exactly three things: mod id, `ModData.Manifest.Metadata.Version`, and `OrdersProtocol`. **`Metadata.Version` is a hardcoded literal in `mod.yaml` that never moves when engine C# changes**, so *two players on different builds pass the handshake* — no check exists that can see a stale binary. Two structural cautions for anyone adding one:

- **`Server.ValidateClient` wraps its whole body in a catch-all that calls `DropClient`.** Any exception thrown by code added there — including a diagnostic that touches the file system — makes the game **unjoinable** rather than merely unfingerprinted. Anything added must be non-throwing by construction.
- **Each half of a build fingerprint must be measured where the thing it describes takes effect.** Engine C# is *compiled*, so its identity has to be stamped at **build** time — the running binary is whatever was on disk when it was last compiled, not what the working tree says now. Mod YAML and content packages are *read at load*, so theirs must be computed at **run** time. Inverting either half produces a fingerprint that agrees while the games differ. Note `Folder.Name` is the **absolute path on disk** (`FileSystem/Folder.cs:25`), so any digest over mounted packages must hash the leaf names *inside* each package, never the package name — hashing the name makes two installs differ forever by construction.

**The content packages are the most likely thing to differ, and nothing fails loudly when they do.** `mod.yaml` mounts `~^SupportDir|Content/ra/v2/` — a Red Alert installation **outside the repository**, extracted independently by each player from a potentially different release. A mismatch there is invisible to the handshake and to the mod's own loading path.

**Two diagnostics traps worth knowing before you trust a report file.** `Log.AddChannel` returns early if the channel name already exists (`Support/Log.cs:147-148`), so a component that derives a fresh timestamped *filename* per dump but reuses a fixed *channel* name writes every later dump into the **first** file — the second desync in a process appends to the first game's report. And **hand-editing `settings.yaml` is not a reliable way to set anything**: `Settings.Save()` writes back only fields differing from their *compiled* default and **deletes** nodes that match it, and it runs on ordinary paths including every server join — so a hand-set value that happens to equal the default silently disappears.

**Server/lobby notification strings live upstream, not in the mod.** The `[FluentReference]` consts name `notification-`-prefixed keys that resolve out of `engine/mods/common/fluent/common.ftl` (loaded via `mod.yaml`'s `FluentMessages: common|fluent/common.ftl`). **When changing a server or lobby notification string, grep `common.ftl` first**, and only fall back to `mods/ww3mod/languages/en.ftl` if the key genuinely lives there (`internet-server-nat-*` really is ww3mod-owned and live). Related: a ServerTrait can only pass Fluent *arguments* if the queue it uses carries them — `Server.SendFluentMessage(string key, params object[] args)` has always supported flat key/value pairs, but a queue of bare strings cannot. Argument type matters too: an `int` is marshalled as a `FluentNumber` and renders with locale digit grouping, so **a port number must be passed as a string** or `1234` prints as `1,234`.

## Saved games: an order stream, not a snapshot

**`.orasav` stores orders, not world state.** The format is explicit (`Network/GameSave.cs:273-286`): a list of orders in network frame format, then lobby metadata, then a small custom-trait blob. `DispatchOrders` appends every **non-immediate** order as the match runs (immediates, `0xFE`, are skipped); `ParseOrders` pushes the whole stream back from frame 0. **There is no snapshot of actors, resources or map state anywhere in the format.** Three consequences that are architecture, not bugs:

- **Load time scales with how long the saved match ran** — loading re-simulates the entire match from tick 0. A five-minute load of a long game is the design working. Only a real snapshot mechanism, or an honest ETA, changes that; micro-optimisation cannot. A free ETA is already available: `World.GameSaveLoadingPercentage` is `NetFrameNumber * 100 / GameSaveLastFrame` (`World.cs:123`), both terms known up front and near-linear in ticks.
- **The fast-forward is already accelerated and already skips drawing** — `logicInterval` drops to 1 ms with rendering capped at 5 FPS (`Game.cs:1001-1005`), `OrderManager.SuggestedTimestep` returns 1 while `IsLoadingGameSave`, the force-render-per-tick throttle is suppressed (`Game.cs:1031`), and `RenderTick` skips viewport/renderables/draw entirely. **One leftover is un-gated:** `world.TickRender(worldRenderer)` (`Game.cs:813-815`) is gated only on `LocalFrameNumber > 0`, **not** on `IsLoadingGameSave`, so it runs once per replayed tick — driving `ITickRender` across every actor for output that is never drawn. Unmeasured, and the only place free speed plausibly remains.
- **Every real save necessarily records a trailing `Pause`.** Saving is reachable only from the in-game menu, and opening it issues a non-immediate `SetPauseState(true)`. So the restore always ends paused, and `LoadWidgetAtGameStart.GameLoaded` compensates by unpausing and re-opening the options menu to reproduce the player's saved context. A test probe that calls `RequestGameSave` directly therefore **exercises none of this and still looks green** — the faithful shape is pause, let the order settle, *then* save. (And once paused, `World.Tick` stops ticking actors, so `ITick` never fires again — probe logic from that point must live in `ITickRender`, which runs regardless of pause.)

**The restore is validated by exactly ONE sync-hash comparison, and failing it produces a game the player can never resume.** `GameSave.ParseOrders` ends by sending the recorded sync packet (`:262-263`); the client sends a real hash only once `NetFrameNumber >= GameSaveLastSyncFrame`; a mismatch calls `OrderManager`'s `OutOfSync` → `World.OutOfSync()` → `EndGame()` → `SetPauseState(true)` and a latched `IsGameOver`, after which `SetPauseState` early-returns and `UnitOrders` **drops** inbound unpause orders. The observable is "the game seems ended, I can't unpause it". There is now a PITFALL at the site (`World.cs:692`).

- **Enumerate the setters, not the story.** `World.EndGame()` has **four** call sites, not one: `MissionObjectives.cs:180` (normal win/loss), `World.OutOfSync` (`World.cs:698`), and two Lua fatal-error handlers (`Scripting/ScriptContext.cs:274`, `:296`). Reasoning that *one* caller's precondition is unsatisfiable does not establish that the flag cannot be set — that error kept the real cause of a live bug closed. `SyncReport.DumpSyncReport` has exactly one call site inside `OutOfSync`, so **the presence of a `syncreport-*.log` distinguishes the desync caller from the objectives caller.**
- **Saved-game restore is green at real-match scale as of 2026-08-16 — five passes across four seeds and both player configurations.** `test-savegame-resume-riverzeta` passes at seeds `-324877760`, `1017`, `-777333` and `20260816`, and the human-vs-bot variant `…-riverzeta-human` passes too, retiring the long-standing "every result comes from a spectator plus two bots" caveat. Each was checked non-vacuous the same way: the gated-ambusher mechanism logged as live rather than idle, and **no `syncreport-*` bearing the run's timestamp** — that file is written only from `OutOfSync()`, so its absence is the positive evidence the restore passed its single validating comparison. *(**Corrected 2026-08-19.** This bullet previously read "as of 2026-08-12 … not reliably deterministic at real-match scale". The cause was a bot module granting a condition directly instead of issuing an order; fixed at `61546a51`, breadth at `fc145288`, configuration at `a06adaf4`.)*
  - **What is still open is narrower and worth keeping.** The static audit bounded *bot mutates → synced reads*; it does **not** bound the reverse — synced code reading state that only bot ticks refresh — and no detector exists for that shape. Restore suppresses bot ticks entirely (`ModularBot.cs` early-returns while `IsLoadingGameSave`), which is sound only while no bot tick has synced side effects. **Standing hazard: any future `IBotTick` module that draws `SharedRandom` silently breaks saved-game restore, with no symptom until someone loads a save.** Five greens do not speak to either of these.

**Diagnostic fingerprint — black terrain + correct minimap + floating health bars means a PALETTE fault, not a broken map or terrain renderer.** `MenuPaletteEffect` is an `IPaletteModifier`, so it reaches only *palettised* rendering — terrain and actor sprites. Chrome, the radar minimap texture and world annotations (health bars, selection/ownership decorations) are drawn RGBA and bypass palettes entirely. **The map data is provably fine precisely because the minimap drew it.** (The concrete instance — the trait initialises `from = to = Black` and upstream defers the saved-game fade-in to a menu that resolves a *different* trait, `MenuPostProcessEffect` — was fixed at `1c80e279` by fading in directly from `INotifyGameLoaded.GameLoaded`; the fingerprint outlives the bug.)

## Replays: the version gate is inert for dev builds, and divergence is reported rather than silent

**`Metadata.Version` cannot distinguish two builds made from this repo.** `ReplayCompatibility.cs:87` is `if (installedVersion != replayVersion) return IncompatibleVersion;`, and the recorded value comes from `World.cs:272` (`Version = Game.ModData.Manifest.Metadata.Version`, alongside the fingerprint at `:276`). That string is a frozen literal: `mods/ww3mod/mod.yaml:3` reads `Version: release-20230225`, rewritten only by the manual `version` target (`Makefile:177-179`), which `all: engine` (`Makefile:157`) does not depend on — and `git log -p` over that file shows the `Version:` line touched exactly once ever, in `4894008b` (2023-03-19). So every dev build compares `release-20230225` against itself and passes. **Do not cite "replays would refuse to load" as a safety net.**

**But the check is not useless, because release packaging DOES stamp a real tag** — into the staged copy rather than the working tree: `packaging/macos/buildpackage.sh:158`, `packaging/linux/buildpackage.sh:86` and `packaging/windows/buildpackage.sh:108` each call `set_mod_version "${TAG}"` on `mods/${MOD_ID}/mod.yaml` under the build output. (Note the repo has both `packaging/` and `engine/packaging/`; only the former stamps ww3mod.) The comparison is therefore inert between two dev builds and live between a release and anything else.

**A replay that diverges is NOT silent — the sync check runs during playback.** This premise was wrong in two task briefs and one commit message before a review caught it, and it changes what a replay guard should do. `ReplayConnection.SendSync` enqueues the hash the LOCAL simulation just computed (`ReplayConnection.cs:101-104`) and drains it into `orderManager.ReceiveSync` on the next receive (`:108-109`); the hashes RECORDED in the file arrive through the same door, parsed at `:117-118`. Both land in `OrderManager.ReceiveSync` (`OrderManager.cs:225-234`), which keeps the first value seen for a frame and calls `OutOfSync(frame)` when the second disagrees, raising the ordinary Quit/Stay prompt. `DesyncWatcherLogic.cs:51-52` states it from the other side: a null desync *report* is "the normal case in a replay". **Consequence: a build mismatch is a reason to WARN, not to refuse** — the engine already detects and reports the real divergence, and a guard that blocks playback is worse than the bug it diagnoses (the join path reached the same conclusion independently, `Server.cs:545-556`).

**Saves have no version or mod check at all** — `GameSave(string filepath)` (`GameSave.cs:107-140`) reads offsets, markers, settings and slots and never looks at either. They rely on the same sync mechanism, via the single recorded packet at `GameSave.cs:262-263`. So "saves are the well-behaved case, replays are not" is the wrong framing: both rest on the sync hash, and replays additionally carry a version field that happens to be inert.

### `BuildFingerprint`: three segments that differ in KIND, and only two can carry a gate

`BuildFingerprint.ForMod` (`:99`) is `engineRevision/rulesHash/assetDigest`.

- **Segment 1, engine revision, is only as good as its pathspec.** Stamped at build time from git (`engine/Directory.Build.targets:121`). It was once `git rev-parse --short=10 HEAD` — whole-repo HEAD — so a commit touching nothing but `WORKSPACE/` changed it. At 50–122 commits a day here that made the segment **a clock, not an identity**: anything gating on it rejects for a docs edit and names "engine build" as the reason, which is false. Now scoped with `git log -1 --abbrev=10 --format=%h -- engine mods`. The DIRTY-tree suffix keeps an `engine`-only pathspec for a separate still-valid reason recorded in that file: including `mods/` turned every YAML edit into a full engine rebuild.
- **Segment 3, asset digest, is NOT machine-specific.** `ComputeAssetDigest` (`BuildFingerprint.cs:369-396`) hashes only the **leaf names** inside each mounted package, sorted and lower-cased, because `Folder.Contents` selects `Path.GetFileName` (`Folder.cs:35-38`). Two machines holding the same Red Alert extraction produce the SAME digest despite different absolute paths. *(An earlier docstring three lines from that code claimed it was "machine-local by construction" — it was wrong, and this is the corrected form.)* The real reason to keep it out of a gate is narrower: two installs can legitimately hold different content **sets**, and a digest cannot tell "different but equivalent for this replay" from "actually divergent".
- **Excluding it is not free.** A missing sprite shortens an animation rather than erroring, and `WithMakeAnimation` grants a condition for exactly as long as its sequence plays — so a content difference genuinely can move the simulation. That case is left to the sync check, which reports rather than guesses.

So the replay check weighs only the first two segments (`ReplaySegmentsMatch`, `:158`), and `DescribeReplayDifference` (`:186`) truncates before describing, so the warning never names game content as the culprit when game content was not weighed. In the multiplayer handshake the fingerprint is computed and **logged only** — `Server.cs:557-562` writes `buildMismatch` to the server log with no reject, by the explicit design argument at `:545-556`.

### Replay metadata is read BACKWARDS from the end, so a string round-trip test cannot see a stamp error

`ReplayMetadata.Read` does not parse from the top: it seeks to `-(4 + 4)` from `SeekOrigin.End`, reads a length and an end marker, then seeks **backwards** by `-(4 + 4 + dataLength + 4 + 4)` (`FileFormats/ReplayMetadata.cs:92-97`). Anything added to `GameInformation` lengthens the very byte count `Read` navigates by. A `Serialize`/`Deserialize` test is a **string** round trip and is structurally blind to that class of error — `GameInformationStampTest` originally stopped there, and now carries two file-level tests beside the two string ones (`BuildFingerprintSurvivesTheReplayFileRoundTrip`, `MetadataWithoutTheStampSurvivesTheReplayFileRoundTrip`). **Any change to what gets stamped into a replay needs a test that writes and re-reads an actual file.**

Practical consequence: a replay's stamp is readable with no game involved — `tail -c 3000 <file> | strings` shows the `BuildFingerprint`, mod, version, map uid and map title. Pre-stamp replays carry no `BuildFingerprint` line at all, so stamped and unstamped files are distinguishable in the file itself.

**Choosing which replay to open is a map-cache problem, and the check ORDER hides it.** `ReplayCompatibility.Resolve` returns `UnavailableMap` **before** any build check (`ReplayCompatibility.cs:93-94`), deliberately and with the reason in-code at `:90-92` — a missing map stops playback outright, so reporting a build warning instead would name the smaller problem. A map uid is a content hash, so *any* edit to a map package invalidates every replay recorded against it, and a session spent to photograph the build-mismatch dialog gets the map dialog instead. Pick a replay whose map package has not been touched since the recording (`git log -1 -- <map dir>` against the replay's date). Autotest scenarios are in the map cache (`mod.yaml` registers the folder) and are in practice more stable than the shipped maps.

**`Launch.Replay` is the whole dialog path and does not need the replay browser.** `BlankLoadScreen.cs:79-99` hands it straight to `ReplayUtils.PromptReplayCompatibility` with `onWatch: Game.JoinReplay` / `onCancel: Game.LoadShellMap` — the same call the browser makes, so one launch argument exercises the shipped decision, strings and buttons (`tools/autotest/watch-replay.sh` wraps it). **But "a dialog appeared" and "the button was consumed" are both untrustworthy predicates here:** cancel loads the shellmap, which is a real world with terrain and units, so "the screen shows a game" is satisfied by the *dismissal* just as well as by the watch. The discriminators are the in-game HUD with a running clock versus the main menu, the pause panel titled with the *recorded* map's name, and — non-visually — the engine log line `Sync reports disabled (… replay True)` emitted when a replay world is created (`OrderManager.cs:169-171`; note it is built by string interpolation, so grepping the literal `Sync reports disabled` finds nothing in source).

## Fog visibility: `Detectable` is the mod's visibility trait, and `FrozenUnderFog` is a dead end

**`Detectable` (`Traits/Modifiers/Detectable.cs`) is the mod's `IDefaultVisibility`, and it is also the render gate.** Its `ModifyRender` (`:293`) returns `SpriteRenderable.None` (`:304`) when `IsVisible` is false, so the trait decides whether a sprite is drawn at all, not merely whether the actor is targetable. (One exception: with the dev-mode `CosmeticReveal` flag set it returns semi-transparent ghosts instead of nothing.) **There is no `HiddenUnderFog` in this engine** — do not go looking for one.

**`Detectable.Vision` runs the opposite direction to its name.** It is *"what level of vision is required to detect this actor"* (`:24-25`, default `2`) — a **concealment** stat the observer has to beat, resolved through `byPlayer.MapLayers.AnyDetectable(...)` at `:149`. It is **not** a reveal radius and grants the actor no sight whatsoever. **Raising it hides the actor better.** `test-case01b-detect` leans on exactly this, dropping defenders 3→1 to make them *easier* to see.

**Do not reach for `FrozenUnderFog` to make anything non-building survive fog. Two independent blockers, either one fatal:**

1. It is declared `Requires<BuildingInfo>` (`Traits/Modifiers/FrozenUnderFog.cs:21`), so putting it on an actor without a `Building` trait is a **load failure, not a no-op**. Husks, units and vehicles are all out. This is the half worth remembering — the natural assumption is that an inapplicable trait is merely inert.
2. Since the `QUICK FIX 260503` short-circuit its `IsVisible` ends in an unconditional `return true` (`:140-148`), with the real `IsVisibleInner` call commented out beneath it. Every actor carrying it today is visible to **everyone, always**, regardless of fog or relationship. Any reasoning that treats it as "remembered image, updated on re-observation" is reasoning about code that is not running. (Frozen-actor *creation* via `ICreatesFrozenActors` is a separate path and does still run — which is why fog-frozen structure GPS dots still work.)

**`AlwaysVisibleRelationships: Ally` includes the owner themselves.** `Player.RelationshipWith` returns `Ally` for `this == other` (`Player.cs:250-251`), and also for spectators (`:257-258`, provided the owner is not `NonCombatant`). So `Ally` is the idiom for *"the owner keeps seeing this through fog; enemies still have to earn it"* — there is no self-only relationship value and none is needed.

**An autotest screenshot cannot verify a fog-dependent visibility change by default.** `TestModeLogic.cs:31` nulls `RenderPlayer`, and every `IDefaultVisibility.IsVisible` in the mod short-circuits to `true` on a null player — so a fogged-out actor renders in the capture anyway and **the shot reads green before and after the fix**. Pass `AUTOTEST_EXTRA_ARGS="Test.KeepRenderPlayer=true"` to `run-test.sh` (the generic launch-arg passthrough at `tools/autotest/run-test.sh:735`; there is no dedicated flag).

**Aircraft wrecks are two-stage, and six airframes have no second stage.** A shot-down aircraft spawns an airborne `*.Husk`, which `FallsToEarth` drives down until `self.Kill(self)` on impact; that husk's own `SpawnActorOnDeath` then leaves the persistent `*.Husk.ground` (`^Husk`, `HuskDecay: Delay: 2240` ≈ 134 s at 16.67 tps, `husks/husks-vehicles.yaml:14-16`). Of the 16 airframe husks in `husks/husks-aircraft.yaml`, ten have that second stage; `BADR`, `B52`, `BULL`, `U2`, `U2.NATO` and `SMIG` do **not** — they explode on impact and leave nothing behind *(as of 2026-08)*.

## The black band at a map edge is a deliberate overlay, not a terrain render failure

Reported as *"edge tiles are not rendered, but actors placed there are rendered"* on the main-menu shellmap. Three things had to be true at once, and only the third was a bug.

- **`TerrainSpriteLayer`'s `restrictToBounds` clips ROWS ONLY, never columns.** It uses the visible-cell region solely to pick a `firstRow`/`lastRow`, then emits whole rows at full width (`engine/OpenRA.Game/Graphics/TerrainSpriteLayer.cs:207-231`). So the left/right one-cell border columns were **already** being drawn as terrain; only the top/bottom border rows were ever clipped. **Anyone reasoning "`restrictToBounds` hides the border" will predict the wrong edges.**
- **What actually paints the black is `DrawBeyondMapFog`** (`WorldRenderer.cs:403`, called at `:344-345` under `World.Type != WorldType.Editor`). It fills **fully opaque** black between the viewport edge and the map rect, deliberately **after terrain but before actors** so tall sprites near edges still show (comment at `:341-343`). That ordering is the whole reason actors appear to float: the black is painted, then actors draw on top of it.
- **The ring between `Bounds` and `MapSize` is full of authored scenery.** Every one of the 10 maps is `MapSize N,M` / `Bounds 1,1,N-2,M-2`, and **8 of 10 author actors in that unplayable ring** — `river-zeta-ww3` (the `FirstTimeShellmap`, `mod.yaml:9`) has **189**, including 102 `v17` village buildings and 29 `rice`; `woodland-warfare-ww3` 115; `siberian-pass-ww3` 36. Those sprites were the things standing on black. *(as of 2026-08, parsed from the map files)*

**Why it only showed in the menu.** In a match the ring is covered by opaque shroud: `ShroudRenderer` builds `tileInfos` over `Map.AllCells` — the full `MapSize` — at `ShroudRenderer.cs:123`, while `MapLayers.GetVisibility` returns **0 for any cell outside playable `Bounds`** (`Traits/Player/MapLayers.cs:659`, guard at `:663-664`, and `Map.Contains(PPos)` is `Bounds.Contains` at `Map.cs:1418-1421`). Visibility 0 ⇒ shroud sprite at full opacity. But the shellmap has **`RenderPlayer == null`**, and `ShroudRenderer.UpdateShroud` clears every dirty cell's sprites and then `continue`s without repainting when there is no render player (`:247-285`, `:272-273`) — so the ring loses its cover. `DrawBeyondMapActorFog` (`WorldRenderer.cs:450`), the pass that would fog actor overflow to match, also early-returns on `renderPlayer == null` (`:452-454`). **Same root applies to observers and to TestMode's full-map viewer** — which is why an autotest screenshot of a map edge does not look like what a player sees.

**Geometry rules out "just render the border" as the fix.** `Viewport.Center` and `Scroll` clamp only the viewport **centre** into the playable rect (`Viewport.cs:326`, `:339`), so the edges overhang by up to half a viewport — **~27 cells horizontally at 1080p** (960 px ÷ (24 px `TileSize` × 1.5 zoom)), more via the main menu's own 4× zoom-out. The border is one cell; rendering it can never fill a 27-cell overhang. The opaque overlay has to stay — it just has to start at `MapSize` instead of `Bounds`, which is what `bc22c9d6` did (`DrawBeyondMapFog` now computes its rect from `map.MapSize`, and `TerrainRenderer.cs:84` passes `restrictToBounds: false` unconditionally).

**Reinforcements are NOT affected, contrary to the obvious worry.** `GetSameEdgeCells` measures against `Bounds.Left`/`Bounds.Right - 1` (`Map.cs:1816-1830`) — the **playable** edge — so `ProductionFromMapEdge` spawns inside `Bounds` and never in the ring. Rendering the ring changes nothing about where units appear or how they walk in. *(Known and unfixed: `Map.ChooseClosestEdgeCell` (`Map.cs:1745-1758`) uses bare `Bounds.Right`/`Bounds.Bottom`, which are **exclusive**, so the legacy no-`SpawnArea` path can name a ring cell. Not exercised by the shipped maps.)*

## Widget / chrome authoring gotchas

Engine widget behaviors that fail **silently** — each cost real debugging time in the lobby work:

- **A null `targetLineColor` draws NO LINE AT ALL — it is not a fallback to a default colour.** `Move.TargetLineNodes` (`Activities/Move/Move.cs:453`) and `Attack.cs:362` both guard `if (targetLineColor != null)` before yielding, and the base `Activity.TargetLineNodes` (`engine/OpenRA.Game/Activities/Activity.cs:272-275`) is a bare `yield break`. So every call site that omitted the argument produced a unit that moves or opens fire with **zero** on-screen explanation. **If you are wondering why a unit moved and there was no line, the answer may be that there was never going to be one.**
  - **Two independent gates decide whether a line is visible, and they are easy to conflate.** Lines come from `IRenderAnnotationsWhenSelected`, which `WorldRenderer.cs:188-231` walks over `World.Selection.Actors` only (plus everything friendly while `ShowAllOrders` — spacebar — is held). *On top of that*, `DrawLineToTarget.ShouldRender` requires `Game.RunTime <= lifetime`, and `lifetime` is re-armed only by `LineTargetExts.ShowTargetLines` (called from order resolution) or by `INotifySelected.Selected` (`DrawLineToTarget.cs:63-75`). Consequence: **selecting a unit to find out where it is going buys exactly `Delay` ms of answer, then goes dark while the unit is still walking.** Most automatic sources never call `ShowTargetLines` at all — `AutoFollowAlly`, `Wanders` and `AutoCarryall` have zero references to it, though `AutoSeekSupplies` (`:203`, `:302`) and `AmmoPool` (`:604`, `:619`) do.
  - **"Automatic" is now a colour, and `AutomaticOrder.LineColor` is the whole vocabulary** (`engine/OpenRA.Mods.Common/AutomaticOrder.cs:43`, DodgerBlue `30,144,255`; predicate `IsAutomatic(Color)` at `:45-48`). One colour meaning "the GAME issued this", threaded through the existing `targetLineColor` parameter at **nine sites / sixteen usages** (`SeekSuppliesAndReturn`, `SeekSupplyProvider`, `AutoCrusher`, `AutoFollowAlly`, `Wanders`, `AttackBase:738`, `Mobile:946,956`, `ScaredyCat:164`, `StancePositioningExecutor:414`) rather than a provenance flag on `TargetLineNode`, which would have needed 29 call sites. `DrawLineToTarget.ShouldRender` (`:95`) exempts automatic nodes from the `Delay` timeout via `HasAutomaticNode` (`:103-116`) — load-bearing for one-cell corrections, where a line calibrated to confirm a player's own click would expire while the unit was still visibly moving. **The colour alone is not enough and nobody should "fix" it by adding a `ShowTargetLines()` call at the queueing site**: `lifetime` is never armed for a self-issued move, and `HasAutomaticNode` is what closes that.
  - **Do not cite the old "blue line means automatic" as precedent — it was `self.Owner.Color`**, the player's own colour (`AutoFollowAlly`, pre-`4a696e2c`). It looked blue only because that player was blue; a player who picked green got a line identical to `MobileInfo.TargetLineColor` (`Mobile.cs:80`, `Color.Green`) and one who picked red collided with `AttackBaseInfo.TargetLineColor` (`AttackBase.cs:28`, `Color.Crimson`). It carried no semantics whatsoever.
  - **Provenance exists for attacks and does not exist for moves.** `AttackBase.cs:12` declares `enum AttackSource { Default, AutoTarget, AttackMove }`, with the predicate `AutoTarget.IsAutoAcquiredSource` (`AutoTarget.cs:1068`) and a consumer in `AttackBase.BreakOffApplies` (`:672`) — so provenance and colour already travel together down `GetAttackActivity(…, source, …, targetLineColor)`. There is no equivalent for movement: `Order` (`engine/OpenRA.Game/Network/Order.cs:60-73`) carries no provenance field, and `IMoveInfo.GetTargetLineColor()` (`engine/OpenRA.Game/Traits/TraitsInterfaces.cs:607`) takes no arguments, so it physically cannot distinguish caller intent.
- **`LobbyOptionsLogic` picks its category from a hidden label and DEFAULTS TO `Advanced` when the label is missing — so a panel that forgets it shows only Advanced options.** `var categoryLabel = widget.GetOrNull<LabelWidget>("CATEGORY_FILTER"); category = categoryLabel?.Text ?? CategoryAdvanced;` (`LobbyOptionsLogic.cs:227-230`). The **only** `Label@CATEGORY_FILTER` declared in any chrome file is `engine/mods/common/chrome/lobby-players.yaml:878` — the pre-game lobby. `engine/mods/common/chrome/ingame-info-lobby-options.yaml` has none, so the in-game Options tab is Advanced-only, while every option that actually works (`fog`, `explored`, `startingcash`, `gamespeed`, `timelimit`, `startingunits`, `passiveincome`, `incomemodifier`, `bounty`, `separateteamspawns`, `cheats`, sync reports) is in `CommonOptionIds` (`:71-86`) and filtered out at `:326-328`. **Two further silent guards compound it:** `RenderAdvancedSections` skips any section that is entirely placeholders (`:379-380`, and the catch-all "Other" carries the same guard at `:391`), and `AddSectionHeader` silently no-ops when the panel has no `SECTION_HEADER_TEMPLATE` (`:225`, `:261-262`) — so a panel can be *fixed* into rendering options and still show them un-grouped. **Nothing in this chain reads `LocalPlayer` or `IsObserver`** (grep: zero hits), so an empty in-game Options tab is not a spectator bug however it is reported. *(As of 2026-08-30 the ww3mod in-game tab draws nothing at all: what survives the Advanced filter is `LobbyDummyOptions` (`mods/ww3mod/rules/world.yaml:443`), which stamps `Placeholder = true` on **every** option it yields including the Rules ones (`LobbyDummyOptions.cs:30-40`), and the only trait that could have produced a non-placeholder Advanced option, `PowersLobbyOptions`, is commented out at `world.yaml:555`. Read-only rendering is already correct — `GameInfoLogic.cs:172` passes `configurationDisabled: () => true`.)*
- **The spectator branch of the stats panel shifts by the objective block's FULL height, unclamped — so margin added above it is re-eaten.** When `world.LocalPlayer` is null, `GameInfoStatsLogic.cs:120-127` hides `OBJECTIVE` and does `statsHeader.Bounds.Y -= objectiveGroup.Bounds.Height; playerPanel.Bounds.Y -= …` with no floor. That height is **75** (`engine/mods/common/chrome/ingame-infostats.yaml:6-7`), the header row's authored `Y` is **81** (`:31-33`), and the panel is pinned at `Y: 65` (`engine/mods/common/chrome/ingame-info.yaml:119-120`, mirrored at `mods/ww3mod/chrome/ingame-info.yaml:160-161`) while the tab strip occupies **Y 50→75** (`:38-42`, `Y: 50` + `Height: 25`). So a spectator's header box begins at `65 + (81 − 75) = 71` — **4px inside the tab strip**; it does not visibly collide only because `LabelWidget` centres text in its 25px box. For a player the same headers sit at `65 + 81 = 146` and are clear. **Consequence for anyone fixing "no margin under the tabs": moving the `Y: 65` pin is not sufficient — both have to change together.** Separately, that file's header row and data row are two coordinate systems that were never reconciled (Player header abs X 32 vs name X 51, the row reserving 29px for `Image@PROFILE` that the header does not; Faction header X 252 sits on the flag, not the text at X 286; Score header X 419 vs value X 414) and the string `Align` **appears zero times** in it, so numeric columns are left-aligned — while the observer panel next door uses `Align: Right` 45 times (`mods/ww3mod/chrome/ingame-observer.yaml:299`, `:308`, `:317`, …).
- **`ImageWidget` draws sprites at native size.** `Width`/`Height` are layout-only; `Draw()` calls `WidgetUtils.DrawSprite(sprite, RenderOrigin)` and ignores widget bounds (`ImageWidget.cs:78-91`). To scale a sprite into its bounds use the opt-in `ScaleToBounds: True` (uniform, centered). **When you add a field to a widget, mirror it in the copy-constructor** (`ImageWidget.cs:61`) — template clones run through the copy-ctor and silently drop any field you forgot.
- **Upstream's sub-`MinZoom` decoration cull is a SPECTATOR-era assumption that WW3MOD invalidated — do not reinstate it.** `SelectionDecorationsBase.DrawDecorations` used to `yield break` the whole `IDecoration` loop when `Viewport.Zoom < Viewport.MinZoom`, on the upstream premise that sub-`MinZoom` was reachable only via the observer shroud selector or the map editor (still the only two `UnlockMinimumZoom` callers). WW3MOD broke that premise at `60f27056` by setting `Viewport.unlockMinZoom = true` at **field-initializer level** (`Viewport.cs:69`) — i.e. for every viewport — with `unlockedMinZoomScale = 0.25f` (`:70`), so `MinZoom` sits near the *bottom* of the ordinary player's range and the guard fired across a large part of normal play. The visible report was "cargo/ammo pips vanish about halfway zoomed out", but the guard was one unconditional `yield break` in front of the whole decoration loop, so it took out **every** `WithDecorationBase` — including the 100+ plain `WithDecoration` uses (damage pips, garrison-health) — while selection boxes and health/extra bars, rendered *earlier* in the same method (`:105-111`), were untouched. That asymmetry is why the bug read as "pips only". Nothing needed rescaling: pips are `UISpriteRenderable`s drawn at fixed screen-pixel size with no viewport term, and their scale is driven by selection (1f/0.5f), never zoom — deleting the cull was sufficient. There is now a PITFALL comment at the site (`:125-128`) and `Test.SetZoom(scale)` (`Scripting/Global/TestGlobal.cs:104`, scale as a multiple of `MinZoom`) to drive camera zoom from a scenario; a screenshot reads the last *rendered* frame, so a zoom change and its capture cannot share a tick.
- **`ButtonWidget` renders nothing for a missing chrome variant.** A highlighted button looks up `<Background>-highlighted` (`ButtonWidget.cs:320`), plus `-hover`/`-pressed`/`-disabled` suffixes; if that collection is absent, `WidgetUtils.DrawPanel` early-returns with no error and the button draws with no fill. Any custom `Background:` needs the full variant set.
- **In the lobby, `TOP_PANELS_ROOT` is a MID-STACK container, not an overlay root — a widget parented there renders under half the screen.** OpenRA paints children in **declaration order with no z-sort**: `Widget.AddChild` appends to `Children` (`Widget.cs:526-530`) and `DrawOuter` draws self then walks `Children` in order (`:500-509`). In `engine/mods/common/chrome/lobby.yaml` (which ww3mod inherits wholesale via `mod.yaml:193` — there is **no** `mods/ww3mod/chrome/lobby.yaml`), `Container@TOP_PANELS_ROOT` is declared at `:255`, and `MAP_PREVIEW_ROOT` (`:265`), `MAP_BROWSE_ROOT` (`:273`), `MUSIC_PANEL_ROOT` (`:282`), `LOBBYCHAT` (`:339`) and the bottom CTA banner (`:400+`) are all **later siblings**. Every one of them therefore paints over anything parented into `TOP_PANELS_ROOT` — including a dialog declaring `Width: PARENT_WIDTH`. **Anything that must sit above the lobby has to be parented to something declared after `LOBBYCHAT`, or the layout has to be reordered.** The trap is live: `TOP_PANELS_ROOT` is still the parent for `LOBBY_PLAYER_BIN` (`LobbyLogic.cs:283`) and `LOBBY_SERVERS_BIN` (`:532`). This bites anything in the engine that assumes the stock RA lobby's structure, where the panel bin happened to be near the end.
- **A SCREENSHOT CAN NEVER DEMONSTRATE A SELECTION IN THIS MOD — verify selection from game state, not from a capture.** Two independent mechanisms, and neither is obvious from the picture. **Infantry** are explicit: `^Infantry` sets `SelectionDecorations: ShowNever: true` (`infantry.yaml:55`, the only `ShowNever` in the mod) and `SelectionDecorationsBase.cs:109` is literally `if (selected && !Info.ShowNever)`, so no selection box is ever drawn for any infantry. **Vehicles are the surprise:** own vehicles render white corner brackets and pips *whether or not they are selected*, because `renderDecorations = selected ? selectedDecorations : decorations` (`:129`) — the unselected path draws them too — so the bracket reads as a selection box and is not one. Measured by full-frame pixel diff: selecting four Bradleys changed **zero pixels** on those units. What *does* change is UI chrome (the command bar, the notification feed), not the world. Use `Test.GetSelectedCount()` / `Test.GetSelectedCountOfType(type)` (`Scripting/Global/TestGlobal.cs:187`, `:194`); two full scenario rewrites were burned chasing a visible selection box that exists for no unit type.
- **An UNKNOWN substitution symbol in a coordinate expression evaluates to 0 — no throw, no warning — so one wrong identifier puts a whole panel off screen.** `VariableExpression.ParseSymbol` is `symbols.TryGetValue(symbol, out var value); return value;` (`VariableExpression.cs:664-667`), and a missing key yields `default(int)`. `Widget.ApplyBounds` registers exactly four symbols — `WINDOW_WIDTH`, `WINDOW_HEIGHT`, `PARENT_WIDTH`, `PARENT_HEIGHT` (`Widget.cs:294-297`). The concrete instance: `CARGO_PANEL` was declared `X: WINDOW_RIGHT - 240` / `Y: WINDOW_BOTTOM - 340` — names that were renamed out of upstream OpenRA (there is a migration rule in-tree, `UpdateRules/Rules/20231010/RenameWidgetSubstitutions.cs`) — so it resolved to `X = -240, Y = -340` and sat entirely outside the window, ticking and handling input normally while painted where no one could see it. **When a panel "doesn't show", check its resolved bounds before its visibility predicate**: the predicate is the obvious suspect and the bounds are the silent one. A design review that reasons about a widget's layout from its YAML cannot tell you the widget is visible — one investigation costed three redesign options for a panel that had never appeared on a screen.
  - **Guarded since `a72a88ba` by the `CheckChromeIntegerExpressions` lint — which has a blind spot: it only opens layouts the manifest lists.** `Run` iterates `modData.Manifest.ChromeLayout` (`CheckChromeIntegerExpressions.cs:65`), so a `chrome/*.yaml` nobody registered is never opened, and every expression in it is unchecked. **A layout file absent from the manifest is also invisible to the game**, and reads exactly like working code. Two exist today *(as of 2026-08)*: `chrome/_lobby-palette.yaml` (deliberate — a colour reference cited only from comments, defining no widgets) and `chrome/garrison-panel.yaml`, which does define `Container@GARRISON_PANEL` (`:1`) and is dead, the live panel of that name being defined inline at `ingame-player.yaml:629`.
- **A widget list keyed on `ISelectable.Class` gets one row per CLASS-LESS actor, so "how many rows" is not answerable from the obvious roster.** `CargoManifest` groups passengers by `ISelectable.Class` **falling back to the actor name** when the class is empty (`CargoManifest.cs:50-53`, Actor adapter at `:76-79`); both the unload menu and the sidebar cargo panel are drawn from it, so this count bounds the rows in either. Counting `Cargo: Types: Infantry` passengers *(as of 2026-08)* gives **24** distinct keys, not the 16 combat classes: plus `CivInfantry`, `Pilot` — which four actors share, `crew.{pilot,copilot}.{america,russia}` all setting `Selectable: Class: Pilot` (`crew.yaml:66-67,82-83,130-131,146-147`) — and **six** separate `crew.{commander,driver,gunner}.{america,russia}` keys, ejected vehicle crews that set no `Class` and so group under their own actor names. All 24 fit one 36-weight Chinook (`aircraft-america.yaml:72-73`), so the worst case is 24 rows, not 16. **Whenever a group key falls back to an actor name, every class-less actor is its own row.**
- **When one widget carries both an ACTION and a FACT, a deletion argued on the action silently takes the fact with it — and every artefact you would audit with is written in the vocabulary of the action.** The concrete case: `7b5c692b` deleted the cargo passenger rows. Those rows' buttons were control (MARK / EJECT / RALLY plus a drop order generator); their label was readout — the passenger's name and ammo, `Rifleman [3/6]`. The commit reasoned about control only, and reasoned *correctly* — the J menu is a better home for aiming a drop, and the order generator carried a real defect. **Nothing in the commit, its message, or the replacement inherits the readout**, and the replacements do not carry it: the unload menu renders only a group label and an `x{N}` count (`CargoUnloadMenuLogic.cs:160-166`) under a `{title} {PassengerCount}/{MaxWeight}` header (`:114`), `WithCargoPipsDecoration` renders a count and a per-type pip colour, and the sidebar panel shows a total. So after a well-reasoned deletion the game had nowhere at all that named *who* was aboard a transport, still less their ammo or health. The right answer to "was this deleted for a good reason?" was **yes for the buttons, no for the label**. **Before deleting a control, ask what its label said and where that fact moves** — a commit message can be honest, complete and specific and still leave this invisible, because "deletes the superseded per-passenger panel" is true of the buttons and false of the label.
- **Hidden widgets keep keyboard focus.** `Widget.IsVisible` is `() => Visible` (`Widget.cs:231`) — it checks the widget's OWN `Visible` flag, not its ancestors'. A focused `TextField` whose parent tab is hidden still looks visible to the focus system, so it keeps eating key presses (and Enter can fire its `onSelect`). Any tab-switch that hides a focused widget must hand focus off explicitly.
